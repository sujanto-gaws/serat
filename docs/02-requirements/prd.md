## Problem statement

Past a few thousand notes, a plain-Markdown vault becomes a small, badly-typed database, and the tools for interrogating it (Obsidian Bases, Dataview) are read-only, frontmatter-only or per-render JavaScript bolt-ons. Everything in the vault that is not Markdown — PDFs, decks, spreadsheets, screenshots — is unsearchable, unqueryable and untypeable by construction. Serat must deliver typed schemas over plain Markdown, a declarative type-checked query language with writable views, binaries extracted into the same index as notes, and AI that reads the whole graph with every write reviewed — in one fast local binary that opens an existing Obsidian vault unmodified. See the charter for the full wedge and competitive read.

## Users & personas

All personas are the same single vault owner wearing different hats (assumption A-01: one author per vault). Stories are written from the hat that motivates them:

| Persona | Cares about | Stories |
|---|---|---|
| Vault owner | Zero switching cost, files staying plain Markdown, never losing work, installing like a normal app | 10 |
| Systems analyst | Typed data, queries they can trust, rollups, drift detection, spreadsheets beside notes | 5 |
| Project manager | Lens switching, promotion through lifespan folders, every task in one place, dashboards as files | 4 |
| Daily user | Reach any note instantly, search everything, stay fast as the vault grows | 4 |
| Engineer | Letting Claude Code query the vault properly over MCP, never being edited behind their back | 3 |
| Researcher | Reading, searching inside and quoting PDFs and scans; asking the vault a question with citations | 3 |
| Writer / note-taker / query author | Live preview without visible syntax, linking and traversing, catching typos before a table is empty | 4 |
| Privacy-minded / pragmatist / new / long-term / busy user | Keeping folders out of AI entirely, working with no API key, first-run experience, history, one-motion capture | 5 |

## Identifier scheme

`FR-AREA-nn` functional, `NFR-AREA-nn` non-functional, `US-nn` stories, `A-nn` assumptions, `C-nn` constraints. Identifiers are permanent: a dropped requirement is marked dropped, never deleted and never reused.

### Priority and verification

| Code    | Meaning                                                                     |
|---------|-----------------------------------------------------------------------------|
| M       | Must — v1 does not ship without it                                          |
| S       | Should — v1 is materially weaker without it; may slip one phase             |
| C       | Could — Included if the phase has room                                      |
| W       | Won't — Explicitly out of scope for v1 — recorded so it is not rediscovered |
| Test    | Automated test in CI                                                        |
| Bench   | Benchmark against the 20k/50k synthetic vault, enforced in CI               |
| Demo    | Manual demonstration against the phase gate                                 |

### NFR-PRF — Performance

The numeric budgets that constrain every design decision.

| ID         | Requirement                                                                                                                                                  | Pri    | Phase | Acceptance criteria                                                           | Verify  |
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|--------|-------|-------------------------------------------------------------------------------|---------|
| NFR-PRF-01 | **Cold start (Serat term)** — Of the interval from process start to an interactive window and a fully usable vault, at 20,000 notes with a warm index, the portion Serat's own code is responsible for — main-thread setup plus the front end's mount, first composited frame and settle, running inside the platform's webview — shall not exceed 350ms at p95. **NFR-PRF-01 was re-baselined at P0 as a split, not a slackening (ADR-0014, task #104).** The original 400ms/1s targets were carried over from the blueprint with no webview-startup term in them; measured on Windows/WebView2, `WebviewWindowBuilder::build` alone costs 596–1687ms across the runs taken — more than the entire original budget, with no Serat code inside it. The re-baseline partitions cold start into a **platform term** (loader, webview environment and controller creation — unbudgeted, because no change confined to this repository moves it) and a **Serat term** (our main-thread setup plus our front end's mount, first composited frame and settle — the quantity C-06 now binds). 350ms is inside the interval ADR-0014 derives from the measured Serat-term p95 (233.8ms) and the original 400ms ceiling — `[s95×1.3, 400ms]` = `[304, 400]`, non-empty with 96ms of room — chosen with margin above the floor for cross-batch variance the sampled batches cannot bound (F-405), while remaining a real tightening of a number that used to cover the platform term as well.

Four bounds travel with this number and must not be dropped when it is next quoted:

- **One platform.** Attested on Windows/WebView2 only (F-96); WKWebView and WebKitGTK are unmeasured. If their platform terms are of the same order, the *requirement* was wrong rather than the design, and this split is the permanent fix — decided at P1, not here.
- **Warm vault.** Every cold-start figure taken to date is a warm-vault figure; a cold vault could not be produced on the measuring machine (F-154). This is a stated best case, not a floor.
- **Scanner disabled** (`gate_eligible: false`, RISK-012). Both this bound and the warm-vault one push the figure the same way — toward a more flattering number than a first real open will show.
- **The aggregate totals are reported, not gated.** The pre-split totals move roughly 19% batch-to-batch at zero build contention, against roughly 8% for the Serat term itself (F-405, F-407); a scalar that moves 19% between attested batches cannot decide a pass at any budget set on it. Window-visible ≤400ms and vault-usable ≤1s therefore stay as the user-facing description of total wait, not as CI gates — only the Serat term is asserted in CI.

The paint mark this budget depends on was unguarded when the figures above were taken (F-397), and the frame/paint conjunction ADR-0014 specifies is enforced nowhere in the tree that produced them (F-403). Neither defect changes the number; both bound how much weight it can currently bear.

## Open questions

- **NFR-PRF-01's platform term is unbudgeted, not proven irreducible.** ADR-0014 books WebView2 environment and controller creation to the platform because no change confined to this repository moves it — that is a claim about ownership, not a claim that the cost cannot be reduced by version pinning, bundle size or navigation ordering. Whether it responds to anything under our control is untested and is P1's to test.
- **Whether WebView2 is an outlier or representative among the three webviews is unresolved, and it is what eventually decides whether C-07 is even a live question.** If WKWebView and WebKitGTK carry a platform term of the same order at 20,000 notes, NFR-PRF-01's split is the permanent shape of the requirement across all three platforms. If they do not, Windows is the outlier, and only then does it become a question about whether Tauri v2's WebView2 term responds to nothing under our control — which is the point at which C-07 would actually be tested rather than reopened speculatively. Neither branch is decided; both need the same seven-term partition run on the other two platforms.
- **NFR-PRF-03 remains unmeasured.** The harness that exists (`bench/budget/src/subject.rs:517`) calls `IndexHandle::apply()`/`flush()` directly against serat-index, bypassing `AppState::write_file`, `write_atomic`, the re-read/hash and echo suppression — the path the requirement's words name. It cannot detect the degradation that path is meant to catch. Blocked on task #111. No number exists to re-baseline against, so none was taken.
- **NFR-PRF-08 (budgets enforced in CI) cannot be satisfied on the current infrastructure.** CI produces no jobs at all (F-384), for reasons unrelated to this requirement or the code it governs. Recorded here rather than left to fail silently: a Must unmet because of infrastructure reads differently from a Must unmet because a feature is missing, and the gate report must say which this is.
- The performance numbers not covered above are targets carried over from the blueprint, not measurements, and remain open in that sense until a P0 or later spike replaces them.
- Assumptions A-06 (Rust is a learnable cost), A-07 (local embedding quality suffices) and A-08 (extraction quality is good enough) are each verified by a P0 or pre-P2 spike; a negative result re-opens the corresponding pillar.

## Assumptions and constraints

An assumption is something believed true that was not verified; a constraint is a decision already made that requirements may not reopen. Each assumption records what breaks if it turns out to be wrong, because that is the part people forget to write down.

### Assumptions

| ID   | Assumption                                                                                                                             | If it is wrong                                                                                     |
|------|----------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| A-01 | **Single user, single machine** — There is one author per vault. No concurrent multi-user editing is designed for.                        | If collaboration becomes a requirement, the write-back and history design both change materially.  |
| A-02 | **Vault fits on local disk** — Vaults are local folders, not network shares or object stores.                                             | Network filesystems may break the watcher and atomic-rename assumptions.                           |
| A-03 | **Sync is external** — The user runs git, Syncthing or a cloud folder for multi-device sync.                                              | Serat must tolerate files changing underneath it at any moment — hence FR-VLT-04 and FR-VLT-05.    |
| A-04 | **Obsidian remains the reference dialect** — Wikilink, embed and inline-field syntax follow Obsidian and Dataview conventions.            | A divergence in Obsidian's syntax would require a parser update to preserve NFR-CMP-01.            |
| A-05 | **One developer, part-time** — Effort estimates assume solo part-time delivery of roughly 30 weeks to v1.                                 | Any phase gate slipping compounds; scope is cut before gates are weakened.                         |
| A-06 | **Rust is a learnable cost** — The Tauri decision commits the core to Rust rather than Go.                                                | P0 exists in part to measure this friction before the remaining 28 weeks are committed.            |
| A-07 | **Local embedding quality suffices** — A small local embedding model gives adequate semantic recall over personal notes.                  | If not, retrieval leans harder on lexical and graph signals rather than adding a cloud dependency. |
| A-08 | **Extraction quality is good enough** — Open-source PDF and Office extractors produce text of usable fidelity on the user's real archive. | Move 5 in the blueprint exists to test this before the pillar is committed to.                     |

## Glossary

Canonical vocabulary. Where this document, the blueprint, the code and the UI disagree on a term, this section is what the others are wrong about.

| Term                   | Definition                                                                                                                               | Source   |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------|----------|
| **Vault**              | A folder of Markdown files and assets that Serat opens. The vault is the product's unit of scope; there is exactly one per window.       | §04      |
| **Note**               | A single Markdown file in the vault. Also the row representing it in the index.                                                          | §05      |
| **Block**              | A parsed structural unit within a note — paragraph, heading, task, list item, code fence, table. The granularity at which Serat indexes. | §05      |
| **Field**              | A typed key/value pair attached to a note, from YAML frontmatter or from a key:: value occurrence in the body.                           | §05      |
| **Frontmatter**        | The YAML block at the top of a note. One of the two sources of fields.                                                                   | §05      |
| **Inline field**       | A key:: value pair written in the note body. Indexed identically to frontmatter, unlike in Obsidian Bases.                               | §03 B    |
| **Wikilink**           | A link written \[\[target\]\], optionally with \#heading, ^block or \|alias.                                                             | §03 A    |
| **Block reference**    | A ^identifier anchor that makes a specific block linkable from elsewhere.                                                                | §05      |
| **Type**               | A declared shape for a note: named fields with kinds, required-ness, enumerations, defaults and order.                                   | §03 B    |
| **Type note**          | The Markdown note that declares a type. Types are content, not configuration.                                                            | §03 B    |
| **Schema registry**    | The in-memory, hot-reloaded set of all types, used to typecheck queries and validate notes.                                              | §04      |
| **SQ**                 | Serat Query — the declarative query language. Compiles to exactly one SQL statement; contains no host-language escape.                   | §06      |
| **Query block**        | A fenced sq code block inside a note whose results render in place.                                                                      | §03 B    |
| **View**               | A rendering of a query's row set: table, board, calendar, gallery or list. The row set is identical across kinds.                        | §03 B    |
| **Rollup**             | An aggregate computed over notes one link hop from a result row.                                                                         | §06      |
| **Write-back**         | Editing a source note by changing a value in a view. Implemented as a byte-range patch, never a document rewrite.                        | §07      |
| **Field-scoped patch** | A write that replaces only the recorded byte range of one field or task marker.                                                          | §07      |
| **Stale guard**        | The check that refuses a view-originated write when the file's hash changed since the row was read.                                      | §07      |
| **Locator**            | The position of an extracted block inside a binary: page, slide, cell range or timestamp. The binary's equivalent of a byte range.       | §05, §08 |
| **Asset**              | A non-Markdown file in the vault, represented in the index by a row of its own.                                                          | §08      |
| **Sidecar note**       | The companion Markdown file that carries an asset's frontmatter, type, tags, links and annotations.                                      | §08      |
| **Extractor**          | A per-format component that converts a binary into block rows. Runs out of process, capped, with no network.                             | §08      |
| **Extraction cache**   | Extraction output stored by content hash and extractor version, surviving index deletion because it is expensive to recompute.           | §08      |
| **Chunk**              | A span of blocks embedded as one vector for semantic retrieval, carrying its heading path as context.                                    | §09      |
| **Hybrid retrieval**   | Fusing lexical (BM25), semantic (vector) and structural (link graph) signals into one ranking.                                           | §09      |
| **Diff queue**         | The review surface where every AI-originated change waits for explicit acceptance. In-app and MCP writes share it.                       | §09      |
| **MCP server**         | The typed external interface onto the same query API the UI uses, so agents see exactly what the app sees.                               | §09      |
| **Lens**               | A role-scoped configuration — filter, dashboard, pinned views — declared as a note and switchable in one keystroke.                      | §03 C    |
| **Lifespan tier**      | The folder level expressing how long an artifact is expected to live: inbox, project, system, note, ref.                                 | §03 C    |
| **Promote**            | Moving a note to a longer-lived tier, rewriting its frontmatter and repairing inbound links atomically.                                  | §03 C    |
| **Index**              | The SQLite database in .serat/. Entirely derived, never synced, and rebuildable from the vault alone.                                    | §05      |
| **Budget**             | A numeric performance limit asserted in CI. A change that breaches one fails the build.                                                  | §03 E    |
| **Gate**               | The exit condition for a delivery phase, stated as an observable outcome rather than a date.                                             | §11      |
| **Benchmark vault**    | A generated synthetic vault of 20,000 notes used for every performance measurement.                                                      | §14      |
