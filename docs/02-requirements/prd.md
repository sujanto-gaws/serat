## Problem statement

Past a few thousand notes, a plain-Markdown vault becomes a small, badly-typed database, and the tools for interrogating it (Obsidian Bases, Dataview) are read-only, frontmatter-only or per-render JavaScript bolt-ons. Everything in the vault that is not Markdown — PDFs, decks, spreadsheets, screenshots — is unsearchable, unqueryable and untypeable by construction. Serat must deliver typed schemas over plain Markdown, a declarative type-checked query language with writable views, binaries extracted into the same index as notes, and AI that reads the whole graph with every write reviewed — in one fast local binary that opens an existing Obsidian vault unmodified. See the charter for the full wedge and competitive read.

## Users & personas

All personas are the same single vault owner wearing different hats (assumption A-01: one author per vault). Stories are written from the hat that motivates them:

| Persona | Cares about | Stories |

| Project manager | Lens switching, promotion through lifespan folders, every task in one place, dashboards as files | 5 |
| Daily user | Reach any note instantly, search everything, stay fast as the vault grows | 5 |
| Engineer | Letting Claude Code query the vault properly over MCP, never being edited behind their back | 3 |
| Researcher | Reading, searching inside and quoting PDFs and scans; asking the vault a question with citations | 3 |

| Privacy-minded / pragmatist / new / long-term / busy user | Keeping folders out of AI entirely, working with no API key, trusting the dependencies, first-run experience, history, one-motion capture | 6 |

## Identifier scheme

`FR-AREA-nn` functional, `NFR-AREA-nn` non-functional, `US-nn` stories, `A-nn` assumptions, `C-nn` constraints. Identifiers are permanent: a dropped requirement is marked dropped, never deleted and never reused.

### Priority and verification

| Code    | Meaning                                                                     |
|---------|-----------------------------------------------------------------------------|
| M       | Must — v1 does not ship without it                                          |
| S       | Should — v1 is materially weaker without it; may slip one phase             |
| C       | Could — Included if the phase has room                                      |
| W       | Won't — Explicitly out of scope for v1 — recorded so it is not rediscovered |
| Test    | Automated test in CI                                                        |
| Bench   | Benchmark against the 20k/50k synthetic vault, enforced in CI               |
| Demo    | Manual demonstration against the phase gate                                 |
| Inspect | Code, config or document review                                             |

**NFR-PRF-01 was re-baselined at P0 as a split, not a slackening (ADR-0014, task #104).** The original 400ms/1s targets were carried over from the blueprint with no webview-startup term in them; measured on Windows/WebView2, creating the webview environment and controller (`P_webview`) costs **725ms median and 1199ms at p95** — more than twice the entire original budget, with no Serat code inside it. The whole platform term `P` — loader, `tauri::Builder` and webview creation together — is 1117ms median and 1687ms at p95. The re-baseline partitions cold start into a **platform term** (loader, webview environment and controller creation — unbudgeted, because no change confined to this repository moves it) and a **Serat term** (our main-thread setup plus our front end's mount, first composited frame and settle — the quantity C-06 now binds). 350ms is inside the interval ADR-0014 derives from the measured Serat-term p95 (233.8ms) and the original 400ms ceiling — `[s95×1.3, 400ms]` = `[304, 400]`, non-empty with 96ms of room — chosen with margin above the floor for cross-batch variance the sampled batches cannot bound (F-405), while remaining a real tightening of a number that used to cover the platform term as well.

Four bounds travel with this number and must not be dropped when it is next quoted:

- **One platform.** Attested on Windows/WebView2 only (F-96); WKWebView and WebKitGTK are unmeasured. If their platform terms are of the same order, the *requirement* was wrong rather than the design, and this split is the permanent fix — decided at P1, not here.
- **Warm vault.** Every cold-start figure taken to date is a warm-vault figure; a cold vault could not be produced on the measuring machine (F-154). This is a stated best case, not a floor.
- **Scanner disabled** (`gate_eligible: false`, RISK-012). Both this bound and the warm-vault one push the figure the same way — toward a more flattering number than a first real open will show.
- **The aggregate totals are reported, not gated.** The pre-split totals move roughly 19% batch-to-batch at zero build contention, against roughly 8% for the Serat term itself (F-405, F-407); a scalar that moves 19% between attested batches cannot decide a pass at any budget set on it. Window-visible ≤400ms and vault-usable ≤1s therefore stay as the user-facing description of total wait, not as CI gates — only the Serat term is asserted in CI.

The paint mark this budget depends on was unguarded when the figures above were taken (F-397), and the frame/paint conjunction ADR-0014 specifies was enforced nowhere in the tree that produced them (F-403). Neither defect changes the number; both bound how much weight it can currently bear.

**v1.2 said those bounds lift when task #113 and its siblings close. #112, #113, #114 and #115 have all merged, and neither bound lifts — for two different reasons, recorded here rather than left as a date nobody was watching (F-471).** The call-site guard is real now: #113 pins that `mark_first_paint` is reached with the value the front end measured, which is exactly what F-397 found missing. **But it landed after #100's figures were taken, so those figures are still unguarded figures** — a fix cannot reach backwards into a measurement, and only a re-measurement under the enforced guard retires this bound. None has been taken. The conjunction, meanwhile, was not enforced but **demoted**: `validate_paint_evidence` (`crates/serat-app/src/startup.rs:909`) rejects a non-finite or non-positive paint value and requires the two frame timestamps to be finite and strictly increasing, but compares the frames *to the paint entry* only in a non-rejecting diagnostic, because the check as ADR-0014 specified it could never fire on this platform (F-406). A plausible-positive paint value is therefore accepted as asserted contract, and the guard's soundness rests again on `index.html` carrying no content of its own — which nothing asserts (F-482). **Neither restatement moves the 350ms budget.** Both say what the number may currently be quoted for, which is the whole purpose of a bound.

**NFR-PRF-03 was measured at P0 and the 50ms target stands unchanged (task #95, `docs/05-testing/reports/nfr-prf-03-save-to-index.md`).** The fourth attempt was the first to produce a number: **p95 4.306ms against the 50ms limit**, n=1,000, `degraded: null`, with the save-path census closing — **1,000 attempted, 1,000 submitted, 0 writer-refused, 0 handle-missing** — so the p95 is computed over the whole workload rather than over whichever fraction of it survived. Replicated immediately at 4.4ms; **the first run is the number of record because it was the pre-registered one, so designating one cannot be read as choosing the better.** It is a **measured number with a named gap, not yet the charter's figure** — and after #122 exactly one bound says why. Bound 4 was the other: *"a number taken with an unmutated instrument is not a gate number here"* was the standing ruling, and #122 satisfied it. **What remains is bound 1, which is about the machine and not the instrument** — the harness still emits `gate_eligible: false`, and no result from #122 can change a fact about real-time scanning.

**It is deliberately not a re-baseline, and nothing asked for one.** 11.6× of headroom is a reason to trust the design, not a reason to move a requirement: this budget exists to catch a regression on the write→parse→index path, and a budget re-set at the best case observed on one machine with the scanner disabled would fail on the first honest run rather than on the first real regression. The figure could not ratify a tighter budget in any case, because the harness itself declines to call it the charter number. NFR-PRF-01 was re-baselined at P0 because its original target was measuring a quantity that included a platform term nobody had budgeted for; **NFR-PRF-03's target measures what it always said it measured, so there is nothing to correct.**

Four bounds travel with this number and must not be dropped when it is next quoted:

- **`gate_eligible: false` — real-time scanning is disabled on the measuring machine (RISK-012).** The harness's own environment gate refuses to call this the charter number — *"a best case no user will see"* — and the measurer explicitly declined to treat the headroom as licence to drop the caveat. **A scanner-enabled re-run is approved as task #123 and is what turns 4.306ms into the charter's figure.** When it lands it replaces the figure in this note and this bound with it; the requirement's text and its 50ms target do not move either way, which is the point of writing the figure here rather than into the budget. **#123 is blocked on a decision that is the repository owner's and not the team's** — real-time protection is a security setting on their machine, and test-engineer declined to change it to make a benchmark eligible, which is the only sound call available: a team that disables a user's antivirus to improve its own number has produced a worse artefact than the caveat it was removing. **Until the owner enables it, `gate_eligible: false` stands and this bound is the honest record**, not a placeholder. No figure is pre-announced here.
- **A warm, already-open vault** — implicit until F-450, load-bearing since, and now in the acceptance criterion rather than only in a report. NFR-PRF-03's words are *a note saved through Serat's own write path*, and a vault whose first index build is still running is not a vault Serat has yet saved into; a harness that raced that build is what produced the 1,000/1,000 that cost three of the four attempts. **The pre-warm makes the requirement's words true rather than slackening them**, and that is the distinction a future reader will most easily lose — which is why it is stated in the criterion and not only here. Note this premise is not the same *kind* as NFR-PRF-01's warm vault: there, warm is a stated best case standing in for a cold one nobody could produce (F-154); here, warm is the case the requirement governs, and the cold-rebuild case belongs to NFR-PRF-04.
- **One machine, one platform.** Windows, 16 cores, `concurrent_build_processes: 0` attested under a declared build freeze — as NFR-PRF-01 is bounded to one webview by F-96. No CI ceiling exists for this budget (`ci_limit_ms: None`), so a CI run today would assert the product limit on a slower runner; that is deliberate, a placeholder ceiling invented at a desk being worse than an honest red. It is a second thing standing between this budget and a CI assertion that means anything, beside F-384's having no CI jobs at all: with jobs restored, the assertion would exist and would be calibrated for a machine other than the one it runs on. Both are NFR-PRF-08's concern — see Open questions.
- **The composed tree was not mutation-attested when the figure was taken (F-429) — discharged by task #122, not falsified.** code-reviewer verified `690b70c` byte-identical to the approved `8460e32` and verified #94 would merge cleanly, but had not mutated the composition `c60dfdd` itself, so F-429 was satisfied on the merges and *inferred* on the composition. **#122 ran the attestation against `c60dfdd` and it PASSED** — control 95/0, ten of eleven mutations red, identical to the approved `d30aa34`. Had it failed, 4.306ms would have been void. **The bound is recorded rather than deleted because it remains true of the figure: this number was taken before its instrument was attested, and a later pass does not change the order those two events happened in.** What it does is retire the risk, which is why this bullet says *discharged* and not *withdrawn*.

## Assumptions and constraints

An assumption is something believed true that was not verified; a constraint is a decision already made that requirements may not reopen. Each assumption records what breaks if it turns out to be wrong, because that is the part people forget to write down.

### Assumptions

| ID   | Assumption                                                                                                                             | If it is wrong                                                                                     |
|------|----------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| A-01 | **Single user, single machine** — There is one author per vault. No concurrent multi-user editing is designed for.                        | If collaboration becomes a requirement, the write-back and history design both change materially.  |
| A-02 | **Vault fits on local disk** — Vaults are local folders, not network shares or object stores.                                             | Network filesystems may break the watcher and atomic-rename assumptions. They also void the index's single-writer lock (`.serat/index.lock`, ADR-0001), which, like SQLite's WAL, is guaranteed only on a local filesystem: on a network share a second Serat writer may not be refused, and where the share does not support the lock the index is unavailable while the vault itself stays editable (NFR-REL-01). |
| A-03 | **Sync is external** — The user runs git, Syncthing or a cloud folder for multi-device sync.                                              | Serat must tolerate files changing underneath it at any moment — hence FR-VLT-04 and FR-VLT-05.    |
| A-04 | **Obsidian remains the reference dialect** — Wikilink, embed and inline-field syntax follow Obsidian and Dataview conventions.            | A divergence in Obsidian's syntax would require a parser update to preserve NFR-CMP-01.            |
| A-05 | **One developer, part-time** — Effort estimates assume solo part-time delivery of roughly 30 weeks to v1.                                 | Any phase gate slipping compounds; scope is cut before gates are weakened.                         |

## Glossary

Canonical vocabulary. Where this document, the blueprint, the code and the UI disagree on a term, this section is what the others are wrong about.

| Term                   | Definition                                                                                                                               | Source   |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------|----------|
| **Vault**              | A folder of Markdown files and assets that Serat opens. The vault is the product's unit of scope; there is exactly one per window.       | §04      |
| **Note**               | A single Markdown file in the vault. Also the row representing it in the index.                                                          | §05      |
| **Block**              | A parsed structural unit within a note — paragraph, heading, task, list item, code fence, table. The granularity at which Serat indexes. | §05      |
| **Field**              | A typed key/value pair attached to a note, from YAML frontmatter or from a key:: value occurrence in the body.                           | §05      |
| **Frontmatter**        | The YAML block at the top of a note. One of the two sources of fields.                                                                   | §05      |
| **Inline field**       | A key:: value pair written in the note body. Indexed identically to frontmatter, unlike in Obsidian Bases.                               | §03 B    |
| **Wikilink**           | A link written \[\[target\]\], optionally with \#heading, ^block or \|alias.                                                             | §03 A    |
| **Block reference**    | A ^identifier anchor that makes a specific block linkable from elsewhere.                                                                | §05      |
| **Type**               | A declared shape for a note: named fields with kinds, required-ness, enumerations, defaults and order.                                   | §03 B    |
| **Type note**          | The Markdown note that declares a type. Types are content, not configuration.                                                            | §03 B    |
| **Schema registry**    | The in-memory, hot-reloaded set of all types, used to typecheck queries and validate notes.                                              | §04      |
| **SQ**                 | Serat Query — the declarative query language. Compiles to exactly one SQL statement; contains no host-language escape.                   | §06      |
| **Query block**        | A fenced sq code block inside a note whose results render in place.                                                                      | §03 B    |
| **View**               | A rendering of a query's row set: table, board, calendar, gallery or list. The row set is identical across kinds.                        | §03 B    |
| **Rollup**             | An aggregate computed over notes one link hop from a result row.                                                                         | §06      |
| **Write-back**         | Editing a source note by changing a value in a view. Implemented as a byte-range patch, never a document rewrite.                        | §07      |
| **Field-scoped patch** | A write that replaces only the recorded byte range of one field or task marker.                                                          | §07      |
| **Stale guard**        | The check that refuses a view-originated write when the file's hash changed since the row was read.                                      | §07      |
| **Locator**            | The position of an extracted block inside a binary: page, slide, cell range or timestamp. The binary's equivalent of a byte range.       | §05, §08 |
| **Asset**              | A non-Markdown file in the vault, represented in the index by a row of its own.                                                          | §08      |
| **Sidecar note**       | The companion Markdown file that carries an asset's frontmatter, type, tags, links and annotations.                                      | §08      |
| **Extractor**          | A per-format component that converts a binary into block rows. Runs out of process, capped, with no network.                             | §08      |
| **Extraction cache**   | Extraction output stored by content hash and extractor version, surviving index deletion because it is expensive to recompute.           | §08      |
| **Chunk**              | A span of blocks embedded as one vector for semantic retrieval, carrying its heading path as context.                                    | §09      |
| **Hybrid retrieval**   | Fusing lexical (BM25), semantic (vector) and structural (link graph) signals into one ranking.                                           | §09      |
| **Diff queue**         | The review surface where every AI-originated change waits for explicit acceptance. In-app and MCP writes share it.                       | §09      |
| **MCP server**         | The typed external interface onto the same query API the UI uses, so agents see exactly what the app sees.                               | §09      |
| **Lens**               | A role-scoped configuration — filter, dashboard, pinned views — declared as a note and switchable in one keystroke.                      | §03 C    |
| **Lifespan tier**      | The folder level expressing how long an artifact is expected to live: inbox, project, system, note, ref.                                 | §03 C    |
| **Promote**            | Moving a note to a longer-lived tier, rewriting its frontmatter and repairing inbound links atomically.                                  | §03 C    |
| **Index**              | The SQLite database in .serat/. Entirely derived, never synced, and rebuildable from the vault alone.                                    | §05      |
| **Budget**             | A numeric performance limit asserted in CI. A change that breaches one fails the build.                                                  | §03 E    |
| **Gate**               | The exit condition for a delivery phase, stated as an observable outcome rather than a date.                                             | §11      |
| **Benchmark vault**    | A generated synthetic vault of 20,000 notes used for every performance measurement.                                                      | §14      |
