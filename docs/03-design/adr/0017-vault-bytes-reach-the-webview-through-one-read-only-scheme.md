# ADR-0017: Vault bytes reach the webview through one read-only custom scheme

**Status:** proposed — stays proposed until review of task #6 is clean and tauri-app-dev has reviewed it · **Date:** 2026-09-24 · **Serves:** FR-BIN-11, FR-BIN-12, FR-EDT-03 (image embeds), NFR-SEC-06, NFR-SEC-01
**Honours:** ADR-0012 (the IPC ACL; this ADR records what it does not cover), threat model T-07 (one containment rule) and T-10
**Amended:** 2026-11-09 (task #94): pdf.js ≥ 6 configuration, `read_asset_range` as the PDF transport on every platform, the worker port, `useWasm: false`, and cMaps and standard fonts. See §Amendment 1. The text below is corrected in place where it described options pdf.js 6 does not have.
**Amended:** 2026-11-12 (task #115): the app CSP gains `form-action 'none'; base-uri 'none'`, and Amendment 1 item 6's claim that `connect-src 'self'` covers cMaps and standard fonts is corrected. See §Amendment 2.

## Context

P1 ships a PDF viewer (FR-BIN-11), an image viewer (FR-BIN-12) and image embeds in notes (§9.3). All three need the bytes of a vault file inside the webview, and PDFs of a hundred megabytes must load incrementally, because pdf.js asks for byte ranges. Every path that reads a vault file has to enforce T-07's rule that nothing outside the vault root is read. The webview's CSP is `default-src 'self'` with an IPC `connect-src` (`crates/serat-app/tauri.conf.json`), so some change to it is unavoidable. The question is which change.

It is an ADR because it adds a third read path into the vault, beside `read_file` and the walk. It changes the CSP. And it sits outside ADR-0012's ACL, which governs IPC commands only.

## Options considered

1. **Tauri's asset protocol** (`convertFileSrc`, `assetProtocol.scope` widened at runtime to the opened root). Rejected on three grounds:
   - Containment would rest on Tauri's scope matcher, which checks path patterns rather than resolving symlink components. T-07's history records two implementations of one rule disagreeing as the defect.
   - The scope would span the whole directory tree, including `.md` files, `.serat/` and `.obsidian/`, because it does not know the ignore rules.
2. **An IPC command returning bytes** (`tauri::ipc::Response`). It stays inside the ACL, but pdf.js would need a custom range transport, and every image embed would pay a round trip and a blob copy. **Kept as the per-platform fallback** (§Fallback), not as the primary path.
3. **One custom URI scheme, `serat-asset`, handled by serat-app, resolving every request through the vault's containment functions.** Chosen.

## Decision

**`serat-asset://localhost/<percent-encoded vault-relative path>` is the only way vault bytes reach the webview other than `read_file`.** Tauri presents a custom scheme to the page as `serat-asset://localhost/…` on macOS and Linux, and as `http://serat-asset.localhost/…` on Windows. **`use_https_scheme(false)` is pinned on the main `WebviewWindowBuilder`** in `crates/serat-app/src/lib.rs`, not in `tauri.conf.json`: the window is built in code and the config's `"windows"` array is empty, so a config key would pin nothing. The `security_config` test `the_main_window_pins_the_http_custom_protocol_scheme` asserts that the builder call is present and that `use_https_scheme(true)` is not. So the Windows form is exactly `http://`, and the webview-facing URL, the app CSP and the CORS origin all use that form on Windows.

**The handler itself sees one form on every platform.** On Windows, wry rewrites the custom scheme to `http://serat-asset.localhost/…` for the page and reverts that rewrite before calling the handler (wry 0.55.1 `custom_protocol_workaround::revert_uri_work_around`, called from `webview2/mod.rs`; Tauri's own `tauri://` scheme relies on the same revert). So the handler accepts `serat-asset://localhost/…` on every platform and nothing else. The platform matters to the handler only for the CORS origin of step 8.

The handler, in serat-app, applies these steps **in this order**:

1. **Allows `GET` and `HEAD` only.** Everything else gets 405. The one exception is `OPTIONS`, answered as in step 8, so that preflight is covered whatever a webview decides to send. The scheme cannot write.
2. **Refuses any host but `localhost`** with a 404.
3. **Decodes the path exactly once, and that is the only rule.** A decoded path containing NUL or invalid UTF-8 gets a 404. The decoded text is the file name, literally: a `%` left in it is an ordinary character and is never decoded again. So `%252e` names a file literally called `%2e`, and a real file named `a%41.pdf` stays servable, because the front end requests it as `a%2541.pdf`.
4. **Builds a `VaultPath` under task #34's rules, which this ADR relies on and does not restate as its own guard.** **Some of those rules apply on every platform, and some only on Windows.**
   - **On every platform**, `VaultPath::new` rejects `..`, empty paths and absolute paths. A leading `/`, or a first segment that is exactly a drive letter (one ASCII letter and `:`, as in `C:/Users/…`), counts as absolute. A first segment such as `Notes:` is not a drive letter and is an ordinary name outside Windows. `\` is read as a separator.
   - **On Windows only**, #34 adds three rules. It rejects **`:` in any segment**, which closes the drive-relative escape (`C:Users` replaces the whole path in `PathBuf::push`) and NTFS alternate data streams. It rejects **Windows device names** (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `CLOCK$`, `COM0`–`9`, `LPT0`–`9`, in any case, with or without an extension or a trailing space). And it rejects **trailing dots or spaces**, which Windows strips silently.
   - **Elsewhere, those three are ordinary file names, and refusing them would be a defect.** On Linux and macOS, `C:Users.png`, `CON.pdf` and `aux.png` are legitimate files that a user can have in a vault, with none of the Windows hazards. They pass step 4 and are judged by steps 5–7 like any other name. This is `serat_core::path::Platform`. The rules are a function of an explicit platform value, so both directions are testable from any runner (#34's own regression: universal rules made `aux.md` and `Meeting 10:30.md` vanish from Linux vaults).

   The check that existed before #34 is not relied on. **Until #34 lands, this scheme must not ship.**
5. **Refuses anything but a viewable asset**, using the one extension→MIME table in `serat-core`. `application/pdf` and `image/png|jpeg|gif|webp|avif|bmp|svg+xml` pass. Everything else gets 404, including Markdown and any path under an ignored directory. The ignored-directory check folds case, which is #34's fourth rule.
6. **Resolves through `Vault::resolve`**, which refuses a symlink component anywhere in the path (T-07). Then, per #34, it **asserts that the result `starts_with` the canonical root**. A refusal gets 404 with no detail.
7. **Opens, then re-verifies the open handle, which closes the gap between resolving a path and opening it (TOCTOU).** Between step 6 and `open`, a component could be swapped for a symlink. After `open`, the handle's real path is read back through the **`filepath` crate** (`FilePath::path`; the workspace forbids `unsafe_code`), which asks the platform: `GetFinalPathNameByHandleW` on Windows, `fcntl(F_GETPATH)` on macOS, `/proc/self/fd/N` on Linux. On Windows the result carries the `\\?\` verbatim prefix, so both the real path and the root have it stripped (`\\?\UNC\` becomes `\\`), and only then is the real path required to lie under the canonical root. **The ignored-directory check of step 5 is then re-run on the real path relative to the root**, case-folded as before: a component swapped between steps 6 and `open` could otherwise land the handle inside `.serat/` or another ignored directory while still under the root (S1 of task #19's review). **The handle's metadata must also say `is_file()`**: a FIFO or device would otherwise block the read forever. Any failure closes the handle and returns 404. This is recorded in T-10.
8. **CORS.** The scheme is a different origin from the app, so pdf.js's range `fetch` is cross-origin. Every response carries:
   - `Access-Control-Allow-Origin` set to **the exact app origin** of the platform (`tauri://localhost`, or `http://tauri.localhost` on Windows), never `*`;
   - `Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length`.
   `OPTIONS` from the app origin is answered 204 with `Access-Control-Allow-Methods: GET, HEAD` and `Access-Control-Allow-Headers: Range, If-Range`, and is refused from any other origin. Because this is answered, the design does not depend on whether each webview sends a preflight for a `Range` header.
9. **Serves bounded spans, and nothing streams.** Tauri's `UriSchemeResponder` takes a whole body, so every response is one bounded buffer:
   - **Each span is capped at 1,000 KiB** (Tauri's own figure). A single `Range: bytes=a-b` gets 206 with at most that many bytes from `a`. An `a-b` wider than the cap is truncated to the cap and says so in `Content-Range`, which is valid HTTP; the client asks for the rest.
   - **A request with no `Range` depends on the type.** An `<img>` never sends `Range`, so an image cannot be split into spans. An image is **served whole, as 200, up to 64 MiB**; above that it gets **404**, and the viewer shows "couldn't be displayed". **Only `application/pdf`** answers a no-`Range` request over the cap with **206 and the first span**, plus `Content-Range: bytes 0-…/<size>` and `Accept-Ranges: bytes`. pdf.js is the only consumer that reads spans, so no PDF request ever loads a large file whole. (The first draft of this fix applied the first-span 206 to every type, which would have truncated every photo over 1,000 KiB; review caught it.)
   - **pdf.js does not read PDFs through this step (corrected, Amendment 1).** It was to be given `length` and the scheme URL. pdf.js ≥ 6 has no `length` option on `getDocument`, and its stock network stream never sends `Range` on a non-http scheme, then rejects this step's 206-for-no-`Range` answer. **PDFs reach pdf.js through `read_asset_range` on every platform** (§Fallback, now the PDF transport everywhere), with `rangeChunkSize` set to the cap, `disableStream: true` and `disableAutoFetch: true`, so it still fetches only the spans of the pages being shown. The scheme keeps serving PDF spans exactly as above, because the handler and its hostile suite are unchanged and a future pdf.js or another consumer may use them; P1's viewer does not.
   - Malformed ranges (a start beyond the end, an inverted range, a multi-range) get 416. A suffix range (`-n`) is served within the cap.
   - **`If-Range` is honoured by the scheme.** A range request carrying the `ETag` of an earlier response in `If-Range` is answered 200 with the first span when the file has changed, and `If-Range` is in `Access-Control-Allow-Headers`. **For PDFs the same check now lives in the transport (Amendment 1):** `read_asset_range` takes the validator the load started with and refuses a span when the file's current validator differs, so a PDF still restarts rather than mixing versions.
10. **Headers on every response:**
   - `Content-Type` from the table.
   - `X-Content-Type-Options: nosniff`.
   - `Content-Security-Policy: default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; sandbox`.
   - `Cache-Control: no-store`.
   - An `ETag` built from size and mtime (one stat). Combined with `If-Range`, a file changed during a load restarts cleanly instead of mixing versions. A false "changed" costs one reload.

**The app CSP changes by exactly two sources and two explicit pins** (four pins since Amendment 2). It adds `img-src 'self' serat-asset: http://serat-asset.localhost`, and the same two origins in `connect-src`. It pins **`frame-src 'none'; object-src 'none'`** explicitly (control (c) below), and, since Amendment 2, **`form-action 'none'; base-uri 'none'`**. It adds no remote origin, no `data:` (§9.3 drops `data:` URLs), no `blob:` and no `'unsafe-*'`.

**pdf.js is pinned at ≥ 4.2.67**, the release that fixes CVE-2024-4367 (arbitrary JavaScript through a crafted font); P1 bundles **pdfjs-dist 6.5.438** exactly (task #26), and a version change is a reviewed dependency change. **Corrected (Amendment 1):** this paragraph said pdf.js also runs with `isEvalSupported: false`. pdf.js ≥ 6 has no such option and no `eval` or `new Function` path in `pdf.mjs` or its worker. **The independent control is the app CSP, which has no `'unsafe-eval'`**, so the CVE's path cannot execute even in a build that regressed it. Passing a non-existent option is not a control, and the viewer must not pass it, because a reviewer would read it as one.

**pdf.js is bundled and inert.** Its worker, cMaps and standard fonts are served from `'self'` (Amendment 1 says how, and what P1 must ship). It runs with **`enableScripting: false`** and `useWasm: false`, under a CSP with no `'unsafe-eval'` and no `'wasm-unsafe-eval'`, so a PDF's JavaScript never runs. A link inside a PDF opens only on an explicit click, and only through the system opener (the same rule as §9.3's external links). **SVG is shown only through `<img>`**: never inline in the DOM and never as a navigated document, and the per-response `sandbox` CSP backs that up.

**What stops a `serat-asset` document from reaching IPC — corrected.** ADR-0012's command ACL gates `invoke`, and a scheme handler is reached by URL loads, so the ACL does not cover it. **There is no origin-classification control.** An earlier version of this paragraph said Tauri classifies `serat-asset` content as a remote origin (`is_local_url` false), so a document loaded from it could invoke no IPC command. **That is false.** tauri-app-dev checked the tauri-2.11.5 source:

- `webview/mod.rs:1698-1739` counts every scheme registered through `register_asynchronous_uri_scheme_protocol` as local.
- `Origin::Local` matches the local capability unconditionally (`tauri-utils` `acl/authority.rs:57-66`).

So a `serat-asset` document that became the main webview's top-level document, **or a frame inside it**, **could invoke every command granted to `main`**. Three controls actually hold, and all three must stay in place:

- **(a) Top-level navigation — the main frame only.** serat-app's `on_navigation` refuses every URL that is not the app's own origin (architecture §9.3), including `serat-asset://…` and `http://serat-asset.localhost/…`. **It sees top-level navigations only.** wry-0.55.1 on WebView2 hooks `NavigationStarting`, which is main-frame only, and does not hook `FrameNavigationStarting`. So an `<iframe src="serat-asset://…">` never reaches `on_navigation`, and a framed scheme document is still `Local`. (a) keeps the scheme from becoming the top-level document; it does not keep it out of a frame.
- **(b) No script runs in a scheme document.** Every response carries `Content-Security-Policy: default-src 'none'; …; sandbox` with **no `allow-scripts`** (step 10), so even a document that did load from the scheme, framed or top-level, executes nothing. That also covers an SVG with script, and anything a PDF carries. **Whether an engine honours a `sandbox` CSP on a custom-scheme response is engine-specific**, so (b) is proven on all three engines, never assumed from one.
- **(c) No frames or plugin objects in the app document.** The app CSP pins **`frame-src 'none'; object-src 'none'`** explicitly. Until now that behaviour came, unnamed, from the `default-src 'self'` fallback, so any edit to the CSP could have removed it without a test noticing. The explicit pin is a change to `crates/serat-app/tauri.conf.json`, for task #37 or #19 to implement with its test. **The sanitiser is the markup layer of the same control**: it strips `iframe`, `object` and `embed` from rendered notes (§9.3), so a note cannot even ask for a frame.

The read-only, viewable-types-only, contained-paths handler (steps 1–10) limits what the scheme can *serve*. It does not limit what a loaded document could *invoke*, so it is not a control against IPC.

**Downloads are refused.** `<a download href="serat-asset://…">` would make the webview write a vault file somewhere outside the vault, which is a write path T-06 does not list. serat-app refuses every download: WebView2 `DownloadStarting` is cancelled, and WebKit's `download-started` is cancelled on WKWebView and WebKitGTK. The sanitiser also strips the `download` attribute, as a second layer. Recorded in T-06 and T-10.

**The default context menu is disabled in release builds** (it offers "Save image as…", "Open frame in new window" and "Inspect"). Debug builds keep it for development. **Today (task #37) it is disabled on Linux only.** Windows and macOS wait for task #39, which needs platform access, and until then the menu is a known gap on those two platforms, recorded in T-10.

**Sidecar pairing matches bytes exactly, deliberately.** `X.PDF` and `x.pdf.md` are not a pair: ADR-0005 defines the sidecar name as the binary's full file name with `.md` appended, and on a case-sensitive filesystem the two could name different files. Folding case here would let one sidecar claim two binaries. A user who wants the pairing renames one of the two, and nothing is guessed.

### Fallback, if a webview will not deliver a custom-scheme 206 — now the PDF transport on every platform

**Amended (task #94):** for PDFs this is no longer a fallback. pdf.js ≥ 6 cannot read the scheme's spans (Amendment 1), so `read_asset_range` and the custom `PDFDataRangeTransport` below are **the PDF transport on every platform**, whether or not a webview delivers a custom-scheme 206. The command is already granted to `main` on every platform (ADR-0012, `capabilities/default.json`), so nothing widens. What remains a per-platform fallback is the image half: images use the scheme through `<img>` wherever it works, and `blob:` stays confined to a platform where it does not.

If WebKitGTK or WKWebView does not deliver a custom-scheme 206 with these headers (the open question below), that platform uses **option 2 in span form**. A `read_asset_range(path, start, len) -> bytes` IPC command applies steps 2–7 and the span cap of step 9 unchanged, granted to the main window in the capability file (ADR-0012). The viewer supplies pdf.js with a custom `PDFDataRangeTransport` that calls it. **Loading therefore stays incremental and per page on every platform**, and the viewer's loading state can be the same everywhere: a real progress indicator driven by fetched spans against `assets.bytes`, not a skeleton waiting for the whole file. Images on that platform use the same command and a `blob:` URL. **Only** on that platform, `img-src` gains `blob:`, and that addition is recorded in T-10 when it is made.

### Amendment 1 (task #94): pdf.js 6.5.438, as bundled by task #26

Serves FR-BIN-11, NFR-SEC-06, NFR-SEC-01; threat model T-07, T-10. Review of #26 found that this ADR named options pdf.js ≥ 6 does not have. Each ruling below replaces the text it names, which is corrected in place above.

1. **No `isEvalSupported`.** The option does not exist, and pdf.js 6 has no eval path. The control is the app CSP's lack of `'unsafe-eval'`. The viewer does not pass the option. The hostile case "a PDF with JavaScript" stays in §Tested against, and a CSP test that asserts no `'unsafe-eval'` replaces any test of the option.
2. **No `length` on `getDocument`; `read_asset_range` is the PDF transport everywhere.** The length travels in a custom `PDFDataRangeTransport(length, null)`, built from `asset_info`'s `bytes`, whose `requestDataRange(begin, end)` calls `read_asset_range` and answers with `onDataRange`. The stock stream is not used on any platform, because it never sends `Range` on a non-http scheme and rejects step 9's 206-for-no-`Range` answer. `rangeChunkSize` is the 1,000 KiB cap, and `disableStream` and `disableAutoFetch` stay `true`. The loading indicator is driven by spans fetched against `bytes` on every platform.
3. **`If-Range` becomes a validator check in the transport.** `asset_info` returns the asset's validator, `AssetInfo::etag`, in the same form as step 10's `ETag` (size and mtime, one stat of the opened handle). The transport passes it as `ReadAssetRangeArgs::if_match` on every span. serat-app compares it with the opened handle's current validator. On a mismatch it serves nothing and answers **`IpcError::AssetChanged { path, validator }`**, a dedicated variant. It does not reuse `StaleHash`, whose `current_hash` is a BLAKE3 content hash that note code adopts as a base; generic `stale_hash` handlers must never receive an opaque size-mtime string as if it were one. The transport then destroys the loading task, calls `asset_info` again and reloads with the new length. The viewer shows binary-viewers.md's non-blocking notice, "This file changed on disk — showing the latest version", for 4 s. A false "changed" costs one reload, as with the scheme. **The validator's limits are the scheme `ETag`'s limits, because it is the same value.** It misses two kinds of change. The first is a same-size rewrite within the filesystem's mtime granularity: FAT/exFAT (2 s, or 10 ms for exFAT's fine field) or HFS+ (1 s). **The granularity is also a property of the kernel, not only of the filesystem (#98 and #108 reviews).** On Linux before 6.13, ext4, XFS and Btrfs stamp mtime from the coarse clock, one jiffy (about 1–10 ms). So a same-size rewrite within one tick of `asset_info`'s stat is missed on any filesystem. From 6.13, multigrain timestamps close that window. Measured on a 6.18 kernel: 0 misses in 2,000 same-size rewrites on ext4. The FAT/exFAT and HFS+ figures above are unaffected, because they are the filesystem's own resolution. The second is a writer that preserves mtime, such as `cp -p` or `rsync -a`. Either can mix bytes from two versions within one load. pdf.js then shows a damaged page or a parse error, never a file outside the vault, so the failure is display only (goal 5). Adding the file's inode or file ID to the validator would strengthen the scheme and the transport at once, and, on a filesystem with stable file identities (ext4, XFS, Btrfs, APFS, HFS+, NTFS), it closes every case in this paragraph when the writer replaces the file by rename (atomic-save editors, `rsync -a` without `--inplace`): the coarse-clock tick, HFS+'s resolution and mtime preservation alike. A writer that unlinks and then creates (a git checkout) is covered only when the filesystem does not reuse the freed inode number. FAT and exFAT have no persistent file identity (Linux synthesises it per mount; Windows derives it from the directory entry's position), so there it adds nothing reliable. It does not close an in-place rewrite, which keeps the inode: `cp -p` over an existing file, or a same-size write within one tick. Only a content hash would close that, and it is not proposed. **`asset_info` returns `etag` only for a viewable asset** (#98). For any other asset it is `None`, because no transport reads it. It is not required for P1 and is recorded here for whoever next touches `asset.rs`'s `etag`. Both fields are optional on the wire and are implemented by #98 (`asset.rs`: `info` fills `etag` for viewable assets; `read_range` answers `AssetChanged` before serving, and again if the file changed during the read). A transport that omits `if_match` cannot detect a change.
4. **The worker is attached through `GlobalWorkerOptions.workerPort`**, as `new Worker(new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url), { type: "module" })`. It is not set as `workerSrc`. pdf.js treats a worker URL it judges cross-origin as needing a `blob:` wrapper. On `tauri://localhost` it judges the Vite-emitted URL that way, and the app CSP's `script-src 'self'` blocks the `blob:` worker, so pdf.js silently falls back to a main-thread "fake worker". That keeps working, but parsing and rendering then run on the main thread, against goal 2. A worker the app constructs itself from a same-origin URL never takes that path. The #26 follow-up asserts that the worker is a real `Worker` and that no fake worker was created.
5. **`useWasm: false`.** pdf.js 6 can decode some image formats with WebAssembly. Compiling WebAssembly needs `'wasm-unsafe-eval'` in the CSP, and this ADR adds no `'unsafe-*'` source. With `useWasm: false`, pdf.js uses its JavaScript decoders where it has them. **JPEG 2000 (JPX) images are not decoded in P1** and render blank. This is a known gap, recorded in binary-viewers.md's states. It is a rendering gap, not a security one, so T-10 does not carry it.
6. **cMaps and standard fonts must ship under `'self'` in #26, not later.** Without them, a PDF that uses a CJK CMap renders its text as boxes or not at all. A PDF that relies on a non-embedded standard font renders with a substitute that gets widths and glyphs wrong. The FR-BIN-11 promise "a PDF is readable in Serat" fails silently on exactly the documents a user cannot fix. The cost is a few megabytes in the installer and nothing at startup, because the files are fetched only by a PDF that names them. So the build copies `pdfjs-dist/cmaps/` and `pdfjs-dist/standard_fonts/` into the bundle. `getDocument` is given `cMapUrl`, `cMapPacked: true` and `standardFontDataUrl`, all same-origin relative URLs. **Corrected (Amendment 2):** this item said "`connect-src 'self'` covers them and the CSP is unchanged". The CSP's `connect-src` has no `'self'` (it is `ipc: http://ipc.localhost serat-asset: http://serat-asset.localhost`, task P0 #117/F-423), and an explicit `connect-src` replaces `default-src` for `fetch` and XHR, so today's CSP would **block** them. Closing this gap therefore changes the CSP by exactly one source: `connect-src` gains `'self'` (Amendment 2 gives the string). They are not served through the scheme and do not need its origin. This is a merge condition on #26. If #26 merges without them, the gap is recorded in binary-viewers.md, with the follow-up task that closes it, before the merge.
7. **The CSP is unchanged by pdf.js 6.** No `'unsafe-eval'`, no `'wasm-unsafe-eval'` and no `blob:` in `script-src` or `worker-src`. The scheme origins in `connect-src` are no longer used by pdf.js. Removing them would narrow the CSP, and that is left to tauri-app-dev with the CSP test. It is not required. **Amended (Amendment 2, task #115):** the CSP has since gained `form-action 'none'; base-uri 'none'`, two pins that narrow it, and item 6's cMaps will add `'self'` to `connect-src` when they ship.

**Why this is an amendment and not a new ADR.** The decision is unchanged: one read-only path for vault bytes, the same containment steps and the same CSP. What changed is which of the two existing paths, both decided here, carries PDFs, and which library options implement the controls this ADR already required. Reversing it costs one transport file in `app/`.

**The cost this accepts, and who still has to review it.** §Options rejected option 2 for its per-span IPC cost, and making it the PDF transport everywhere accepts that cost. A span is at most 1,000 KiB of raw bytes through `tauri::ipc::Response`, with no JSON. pdf.js asks for the visible pages' spans only. So the cost is per page shown, not per keystroke, and it is off the editor's path. #26's follow-up reports time-to-first-page for a 100 MB PDF beside FR-BIN-11. **Not yet reviewed:** vue-frontend-dev (#26, the transport). The validator check is implemented and reviewed in #98. Their objections are recorded here when they are given. This amendment was written from #26's code review, not from an exchange with them.

### Amendment 2 (task #115): two more pins, and what item 6 will cost the CSP

Serves NFR-SEC-01, NFR-SEC-06; threat model T-07, T-09. Raised by the code review of #20 (the no-network evidence, `docs/05-testing/no-network-evidence.md`, which recorded both points as the architect's).

1. **The app CSP gains `form-action 'none'; base-uri 'none'`.** Neither directive falls back to `default-src`, so until now the CSP said nothing about either. **`form-action`:** a form in the app document could submit to any origin. `on_navigation` (T-09) refuses a top-level form submission today, so this is defence in depth, but that guard sees the main frame only, and `form-action` does not depend on it. **`base-uri`:** an injected `<base href>` would re-point every relative URL the app resolves, which after item 6 includes `cMapUrl` and `standardFontDataUrl`, and today includes the pdf.js worker URL. The sanitiser already strips `<form>` and `<base>` (T-09); this is the CSP layer behind it. **Cost: none found.** The one form in `app/` (`FileTree.vue`'s create prompt) cancels its `submit` event with `.prevent`, and a cancelled submission never reaches the `form-action` check. The app emits no `<base>` element; Vite's `base: "./"` is a build setting, not a tag. The CSP is now:

   `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' serat-asset: http://serat-asset.localhost; connect-src ipc: http://ipc.localhost serat-asset: http://serat-asset.localhost; frame-src 'none'; object-src 'none'; form-action 'none'; base-uri 'none'`

   `crates/serat-app/tauri.conf.json` and the pinned string in `crates/serat-app/src/security_config.rs` changed together. `no_csp_directive_admits_a_remote_origin_and_the_whole_string_is_pinned` still proves they match byte for byte, now admits `form-action` and `base-uri` only as `'none'`, and two per-directive asserts name why each exists.
2. **Item 6 is corrected; the CSP change it implies is deferred to the change that ships the files.** cMaps and standard fonts are bundled files fetched by pdf.js as same-origin relative URLs (`fetch` on `http://tauri.localhost`, XHR on `tauri://localhost`). Both are governed by `connect-src`, which has no `'self'`. **When the gap closes (the #26 follow-up; item 6 requires it recorded in `binary-viewers.md`, which has not been done), `connect-src` becomes `connect-src 'self' ipc: http://ipc.localhost serat-asset: http://serat-asset.localhost`**, and nothing else changes. That PR changes, in the same commit: `tauri.conf.json`; the pinned `EXPECTED` string and the per-directive `connect-src` assert in `security_config.rs`; item 4 of `no-network-evidence.md`; and T-02's note that the `connect-src` directive now carries the enforcement. The loop in the pin test already accepts `'self'` in any fetch directive, so the byte-for-byte string is what goes red, which is the intended review trigger ("re-run the no-network review"). Adding `'self'` is not adding an origin a note can reach: `default-src 'self'` already admitted it to every other fetch directive, and T-09's rule that no remote origin is reachable is unchanged. **Rejected: adding it now.** It would widen `connect-src` for files that are not shipped, and an unexplained `'self'` is exactly what the pin exists to catch.

**Not yet reviewed:** tauri-app-dev (owner of the CSP and its test). Their objections are recorded here when they are given. The CSP edit is two directives and a test, and reversing it costs the same.

## Consequences

**Positive.** One containment rule, with #34's hardening, serves the read command, the watcher's paths and now the viewer bytes. Large PDFs load a page's spans at a time on every platform, and no request holds more than 1,000 KiB. The CSP gains one first-party scheme. Scheme content is kept from IPC by the navigation guard and by the script-free sandbox CSP. Tauri still classifies the scheme as local, so both controls are load-bearing.

**Negative.** **An image is held whole in memory while it is served**, because `<img>` cannot request spans. That costs up to 64 MiB per image request in the handler, plus the webview's decoded copy. The limit is what bounds it. A photo library with larger files degrades to "couldn't be displayed" (goal 5), never to a truncated image. It is a hand-written HTTP-ish handler, with range parsing, CORS and ten ordered steps to get right, and three platform-specific handle checks. The table of viewable types is a second allowlist beside the index's MIME table, which is why both come from the same function.

**Risks.**
- Range parsing (boundaries, overflow, suffix and multi-range) is the classic bug source.
- The TOCTOU re-check depends on three platform APIs, each needing its own test.
- The whole design depends on #34 landing first. #34's task description already carries all four rules plus `starts_with(root)`.
All of these are cases in task #19's hostile suite.
