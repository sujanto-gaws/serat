# ADR-0020: The save path parses before the command returns, and announces the index change after the commit

**Status:** proposed (task #173; for code-reviewer) · **Date:** 2026-11-24 · **Serves:** NFR-PRF-03, NFR-PRF-02 (evidence only), FR-VLT-04, US-01
**Honours:** ADR-0008 and C-04 (no byte is written differently), ADR-0001 (the writer stays a writer of rows, never a parser), ADR-0011 (the save path keeps `submit`, never `submit_blocking`), ADR-0015 §2 (a hash is paired with an mtime from the same read), ADR-0016 §2 (one save per note in flight; the 1 s debounce), ADR-0019 (#172's figures are supporting evidence, not gate numbers)
**Source:** task #172's finding (`docs/05-testing/reports/save-patch-bridge-release-2026-11.md`, *Unresolved* item 2), and the correction in `docs/05-testing/reports/nfr-prf-02-quiet-rerun-2026-11.md` headed *Correction (task #172)*.

## Context

Task #172 timed the release-profile IPC bridge's `save_patch` on a 5,000-line note at **48.8 / 68.8 / 82.0 ms p50 / p95 / max** (quiet Linux container, n = 60). **87.5% of it (42.7 ms p50) is `AppState::submit_to_index`** (`crates/serat-app/src/state.rs`), which calls `IndexHandle::apply` and therefore `serat_index::apply` (`crates/serat-index/src/incremental.rs`): `source.load` (stat, read and hash of the note from disk), then `build_op` (the whole-note parse), then `writer.submit`, then `record_echo`. All of it runs on the thread that runs the command. A standalone parse of that note is about 31 ms; about 11 ms is unattributed. `Vault::write_patch` itself is 4.6 ms. On the hub note that NFR-PRF-03 gates, `p1-save-tail` measured the same read at 0.07 ms and the parse at 0.18 ms p95 (`docs/05-testing/p1-save-tail-2026-11.md`).

The question put by task #173: should the read, hash and parse move off the command thread, to the index writer or a worker, so that the command returns after the durable write and a cheap hand-off?

### What the code says, checked rather than assumed

1. **Nothing the command returns depends on the parse.** `FileWritten`'s hash, mtime and size come from `Vault::write_patch` (the mtime from the temp file's handle before the rename, task #71). The editor's base advance (`Editor::save_patch`, `crates/serat-app/src/editor.rs`) hashes the in-memory patched text and compares it with the written hash. Both happen **before** `submit_to_index` runs, which only counts its outcome (`save_submitted`, `save_writer_refused`, `save_handle_missing`) and calls the change notifier.
2. **`serat_index::apply` re-reads the file; it does not take the bytes.** The re-read is the third read of the note in one save (write_patch reads the base and re-reads the target before the rename). The hash the editor advances on is computed from the written bytes; the hash recorded for echo suppression, and written to `notes.hash`, is computed from the re-read. They are equal unless another process wrote in between, and §3.1.1 already explains why the re-read's hash is the right one to record.
3. **ADR-0015 §2's pairing is untouched by where the parse runs.** `FileWritten` pairs the write's own hash and mtime (#71). The index row pairs the re-read's hash with the mtime `Vault::read` stats from the same open handle before reading. Neither pairing involves the parse, and neither would change if the parse ran elsewhere.
4. **The command already runs off the webview's main thread.** `save_patch` is an `async` command that calls `save_patch_off_thread` (`crates/serat-app/src/offload.rs`), which runs `AppState::save_patch` on the runtime's blocking pool. The keystroke never waits for it (ADR-0016 §2).
5. **The open-vault lock is held shared across the write and the submit**, so `close_vault` (exclusive) cannot set the clean-close marker between a write that reached disk and its submit (`AppState::write_file`'s comment, architecture §3.1.1 item 6). **The index-handle slot's mutex is held across the read and the parse** (F-382, accepted at P0). The seam F-382 named as its fix now exists: `IndexHandle::writer()` and `serat_index::apply(&dyn IndexWriter, ...)` are public, but `submit_to_index` does not use them yet, and its doc comment still says they are unreachable.
6. **`index://changed` for a save is announced at the submit, before the commit.** `submit_to_index` calls `notifier().changed()` as soon as `apply` returns `Ok`, and `ChangeSignal` emits on the leading edge (`crates/serat-index/src/external.rs`). The writer commits afterwards. The watcher path is not affected: `Reconciler` flushes before it reports, so `ChangeNotifier::settle` (`crates/serat-app/src/consumer.rs`) announces after the commit. The save's own watcher event is then suppressed as an echo, so no trailing announcement follows. A pane that re-reads on the event (`app/src/panes/BacklinksPane.vue`, `app/src/panes/SearchPanel.vue`) can read the pre-save snapshot and receive no later correction. Architecture §3.1.1 step 5 and §2.2 (*"a caller there reads the pre-write snapshot and is corrected by `index.changed`"*) assume the opposite order. This was found while answering #173 and is ruled here because it is the ordering guarantee #173 asks about.

## Options considered

1. **Keep the read, hash and parse on the command thread (status quo), narrow the slot lock, and move the announcement to after the commit.** Chosen.
2. **Parse on the index writer.** The save path would submit a path, and the writer would load and parse it. Rejected. It puts a CPU-bound 31 ms (5,000 lines) in the one queue every other index write waits in, including FR-VLT-04's watcher batches and the catch-up. It gives the writer a parser and a `NoteSource`, which ADR-0001's writer of rows does not have and the rebuild deliberately keeps on the producer side (§2.2). It also makes a submit a request whose outcome (a refused parse is a bare row, a missing file is a `Remove`) is decided on the writer's thread.
3. **A dedicated save-indexing worker (one FIFO thread per open vault) that does the load, parse, submit and echo record. The command returns after the enqueue.** Rejected for P1. It is the only option that shortens the command, and what it buys is small while what it costs is a new obligation for each guarantee this path now meets by construction:
   - **Close.** The last save is submitted before the clean-close marker because the open-vault lock spans write and submit. With a worker, `close_vault` must drain the worker before `IndexHandle::close()`, which is a new barrier on the close path and a new test.
   - **Ordering against the watcher.** The save's load and the consumer's load of a later external write race today only if the save's parse outlasts the 150 ms coalescing window (possible in a debug build at 324 ms, not in release at 43 ms). A worker adds its queue wait to that interval, so a stale save-path op can land after a newer watcher op, and the index keeps the older bytes with nothing scheduled to correct them until the path is touched again (C-02, FR-VLT-04). Closing that needs per-path sequencing between two threads that today share nothing.
   - **The census.** `save_submitted == saves attempted` (§3.1.1, F-382) becomes an asynchronous count that a harness must wait on.
   - **Design goal 3 outranks goal 4 and 5, and goal 2 is not engaged.** Moving the parse moves CPU work in time by a few milliseconds and does not remove it, so it does nothing for the keystroke (NFR-PRF-02) that the off-thread command does not already do. It does nothing for NFR-PRF-03 either: the index-visible interval includes the parse whichever thread runs it (below).
4. **Pass the written bytes into `apply` instead of re-reading.** Rejected again, as §3.1.1 rejected it: it saves the read and hash (0.2 ms of the 42.7 ms) and costs the single entry point, the `Remove` that falls out of a failed load, and the on-disk echo hash.
5. **Report the command's phases over IPC so the editor can show "indexing".** Rejected. The command does not wait for indexing; it waits for a parse and a queue send. "Saved" is the command's reply and "indexed" is `index://changed` (§3.1.1). A phase report would be a third fact that is neither, and it adds a contract field (ADR-0007) for a 43 ms interval that nothing on the keystroke path observes.

## Decision

1. **The read, hash and parse stay on the command thread, before `save_patch` and `write_file` return.** The command returns after the durable write, the parse and the accepted submit, as now. No contract change; `FileWritten` is unchanged.
2. **The slot mutex is not held across the read and the parse.** `submit_to_index` clones a `WriterHandle` out of the index-handle slot under the lock, drops the lock, and calls `serat_index::apply` with the clone (F-382's named fix, now reachable). The open-vault lock is still held shared for the whole of `save_patch`, so decision 1's close guarantee is unchanged. A save whose clone belongs to a writer that a rebuild or a close has since stopped gets `WriterStopped`, is counted as refused, records no echo, and is indexed from its watcher event (the existing degraded path, design goal 5).
3. **`index://changed` for a save is announced after the commit that contains it, never at the submit.** The writer reports each committed batch to an observer that the opener installs; serat-app's notifier calls `ChangeNotifier::changed()` from that report, and `submit_to_index` no longer calls it. This is not a barrier (§2.2): nothing waits for the report, and the save path still never calls `flush()`. Batches that contain only bulk-side ops keep their existing announcement through `Reconciler`; the observer is not a second announcement for them (one `changed()` per batch is still throttled to ten per second, so a duplicate would cost an event, not correctness, but the implementer should not add one).
4. **Revisit condition for moving the parse.** Option 3 is reopened, with the obligations listed above as its acceptance criteria, if either: (a) something on the keystroke path starts to wait on a save's reply, or (b) a release-profile measurement of the whole `save_patch` command on a note class the PRD gates reaches a p95 of **200 ms**, a fifth of ADR-0016's 1 s debounce, at which point consecutive saves start to queue behind each other's parse. Neither holds today: #172's 68.8 ms p95 is on a note class PRD v1.13 reports and does not gate.

### What each interval means after this ruling

- **The command (#172's quantity)** starts at `AppState::save_patch` and ends after `writer.submit` and `record_echo`: on the 5,000-line note 48.8 / 68.8 ms p50 / p95, of which the parse is about 31 ms; on the hub note, the write plus well under 1 ms of read and parse. Decision 2 does not shorten it; it stops a second save on another note, and the watcher consumer's `reconciler()`, from waiting behind it on the slot mutex.
- **NFR-PRF-03's save-to-index interval** is unchanged: `apply()` entered to the commit, which the harness observes through `flush()` (§3.1.1 *What NFR-PRF-03's benchmark may enter*). It still starts inside the command, at the hand-off, after the write. The `p1-save-tail` phases keep their meaning and order: **read and parse run on the command thread before the command returns; submit is the last thing the command does; wake, the transaction's statements, `COMMIT`, checkpoint and post-commit run on the writer after the command has returned.** #172's phase 17 (`app.submit_to_index`) is `p1-save-tail`'s read + parse + submit, not its whole table.
- **When "index-visible" is reached relative to the command's return: this ruling does not change it.** The commit was after the return before this ruling and is after it now, by the writer's wake, transaction and `COMMIT`. Option 3 would also not have changed when the index becomes visible measured from the hand-off; it would only have moved the return earlier. What decision 3 changes is when the front end is **told**: `index://changed` moves from before the commit to after it, so the announcement no longer precedes index-visibility. PRD v1.13's NFR-PRF-03 criterion, which bounds the index-reflect interval, does not depend on this.
- **The ordering guarantee, stated whole.** For one save: the command's reply (`FileWritten`) and `index://changed` are unordered relative to each other, as Tauri orders neither (ADR-0016 §2), and the front end must not assume either order. `index://changed` carrying a generation that covers the save is emitted only after the save's rows are committed, so a read issued on receiving it sees them. `vault://opened` still precedes every event for its vault (§3.4, task #79; `vault_opened_precedes_every_event_carrying_the_new_id_and_the_old_id_never_follows_it` must stay green).

### What does not change, checked against each dependant

- **Echo suppression (§3.2).** The echo is still recorded after an accepted submit, on the command thread, before the command returns, from the re-read's hash. The save's own watcher event arrives after the 150 ms coalescing window; if it reaches the consumer first, it matches nothing and the note is indexed twice from disk, which is wasteful and correct (§3.1.1). Decision 3 does not touch the echo.
- **FR-VLT-04 reconciliation** of the same write through the watcher, and the hash gate, are unchanged.
- **The catch-up window (task #78).** A save whose commit is lost to a crash after the command returned has an mtime inside `caught_up_from_ms − 2000` and is recovered at the next open, as before.
- **C-04 and ADR-0008.** No byte reaches disk differently. The property and hostile tests of the write path (`crates/serat-vault/src/patch_props.rs`, `crates/serat-vault/src/write_race_tests.rs`: concurrent edit, stale base, crash mid-write) are untouched by decisions 2 and 3 and must stay green.

### Cost on each note class (for task #174; this ruling does not decide which class NFR-PRF-03 binds)

| Note class | Read + parse inside the command | Effect of decision 1 | Effect of decisions 2 and 3 |
|---|---|---|---|
| Hub note of the 20k vault (the gated scenario) | 0.07 ms read, 0.18 ms parse, p95 (`p1-save-tail`) | none measurable | the save's `index://changed` arrives later by the writer's wake, transaction and commit; index-visible unchanged |
| 5,000-line fixture (#147 / #172; reported, not gated, in PRD v1.13) | about 31 ms parse of 42.7 ms `submit_to_index`, p50 (release, Linux container) | the command stays at about 49 / 69 ms p50 / p95 | another save or a watcher batch no longer waits up to that long on the slot mutex; the event follows the commit |

If P2 promotes the 5,000-line scenario to gating (PRD v1.13's open question), the parse is inside NFR-PRF-03's interval **on any thread**, so the lever for that class is the parse's own cost (an incremental parse, or a parse pool, §2.2), not where it runs. That is recorded in §Open design questions against NFR-PRF-03.

## Consequences

**Positive.** Every guarantee the save path meets by construction (close-before-marker, the echo after an accepted submit, one sequence per save, the counted census) is kept without a new thread or barrier. The one real cross-command cost of a synchronous parse, the slot mutex held across it, is removed. A view refreshing on `index://changed` after a save now reads the save, which §3.1.1 always claimed.

**Negative.** A save of a 5,000-line note keeps its reply about 43 ms later than the write's durability. The editor's "saved" state, and the hold that ADR-0016 §2 puts on an arriving `ExternalChange` while a save is in flight, are that much longer. Neither is a keystroke cost. A save's `index://changed` now arrives a little later than before (after the commit rather than at the submit), which is the correct time.

**Risks.** The writer's commit report becomes a second producer of `changed()`. If it fires for a batch that contains nothing from the save path, the throttle absorbs it; if it ever fires before `COMMIT` returns, decision 3 is void, so the acceptance test below is written to fail on exactly that.

## Implementation tasks

- **`[P1/impl] Report each committed batch from the index writer to an installed observer`** — **rust-core-dev**, `crates/serat-index/src/writer.rs` (`ActorOptions`, the commit path beside the existing `WriterHook`). The observer is called after `COMMIT` returns, on the writer thread, never under a lock another thread takes, and never for a rolled-back batch. Acceptance: a serat-index test that submits one `UpsertNote` and, inside the observer, opens a fresh read connection and finds the row (red if the call is moved before `COMMIT`); a test that a failed batch reports nothing. Serves NFR-PRF-03, FR-VLT-04; honours ADR-0001, ADR-0020. Bench: `p1-save-tail`'s `post-commit` phase must not grow by more than the observer's call (report it).
- **`[P1/impl] Announce a save's index://changed after its commit, and drop the slot lock before the parse`** — **tauri-app-dev**, `crates/serat-app/src/state.rs` (`submit_to_index`), `crates/serat-app/src/consumer.rs` (install the observer on the opener's `ActorOptions`; wire it to `ChangeNotifier`). Depends on the task above. Acceptance: (a) a serat-app test that on each save's `index://changed` a backlinks or search read returns the saved state (red with the `changed()` call restored at the submit); (b) a test that holds one save inside its load through a test `NoteSource` hook and shows a second save on another note completes its `submit_to_index` meanwhile (red with the lock held across `apply`); (c) the existing census, echo-ordering and `vault_opened_precedes_every_event_...` tests stay green; (d) `submit_to_index`'s doc comment on F-382 is corrected. The write path's property and hostile tests stay green (concurrent edit, undo/redo through the editor's base advance, crash mid-write). Serves NFR-PRF-03, FR-VLT-04, US-01; honours ADR-0016 §2, ADR-0011, ADR-0020.

Nothing moves the parse in P1. The 5,000-line command figure is a **known P2 item against NFR-PRF-03**, settled by PRD v1.13's open question and, if it is promoted, by a `p1-save-tail` run on the 5,000-line fixture (test-engineer).

## Objections recorded

**rust-core-dev and tauri-app-dev were not consulted in the session that wrote this record** (the architect had no channel to them in it). Their objections are therefore **absent, not waived**, and the record stays *proposed* until they have read it. The places I expect them:

- *rust-core-dev*: whether the commit observer belongs on `ActorOptions` or as a generation counter the notifier polls. Either satisfies decision 3; the acceptance test does not depend on which.
- *tauri-app-dev*: that the command's ~49 ms on a large note should simply be accepted as it stands, without the lock change. Decision 2 is kept because F-382 already named it as the fix for the day two saves can be in flight together, and because the watcher consumer's `reconciler()` takes the same mutex today.

## Tested against

1. **#172's phase table**, which is what found the synchronous parse. It is the case that rules out option 5: phase 17 is a parse and a queue send, not indexing, so a progress report on it would report the wrong fact.
2. **The save path's own code**, read for each dependant named in task #173: the `FileWritten` pairing (#71), the base advance, the echo ordering (F-224), the close guarantee, the catch-up window (#78). None depends on the parse having happened when the command returns; the close guarantee and the watcher ordering depend on the submit having happened, which is why option 3 was rejected rather than the parse simply being moved.
3. **Not yet tested:** decision 3's order on the real Tauri event path. The acceptance test (a) is the test; until it exists the claim that a read on `index://changed` sees the save is the design's, not a measurement's.
