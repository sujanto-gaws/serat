# ADR-0002: Rebuild instead of migrate
**Status:** accepted (design baseline 1.0) · **Date:** 2026-08 · **Serves:** FR-VLT-02, NFR-REL-02, NFR-PRF-04
**Source:** Serat Design Description §11, decision ADR-02

## Context
One of ten decisions in the Serat design that would be expensive to reverse. See docs/03-design/architecture.md for the surrounding design.

## Options considered
Versioned migrations, as any application with a real database would use.

## Decision
A breaking index schema change drops the database and rebuilds. No migration scripts.

## Consequences
An entire category of machinery and of partially-migrated failure states never exists. Requires the rebuild to stay fast, which NFR-PRF-04 already demands. The extraction cache is excluded and is migrated properly.

**What this ADR is operative through is the open check's trigger set**, and the set is narrower than it was. Architecture §3.4 lists six conditions under which an existing index is discarded and rebuilt; this decision supplies the third, `IndexVersion`, which is the whole of the upgrade path here. **One of the other five has been demoted and it is recorded in this ADR because the demotion changes what "rebuild instead of migrate" costs a user in practice.**

**A vault-identity mismatch is no longer a rebuild trigger on its own** (task #120, ruled in §3.4 under *Ruling (task #120)*; F-458, F-459). `index_meta.vault_root` was compared as a path string, so a mapped drive, a junction, a UNC form, a differently-cased root or a trailing separator each read as a different vault and bought a full rebuild — 28.6 s measured on the 20,200-note fixture, with no index for its duration. **The decision is that the comparison is canonicalised on both sides** — which is what `schema/001_init.sql:120` already asked for — **and that a surviving mismatch is recorded and reported rather than punished.** The reasoning: `notes.path` is vault-relative (`schema/001_init.sql:134`), and `asset_path` is the same `VaultPath` (`serat_index::apply::upsert_asset`, confirmed on #120), so a vault that moved carries an index in which every row is still right. **This does not weaken ADR-0002.** A schema change still drops the database and rebuilds; what stopped triggering a rebuild is a condition that was never about the schema and never about the index being wrong.

**The implementation has landed, and this paragraph used to carry its own re-check.** It said *"as of `4259abe` the code still compares `to_string_lossy()` and still rebuilds"*, written in the voice of the decision on purpose so that a decision record would not describe code it does not control (F-368). It is no longer true and the sentence is replaced rather than left to rot, which is the same discipline pointing the other way. `serat_index::identity::canonical_root` is recorded by `rebuild::mark_ready` and compared by `schema::inspect_for`; the mismatch is `IndexState::RootChanged`, a value; `RebuildReason::VaultMoved` is gone. The re-check that stays useful either way, because it names the comparison rather than its state: `grep -n 'VaultMoved\|ForeignVault' crates/serat-index/src/schema.rs crates/serat-index/src/open.rs` — zero hits in `schema.rs` is the fix, and the hits in `open.rs` are the renamed reason.

**What replaced the string comparison, which is not what this paragraph first said.** The reasoning above ended *"and the open path falls through to ordinary reconciliation"* when it was written. There is no reconciliation on the open path — §3.4 puts catch-up reconciliation in the *after usable* column, nothing consumes `serat_vault::walk::paths_of`, and the walk's result is counted and dropped (`serat_app::vault::run`). Taken literally the demotion would have served a genuinely foreign index as `Ready` for the life of the session with nothing that could ever notice, which is a **worse** outcome than the rebuild it replaced and not the trade §3.4 costed. So the trigger moved to *reconciliation's finding* instead of to reconciliation — the repair the ruling itself named for this objection. `serat_index::identity::describes` asks the one question a rebuild trigger needs, over a bounded sample of the index's own `notes.path` rows: **does any row name a file that is here?** One surviving path keeps the index and adopts the new root; none rebuilds, under a reason renamed `ForeignVault` after the condition rather than after `VaultMoved`, the single case in which the old name's stated rationale is false. **The rule that matters is unchanged and is now literally true: no rebuild is ever triggered by two path strings differing.**

**What the replacement costs, measured rather than argued, because the ruling's cost sentence was about a mechanism that does not exist.** On the real 20k index (`measure_the_open_check_on_the_20k_vault`): the six stamp steps alone **6.95 ms**, inside §3.4's 5–8 ms band; the whole adopt branch — stamp, then the identity probe, then the write-back — **23.59 ms**. That is what replaced a 28,600 ms rebuild, three orders of magnitude under it and well inside §3.4's remaining window. **Taken during the 2026-09-09 build freeze and therefore contended; both figures are indicative and neither is a gate number.**

**Why it is written here rather than only in §3.4.** This ADR is what a reader consults to learn when an index is thrown away, and a trigger that quietly stops firing is exactly the kind of change that leaves a decision record describing a system that no longer exists (F-368). The ratification of #120 named this obligation — *ADR-0002 documents the trigger being demoted, so its text moves in the same commit as the code* — and the text did not move with it; this is that paragraph, one commit late.

## Objections recorded
None at baseline. Two have arrived since, and they are recorded here because a baseline stub that still says *none* three hundred commits later is telling a reader something false about how examined the decision is (task #120's sweep; the lead's ruling of 2026-09-09).

**The precondition this decision leans on is met with less margin than the sentence implies.** *"Requires the rebuild to stay fast, which NFR-PRF-04 already demands"* reads as though the requirement discharges the obligation. The attested figure is **27,693.5 ms against a 30,000 ms budget** at `concurrent_build_processes: 0` with a 3.2% in-run spread (#96) — about 8% of headroom, while F-327 records the same binary on the same vault moving **35% between sessions**. So the drift exceeds the margin: rebuild-instead-of-migrate is affordable on an attested machine and has not been shown affordable on an arbitrary one. This does not reverse the decision — the machinery a migration path would need is a real and permanent cost, and F-327's drift is a property of the measurement environment rather than of the rebuild — but *"NFR-PRF-04 already demands it"* is a smaller guarantee than it sounds and should not be quoted as though the question is closed.

**The trigger set is where this decision is felt, and one of its triggers was wrong for two hundred commits without anyone paying for it visibly.** F-459's identity check cost a full rebuild on a spelling difference — measured at **8 ms for a warm open against 21–29 s for the rebuild** (test-engineer, #94), three orders of magnitude decided by a comparison no user can see or influence. The objection this raises against ADR-0002 is not that rebuilding is wrong; it is that **a decision whose failure mode is *slow* rather than *unsafe* attracts no scrutiny until someone measures it**, and C-02 is what makes that trade acceptable rather than what makes it invisible.

**rust-core-dev on task #120's demotion — raised, upheld in part, and the ruling changed because of it.** The ruling was taken with this crate's owner unreachable and §3.4 recorded the objection as *absent, not waived*, naming where it expected one: *if reconciliation-on-open assumes the index broadly matches the tree, discovering twenty thousand differences through it may be worse than a rebuild rather than equal.* **The cost objection is withdrawn; a stronger one replaces it.** Cost was never the problem — the problem is that the mechanism the demotion falls through to does not exist. §3.4's *after usable* row is where catch-up reconciliation lives and nothing is built in it; `serat_vault::walk::paths_of` is documented *"for reconciling against the index"* and has no consumer; the vault thread walks, counts the entries and drops them. **A demotion whose safety net is unbuilt is not a demotion, it is a removal** — and it would have replaced a loud 28.6 s rebuild with an index describing another vault, served as `Ready`, until something the user did happened to expose it. That is worse than what it replaced on design goal 3, and it is not the trade §3.4 costed, which explicitly assumed the bad case *"costs about what the rebuild would have cost"*.

**Everything else in the ruling is upheld, and the objection's remedy is the one the ruling itself named.** The two-questions argument is right and the `VaultMoved` name did assert a rationale false of its own case. So the demotion stands in full — *a path comparison never triggers a rebuild again* is now literally true of the code — with the trigger moved onto reconciliation's finding, sampled. The sample is 16 rows from each end of `notes.id` and the bar to keep the index is **one** surviving path, deliberately the weakest bar that can refute anything: a false *foreign* costs the silent rebuild this change exists to delete, while a false *describes* costs stale results on a structure C-02 calls disposable and is what the ruling accepted unconditionally for every mismatch. So the check can only improve on the ruling as written and can never regress it.

**One thing the objection does not close.** The gap it found is not this branch's to fill: the open path still has no reconciliation, and the probe is a bounded substitute for one question, not a replacement for the mechanism. When catch-up reconciliation is built, `identity::describes` is what it subsumes.
