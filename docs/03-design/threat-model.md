# Threat Model — Serat

The security requirements in the baseline are mostly negative — statements about what must not happen — and a negative is only credible if something enforces it. Each therefore has a mechanism rather than an intention.

**Every mechanism below was written in the present tense, and until F-270 one of the six existed.** That is the defect F-239 found in §Traceability arriving here: a control described as operating reads as covered, and a reader checking whether a negative is credible finds a sentence saying it is. So the table now separates **the mitigation**, which is the design and does not change, from **what enforces it today**, which mostly does not exist yet. A mechanism marked *(planned)* is not built.

**Two different absences, and conflating them is how the honest version becomes alarmist.** T-02, T-03 and T-04 are unenforced because the crates they govern — `serat-ai`, `serat-extract`, `serat-mcp` — have not been written; there is nothing yet to enforce anything against, and the design is not in doubt. **T-01 and T-05 are different: both could be enforced today against the code that exists, and neither is.**

## Assets
- The user's vault: plain Markdown notes and binary assets on local disk — the only source of truth (C-01, C-02).
- The rebuildable index in `.serat/` and the extraction cache `.serat/extract/`.
- **Note-open history, `.serat/history.json`** (architecture §9.2, from P1). It records which notes the user opened and when, up to 10 timestamps for each of 2,000 paths. This is behavioural data, not content. It is not derived from the vault and survives a rebuild. **Exposure path:** it sits inside the vault folder, so it reaches git or a sync tool whenever `.serat/` is not ignored. NFR-CMP-04's offer to add the ignore entry is a *Should*, and the user may decline it. Mitigations: it is never written outside `.serat/`; deleting it costs only ranking quality (C-02); and the NFR-CMP-04 offer names this file as a reason to accept. It is not sent anywhere by Serat (NFR-SEC-01).
- AI provider credentials.
- The user's privacy: no telemetry, no network traffic the user did not configure.

## Trust boundaries
- **Main process ↔ extraction worker:** untrusted binaries are parsed only in a short-lived child process with time and memory caps and no network; the worker binary links no HTTP client.
- **App ↔ network:** all outbound calls go through one client in `serat-ai`, constructed only when a provider is configured.
- **App ↔ external agents:** the MCP server binds stdio or a unix socket only; every agent write enters the diff-review queue (C-05).
- **App ↔ OS keychain:** credentials stored via the `keyring` crate, never on the filesystem.

- **Webview ↔ app:** **five of the six IPC commands are reachable from the `main` webview; the sixth and every remote origin are refused.** That is the state after ADR-0012 was implemented (task #48); the history below is kept because the two halves were closed for different reasons and a reader widening this surface needs both.

  - **Remote content cannot reach them at all, by the framework and not by us.** `Webview::on_message` runs the ACL check when the command is a plugin command, **or** when the app defines an ACL manifest, **or** when the origin is not local; a command with no resolved access is then rejected. This half held even before Serat declared a manifest, and still does. A message also carries an `invoke_key` injected by the manager, and one that does not match is dropped without a response.
  - **A local webview is now gated, because Serat opted in.** Tauri v2 allowlists application commands per window and per webview — `RuntimeAuthority::resolve_access` filters the resolved commands by the capability's `windows` and `webviews` selectors, and application commands live in the same map as plugin commands under the `__app-acl__` key. **`crates/serat-app/build.rs` declares an app manifest naming all six commands, and `capabilities/default.json` grants five of them** for `windows: ["main"]`. `open_vault` is deliberately withheld: nothing in the webview calls it, and it is invoked only from Rust inside `setup` (F-342). **Note the name collision before touching this** — `WindowsAttributes::app_manifest` in the same crate takes a string and sets the Windows side-by-side manifest XML, a different thing entirely; the ACL one takes an `AppManifest`.

  **This was not always true, and the previous state is what ADR-0012 was written to end.** Before task #48 the manifest flag was false, so the local path skipped the ACL entirely and all six commands were reachable from any local webview — containment was *there is exactly one window*, not *the commands are gated*.

  **What is still not gated, and it is a different question.** None of the six commands takes a `Window` parameter, so **no command knows its caller**. `windows: ["main"]` now decides *which windows may invoke which commands*; it does not let a command behave differently per window. ADR-0012 option 4 records that as deliberately out of scope, and a second window in P1 arrives with the allowlisting engaged rather than absent — the question it raises is which commands that window gets, answered in a capability file.

  Confirmed against the framework source at the versions `Cargo.lock` resolves — `tauri-2.11.5/src/webview/mod.rs` (the invoke path and its ACL condition), `tauri-2.11.5/src/ipc/authority.rs` (`resolve_access`, `has_app_manifest`), `tauri-utils-2.9.3/src/acl/mod.rs` (`APP_ACL_KEY`), `tauri-build-2.6.3/src/acl.rs` (`AppManifest`) — not from documentation and not from memory (F-280, F-330).

Three of the first four boundaries do not exist yet, because the crates on the far side of them do not. They are stated as the design; the table below states what holds today.

### T-07 in detail: two enforcement points, and the evidence behind them

Task #20's fix is **on main**, so T-07's row above describes a closed gap rather than an open one. It was written as a live gap while the fix sat on a branch, and the sentence saying so survived about ten minutes — which is the argument for the rule rather than against it. A threat model describing a branch as though it were running is the defect this table was corrected for once already, and **the safe direction for a security document is to under-claim**: claiming early asserts a protection that is not there, claiming late describes a gap that has closed, and only one of the two gets somebody hurt.

**The guard now has five tests that fail when it is deleted. It had none, and the difference is tasks #29 and #30.**

What this paragraph said before is kept, because the correction is the point. It first claimed the guard "has its own tests in serat-vault" — written by reading the tests *next to* it rather than by asking F-40's question of them, and false: deleting the four lines that return `PathEscapesVault` left all 62 serat-vault tests passing and the workspace green. That was mutation-verified twice, independently, and it is why the two tasks below exist.

- **Mechanism, `serat-vault` (task #30, `#[cfg(unix)]`):** `a_symlinked_note_is_refused_rather_than_read`, `a_symlinked_directory_component_is_refused` — the symlinked-*ancestor* case a single `lstat` on the final component would miss — and `write_atomic_refuses_a_symlinked_ancestor_before_touching_the_disk`, which also asserts the outside file was never created.
- **Acceptance, `serat-app` (task #29, every platform):** `a_symlinked_note_is_refused_at_read_file_not_followed` and `a_symlinked_note_is_refused_at_write_file_and_the_target_is_untouched`, run through the `read_file` / `write_file` IPC commands — the boundary NFR-SEC-06 is written at and the one task #18 finding 4 was actually about. Deliberately *not* `cfg`-gated the way the mechanism tests are: a security acceptance test that silently does not exist on a runner is worse than one that says it could not run.

**Mutation-checked here rather than taken on trust, which is F-304's rule applied to F-304's own example.** Deleting the guard on this machine fails both acceptance tests, and fails them the right way (F-58): `read_file` returns `Ok` carrying the outside file's bytes and `write_file` returns `Ok(FileWritten)` — the escape actually happening, not an incidental error somewhere near it. Restoring the four lines returns both to green.

**What is still not covered, stated precisely rather than dropped.** The three mechanism tests are Unix-only, so a Windows developer run exercises the guard **only** through the two acceptance tests, and those need a symlink — which on Windows needs Developer Mode or elevation. Where that is unavailable they report `SKIPPED` and assert nothing. **At this point the paragraph said “CI closes it”. CI does not.**

The claim is kept rather than deleted, because how it was reached is the point. It read: `ci.yml` runs `cargo test --workspace` on `ubuntu-latest` as well as `windows-latest`, and on Unix `make_symlink` panics rather than skipping (F-306), so “every push executes all five”. Every clause of that is a correct reading of `.github/workflows/ci.yml`, and it was read off the workflow **file** rather than off a **run**. `ci.yml` has **never produced a single job in its entire history** — 55+ runs across push and `pull_request`, each finishing in 0 seconds with 0 jobs and a “workflow file issue” (F-354). Its `fmt`, `clippy`, `workspace`, `crate` and `location-independence` jobs, the gate CLAUDE.md's definition of done actually names, have not executed once. **A control credited to a workflow that exists is not a control credited to a workflow that runs**, and this is the paragraph whose entire purpose is to state coverage precisely.

**What is executed on every push: two of the five, on Linux only.** `.github/workflows/serat-app-tests.yml` runs `cargo test -p serat-app --all-targets` on `ubuntu-latest`. The two acceptance tests are ordinary `#[cfg(test)]` unit tests in `crates/serat-app/src/state.rs` with no platform gate, and on Linux `make_symlink` resolves to `std::os::unix::fs::symlink` and panics rather than skipping (F-306) — so they run there, and they cannot quietly report `SKIPPED`. That job covers T-07 **by accident**: task #53 added it to answer F-345 about `mock_app()` on Linux, and T-07's acceptance tests happen to live in the crate it names.

**What is executed nowhere: the three mechanism tests.** They are `#[cfg(all(test, unix))] mod symlink_tests` in `crates/serat-vault/src/lib.rs`, and **no workflow runs serat-vault's tests at all** — `budgets.yml` runs `vaultgen` and `budget`, `design-docs.yml` runs `doclint`, `serat-app-tests.yml` is `-p serat-app`, and the one job that would have covered them is `ci.yml`'s crate matrix. On the Windows machines this team works on they do not compile, so they are absent rather than skipped, and nothing prints a line saying so (F-58's distinction, on the other side of it). Their evidence is the authoring run under task #30 — a real observation, and not a standing check.

**That was T-07's standing evidence — two acceptance tests, on `ubuntu-latest`, per push — and task #55 has since changed it. Everything from “At this point the paragraph said” down to here is kept as history**, because what a workflow file that has never run buys you is the whole of F-354's point and is not worth paraphrasing away.

**`ci.yml` now produces jobs, for the first time in this repository's history.** #55 found the cause by bisection rather than by reading: `needs.*.result` is an object-filter over `needs`, which is a **map keyed by job id and not an array**, so the expression is rejected at parse time before a single job is scheduled — legal expression syntax over the wrong type, which is why a YAML validator proved the file well-formed while saying nothing about whether it meant anything. Fixed at `4741956`.

**What that buys T-07, read off a run rather than off the workflow file — which is the whole discipline this section exists to enforce.** On main's run 34044208361: `cargo test --workspace (ubuntu-latest)` green, and every crate-matrix job green, `-p serat-vault` and `-p serat-app` among them, alongside `clippy`, `fmt` and the location-independence job. So **all seven tests bearing on T-07 now execute on every push to Linux** — the three `#[cfg(all(test, unix))]` mechanism tests, which previously ran nowhere at all; the two `serat-app` acceptance tests; and the two ungated walk tests task #62 added.

**And what it does not buy, which has to be said in the same breath.** `cargo test --workspace (windows-latest)` fails **intermittently**, so the `definition of done` gate does not stand. Task #70 settled why — a real cross-process race on the shared 20k vault path — and F-370 draws the consequence that matters here: **a green Windows run after a red one is not evidence the race is gone**, because a stale directory or a wrong path would fail every run alike while a fixture caught mid-generation fails only when the interleaving lands wrong. It needs a structural fix of the kind task #28 met, not a rerun. So **Windows coverage of T-07 is not merely absent; it is unavailable**, and a passing run in the meantime should be read as a sample, not as a result.

**The reason has changed and the conclusion has not, which is the more dangerous of the two ways a sentence like this goes stale.** *"Unavailable until #70 lands"* was written when #70 was the blocker. **#70 landed at `f34edb7`** — `VaultGenerationLock`, an advisory cross-process lock over `ensure_vault`'s check-then-generate window — and the race it names is fixed. Windows coverage of T-07 is still unavailable, for a different and unrelated reason: **CI produces no jobs at all (F-384)**, so there is no Windows run to read as either sample or result. A clause that names a discharged condition reads as *tracked and pending* when it is neither, and it would have retired quietly the day #70 merged if anyone had been looking. One-line re-check: `grep -rn 'VaultGenerationLock' bench/budget/src/lib.rs`.

Even after #70, **four of the seven will run there and three will not**: the mechanism tests are gated out by construction, so a green Windows job would not add them. The remedy for that is un-gating them the way #62 un-gated the walk pair and `serat-app` un-gated its acceptance pair — not a Windows job going green.

**When a security test may be platform-gated, and when it may not — the rule the tree already follows, written down once (task #75).** Task #64 read `serat-app` and `serat-vault` as contradicting each other on this. Read in full they do not; they state one rule from two sides, and it is worth having in one place because the next person will otherwise re-derive it or break it.

- **Gate a *mechanism* test whose property has no platform-specific content.** `serat-vault`'s `#[cfg(all(test, unix))] mod symlink_tests` is this case, and `serat-app` explicitly endorses it: “those are mechanism tests, safe to skip on one platform because the property under test has no platform-specific content.”
- **Never gate an *acceptance* test.** It is the case the requirement is written at, so **a security acceptance test that silently does not exist on a runner is worse than one that exists and says it could not run** — F-58's rule about guards, raised to the level of suites.
- **Do not gate when the claim itself spans platforms.** Task #62's walk tests are ungated for that reason and not as a general objection: `DirEntry::metadata` does not follow symlinks on *either* platform, and a test compiled on one cannot check a sentence about both.
- **`#[cfg]` is still right where the platform cannot run the harness at all.** `crates/serat-app/tests/acl_behaviour.rs` is `#[cfg(not(windows))]` because `mock_app()` faults in the OS loader before any Rust code runs, so `#[ignore]` cannot prevent it (ADR-0012). Gate when the platform cannot start the test; do not gate merely because the API used to *set it up* is platform-specific — that is a helper's job, and `make_symlink` exists twice in this repository to do it.

**Which leaves one question that this rule's own justification depends on, and it is open.** The gate above rests on “the property under test has no platform-specific content”. For containment against links, that is not obviously true on Windows, and **nothing in this repository examines it**: `junction`, `reparse point` and `mount point` appear nowhere in `crates/` or in these documents. A Windows **directory junction** is the ordinary way to link a folder and, unlike a symlink, needs neither Developer Mode nor elevation — so it is a link an ordinary user creates by accident or by tooling. That makes it a link type which no test exercises, which T-07's claim does not distinguish, and for which **the reason the ungated tests give for skipping on Windows — that symlink creation needs privilege — does not even apply.**

Whether `symlink_metadata().is_symlink()` reports a junction is a fact about `std` and the filesystem, not a matter of judgement — so it was **measured rather than reasoned about**, and the answer is the reassuring one.

**It reports one. The gate's justification holds.** On rustc 1.92.0, a directory junction created with `mklink /J` — **and it needed no elevation, confirming the exposure was worth checking** — is reported by `symlink_metadata().is_symlink()` as `true`, and by `file_type().is_dir()` as `false`. So `Vault::resolve`'s per-component check refuses a junction exactly as it refuses a symlink, and the walk declines to descend through one for the same reason task #62 gives about symlinked directories. **The guard is load-bearing here rather than incidentally correct:** reading through the junction succeeds when nothing refuses it, so the escape is real and it is the check that closes it.

**Stated with its limits, because one probe on one machine is not a suite.** This was a standalone probe outside the repository, on one toolchain and one NTFS volume; it covers the **mount-point** reparse tag that `mklink /J` creates and says nothing about other reparse types a filesystem may present. It was an observation rather than a regression test, and **task #76 has since made it one**: `a_junctioned_directory_component_is_refused` in `crates/serat-vault/src/lib.rs`'s `permission_tests` module creates a real NTFS junction pointing outside the vault and asserts `Vault::read` through it returns `PathEscapesVault` rather than the outside file's bytes. Mutation-verified the way F-58 asks: with `resolve`'s `is_symlink` check disabled it fails carrying the outside file's own bytes — the escape itself, not an incidental error.

**It is `#[cfg(windows)]`, and that is the gating rule above being applied rather than contradicted:** a junction is a Windows construct, so the claim under test genuinely is platform-specific and there is nothing for another platform's copy to assert. **What matters more is what it does not need.** `mklink /J` requires neither Developer Mode nor elevation, so unlike every other T-07 test this one cannot skip for want of privilege — **it is the first T-07 test that runs unconditionally on the reference platform**, which is the gap the coverage accounting above spent three passes describing and could not close while symlink privilege was the blocker.

**A convention for this section, written down because five corrections this session came from ignoring it.** A control's entry here cites **what its evidence is** — which tests exist, on which platforms they compile, what a deletion of the guard would turn red — and **not the colour of the last CI run**. Those are different lifetimes: which tests exist changes when someone merges, and can be checked from the tree at any later date; run colour changes hourly and cannot be reconstructed once the logs age out. #57 credited CI that had never run; #67 corrected that after #55 fixed it; #71 swept three more claims resting on the old fact; and #67's and #71's own replacements went stale within two commits, which is what produced this paragraph. **Run colour belongs in the register and the task list, which are written at a moment and read as of that moment. This document is read months later, by someone deciding whether a control holds.** Where a run must be cited — as above, to establish that a workflow schedules jobs at all — name the run id and say what it is evidence of, so a reader can tell a fact about the workflow from a fact about one execution of it.

**The count moved from five to seven and the coverage from two-per-push to seven, and the document said neither until asked.** That is the third time a control here has been under-credited after a merge rather than over-credited, which is the safer direction and still a defect: a security document that understates its own evidence invites work that has already been done.

**And a third enforcement point this accounting missed outright.** Everything above concerns `Vault::resolve`. The rule has *two* enforcement points, which architecture.md's *§A symlink is not a vault file* states as its opening line, and the other is `crates/serat-vault/src/walk.rs` — the `if stat.is_symlink() { continue; }` that the row above means by “a link is never indexed”. **It had no test, on any platform.** Deleting the line left `cargo test -p serat-vault` green: 64 passed, 0 failed, `walk_cost` passing too (removed by task #107; replaced by the counted unit test in walk.rs). Established by deletion rather than by reading (F-40), with a control: a short probe that builds a vault holding `real.md` and a symlinked `escape.md` fails with the guard gone and passes with it restored, so what is missing is the suite's coverage and not the probe's discriminating power (F-58). **Task #62 has closed it**, with two tests — one that the link itself is not enumerated, one that the walk does not descend through a symlinked directory — and deliberately not `#[cfg(unix)]`-gated, because `walk.rs` claims `DirEntry::metadata` does not follow symlinks *on either platform* and a test compiled on one platform cannot check a sentence about both. `std::os::windows::fs::symlink_file` worked on the machine that found this, which is a fact this document should have known before writing the Windows gap up as unavoidable. **Both were mutation-verified, and the first draft of the directory test passed with the guard deleted** — it asserted on the file *behind* the link, which a symlinked directory never reaches anyway, so non-descent came from the `is_dir()` branch rather than from the skip (F-364). The assertion was re-aimed at the link itself. serat-vault now passes 66.

**Why that guard matters past its one line, and why here is the worst place to have missed it.** Two things rest on the walk half and a changer sees only one. FR-VLT-01's lexical prefix strip — the fix that took the walk from about 2.0s to about 50ms — is sound **only** while no symlink is enumerated: canonicalising `vault/link.md` resolves to wherever the link points and is refused, while stripping the root prefix off it yields a perfectly ordinary-looking `link.md`. And T-07's own row asserts that a link is never indexed. Architecture.md warns about precisely this in prose — *“whoever changes it will be looking at only one of them”* — and nothing in the tree stops them, which is a warning with no test behind it. **The paragraphs you are reading exist to state T-07's coverage precisely, and they enumerated five tests over one guard while a second guard had none.** Third time this session a claim has survived by being checked against the layer that agreed with it. The remedy is task #55: fixing `ci.yml` restores all five in one move, rather than growing a second copy of the matrix that this register keeps finding is not free. Whether to widen `serat-app-tests.yml` to `-p serat-vault` as an interim is test-engineer's call and is routed there, not settled here.

**The two near-misses that prompted all of this are still there, and still near-misses.** `resolve_does_not_mistake_a_new_subdirectory_for_a_symlink` pins the false-positive edge and passes with or without the check, because it tests that the guard does **not** fire. The older `PathEscapesVault` assertions at the IPC boundary use `../outside.md`, `/etc/passwd` and the like — every one refused by `VaultPath::new` before `resolve` is reached, so they cover the *lexical* boundary while reading as coverage of the containment one. Neither was removed: they test real properties, and they are recorded here because **what made them dangerous was reading them as evidence of something they never touched**, which is a property of the reader rather than of the tests.

So T-07's control today is **a mechanism, a doc comment, and evidence at both the mechanism and the boundary** — which is what #30 and #29 were for, and both have landed. **What *stands* is narrower than what exists** — two of the five run per push, on Linux only; see the paragraphs above. **Separating the two mattered and is worth keeping separate here (F-282):** whether the guard fires and whether the *product* refuses a symlink through `read_file` are different claims, and only the second is what NFR-SEC-06 is written at. The rule both halves implement is stated once in architecture.md, *§A symlink is not a vault file* — which also records that FR-VLT-01's lexical walk strip is sound **because** of this property, so a fix that unified the two paths by making the walk *follow* links would close T-07 and silently break a performance budget. Write side is bounded **and** guarded: `write_atomic` refuses a symlinked ancestor before `create_dir_all` or the temp file, and independently renames a temp over the target — replacing a link rather than writing through it — and requires `.md`. **Executed, not read: the acceptance test sets `base_hash` to the outside target's own hash so the optimistic lock is satisfied and containment is the only thing left refusing (F-305), which is what stops it passing for the wrong reason.**

**T-07 cited no requirement when it was written, and now cites NFR-SEC-06.** Every other row named an NFR-SEC or an FR; T-07 named two constraints and a design goal, because the baseline covered telemetry, network, extraction, credentials and listeners — every one about reaching outward over a *network*, none about reaching outward over the *filesystem*. **The vault boundary was the product's first design goal and the one boundary with no requirement to violate.** Product-analyst allocated NFR-SEC-06 for it at v1.1, phrased to cover a direct path, a relative traversal and a symlink alike, and satisfiable by a check at the read rather than a promise about callers.

The row was written and left citing nothing, deliberately, rather than inventing a requirement to fill the column: **a threat model may name a threat the requirements missed, and must not quietly mint the requirement to match.** Kept here because the empty column is what made the gap visible, and a table that had been tidied would have hidden it.

## What this model does not cover

Stated so the model is not read as broader than it is, which is the failure the rest of this document was just corrected for.

- The pass behind these entries was **entirely static**. No dynamic verification was performed, and only T-06's guard was mutation-checked.
- **Most of the wider Tauri surface is still not audited.** Per-window command allowlisting and the IPC origin check have since been read in the framework source and are stated under *Trust boundaries* and as T-08; the asset protocol, the custom protocol handlers and the event system have not been. Given that the webview is the one network-capable component at P0, this remains the largest gap, and the CSP credited under T-02 is one control on a boundary still not examined whole.
- **Nothing ties a CSP edit to NFR-SEC-02.** The `tauri.conf.json` policy is enforcement this model did not know it had, which means it is also enforcement no test would notice being loosened.
- `contracts/ipc.rs` was not reviewed against **C-05**, because no AI or MCP path exists yet that could bypass the diff-review queue. That review is owed the moment one does.
- **T-07 is no longer in this list and T-02 still is.** The pass behind both entries was originally static, with no test to mutate — T-07's read path was traced by inspection and never executed, and "a test that creates a symlink inside a vault and calls `read_file`" was named as what would settle it. That test now exists, runs on every platform, and was mutation-checked while this section was being written. **T-02's CSP has had no such thing done to it**: it is still a control credited from configuration nobody has watched fail.
- **That claim was checked against the framework source and was half wrong, which is why it is recorded here rather than quietly fixed.** It held that Tauri v2 capabilities gate plugin commands only, so per-window allowlisting of Serat's six commands *did not exist and could not*. The framework does support it; Serat has not enabled it. The observable consequence today is identical and the remedy is not — one reading leaves nothing to do, the other leaves a decision open — and the difference was invisible from the documentation and from `capabilities/default.json`, both of which the original reading agreed with. **A second source that says the same thing is agreement, not confirmation**, and only the source settled it.
- **`capabilities/default.json`'s description was the misleading part, and task #48 rewrote it.** It said every Serat capability arrives as an application command "so there is no plugin permission to grant" — true, and reading as though nothing *could* be granted, which is a fair share of why F-280's wrong half was plausible for as long as it was. Kept here rather than struck out, because the misleading sentence is what a reader of any earlier revision still meets.
- **`app.security.assetProtocol` is absent, which is correct today and is the thing to watch.** FR-BIN's P2 viewing is what will make someone enable it, and `assetProtocol.scope` is then what decides whether T-07 reopens on a wider path than the IPC commands.

What makes it safe is that `boot_info` is serialised with `serde_json`, and JSON is a subset of JS expression syntax, so the assignment cannot break out of its literal. Recorded because a control credited to the wrong mechanism survives the removal of the mechanism it was credited to.
- `webview/` itself, the bundler and the updater were not reviewed.
