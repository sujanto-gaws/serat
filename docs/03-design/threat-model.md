# Threat Model — Serat

The security requirements in the baseline are mostly negative — statements about what must not happen — and a negative is only credible if something enforces it. Each therefore has a mechanism rather than an intention.

**Every mechanism below was written in the present tense, and until F-270 one of the six existed.** That is the defect F-239 found in §Traceability arriving here: a control described as operating reads as covered, and a reader checking whether a negative is credible finds a sentence saying it is. So the table now separates **the mitigation**, which is the design and does not change, from **what enforces it today**, which mostly does not exist yet. A mechanism marked *(planned)* is not built.

**Two different absences, and conflating them is how the honest version becomes alarmist.** T-02, T-03 and T-04 are unenforced because the crates they govern — `serat-ai`, `serat-extract`, `serat-mcp` — have not been written; there is nothing yet to enforce anything against, and the design is not in doubt. **T-01 and T-05 are different: both could be enforced today against the code that exists, and neither is.**

## Assets
- The user's vault: plain Markdown notes and binary assets on local disk — the only source of truth (C-01, C-02).
- The rebuildable index in `.serat/` and the extraction cache `.serat/extract/`.
- AI provider credentials.
- The user's privacy: no telemetry, no network traffic the user did not configure.

## Trust boundaries
- **Main process ↔ extraction worker:** untrusted binaries are parsed only in a short-lived child process with time and memory caps and no network; the worker binary links no HTTP client.
- **App ↔ network:** all outbound calls go through one client in `serat-ai`, constructed only when a provider is configured.
- **App ↔ external agents:** the MCP server binds stdio or a unix socket only; every agent write enters the diff-review queue (C-05).
- **App ↔ OS keychain:** credentials stored via the `keyring` crate, never on the filesystem.

- **Webview ↔ app:** the six IPC commands are reachable from **any local webview**, and from no remote one. The framework refuses a remote origin outright and does not gate a local one, and the two halves have different causes:

  - **Remote content cannot reach them at all, by the framework and not by us.** `Webview::on_message` runs the ACL check when the command is a plugin command, **or** when the app defines an ACL manifest, **or** when the origin is not local; a command with no resolved access is then rejected. Serat defines no app ACL manifest, so a remote origin resolves to nothing and is refused. A message also carries an `invoke_key` injected by the manager, and one that does not match is dropped without a response.
  - **A local webview is not gated, because Serat has not opted in.** Tauri v2 **can** allowlist application commands per window and per webview — `RuntimeAuthority::resolve_access` filters the resolved commands by the capability's `windows` and `webviews` selectors, and application commands live in the same map as plugin commands under the `__app-acl__` key. Opting in is a build step: `tauri_build::Attributes::app_manifest` (or a `permissions/` directory) declares the app's own permissions, and the capability then names them. **Note the name collision before wiring it up** — `WindowsAttributes::app_manifest` in the same crate takes a string and sets the Windows side-by-side manifest XML, which is a different thing entirely; the ACL one takes an `AppManifest`. `crates/serat-app/build.rs` calls bare `tauri_build::build()`, there is no `permissions/` directory, and `crates/serat-app/gen/schemas/acl-manifests.json` holds `core:*` and no `__app-acl__` key — so the manifest flag is false and the local path skips the ACL entirely.

  None of the six commands takes a `Window` parameter either, so **no command knows its caller** even where the framework would let one be named. **Containment against a second local window is therefore still *there is exactly one window*, not *the commands are gated* — but that is now a choice with a known cost to reverse rather than a limitation of the framework.** The condition that breaks it is the same as before: a second window. What has changed is that the fix exists and is three lines of `build.rs` plus a permission list, so this can be decided when P1 asks for the second window instead of being discovered then.

  Confirmed against the framework source at the versions `Cargo.lock` resolves — `tauri-2.11.5/src/webview/mod.rs` (the invoke path and its ACL condition), `tauri-2.11.5/src/ipc/authority.rs` (`resolve_access`, `has_app_manifest`), `tauri-utils-2.9.3/src/acl/mod.rs` (`APP_ACL_KEY`), `tauri-build-2.6.3/src/acl.rs` (`AppManifest`) — not from documentation and not from memory (F-280, F-330).

Three of the first four boundaries do not exist yet, because the crates on the far side of them do not. They are stated as the design; the table below states what holds today.

| T-02 | No unconfigured network — violation of NFR-SEC-02 | Information disclosure | All outbound calls through one client in `serat-ai`, never constructed without a configured provider; a test asserts no socket opens during a scripted session. | **Partly, and not by the stated mechanism.** `crates/serat-app/tauri.conf.json` sets a CSP of `default-src`/`script-src`/`style-src 'self'` with **no `connect-src`**, which is real enforcement at the webview — the one network-capable component at P0. **Nothing tests it.** No test references `tauri.conf.json` or `capabilities/`; the CSP, the `core:default` grant, the window label and `withGlobalTauri` are each removable without anything going red, so **the one genuine control found here is also the one with nothing guarding it** (F-40). | T-04 | Credentials — violation of NFR-SEC-04 | Information disclosure | OS keychain via the `keyring` crate; a filesystem scan after configuring a key on the release checklist. | **Nothing** *(planned)*. There is no `keyring` dependency in the tree. | — |
| T-05 | Local-only services — violation of NFR-SEC-05 | Spoofing / elevation of privilege | The MCP server binds stdio or a unix socket. There is no TCP listener in the codebase. | **Nothing, and a forbid list cannot supply it** *(planned)*. The claim is true today, but a listener comes from `std::net`, which is not a dependency and so cannot be denied by a crate deny-list. **This control needs a source lint** — a grep or clippy `disallowed-methods` — and saying "forbid list" here would have been wrong rather than merely absent. **Buildable now.** | — |
| T-07 | Reading or writing outside the vault root — violation of NFR-SEC-06 | Information disclosure / Tampering | Nothing resolves to a path outside the root the user opened. The vault is the trust boundary; a path that escapes it escapes the product's central promise (design goal 1, C-01, C-02). | **Yes, at the enumerating path and the reading path both — and the history of their disagreeing is kept below because it is what the control was built out of.** `VaultPath::new` refuses `..` segments, absolute paths and empty paths, and is tested — the lexical escapes are closed. `walk.rs` skips **every** symlink, so a link is never indexed. `Vault::resolve` was `root.join(path)` with **no canonicalisation and no containment re-check**, and `Vault::read` used it directly, so a symlink inside the vault was readable through the `read_file` IPC command even though the walk refused it — **the guard was on the path that enumerates and absent from the path that reads.** Task #20 **closed** it **at `resolve`**, which is the narrowest point every filesystem access in the crate passes through, so `read` and `write_atomic` both inherit it; checked component by component with `symlink_metadata` rather than by `canonicalize`, and a component that does not exist yet is not a symlink, so a new file in a new subdirectory is still allowed. The cost that ruling accepted is no longer an estimate: **43,587 `lstat` calls over 20,200 files, about 2.16 per file**, measured on the 20k vault by task #30, with a `calls_per_file < 4.0` regression bound in `bench/budget` that would catch a change to `canonicalize` — which multiplies by path depth rather than adding noise.

That fix is **on main**, so this row now describes a closed gap rather than an open one. It was written as a live gap while the fix sat on a branch, and the sentence saying so survived about ten minutes — which is the argument for the rule rather than against it. A threat model describing a branch as though it were running is the defect this table was corrected for once already, and **the safe direction for a security document is to under-claim**: claiming early asserts a protection that is not there, claiming late describes a gap that has closed, and only one of the two gets somebody hurt.

**The guard now has five tests that fail when it is deleted. It had none, and the difference is tasks #29 and #30.**

What this paragraph said before is kept, because the correction is the point. It first claimed the guard "has its own tests in serat-vault" — written by reading the tests *next to* it rather than by asking F-40's question of them, and false: deleting the four lines that return `PathEscapesVault` left all 62 serat-vault tests passing and the workspace green. That was mutation-verified twice, independently, and it is why the two tasks below exist.

- **Mechanism, `serat-vault` (task #30, `#[cfg(unix)]`):** `a_symlinked_note_is_refused_rather_than_read`, `a_symlinked_directory_component_is_refused` — the symlinked-*ancestor* case a single `lstat` on the final component would miss — and `write_atomic_refuses_a_symlinked_ancestor_before_touching_the_disk`, which also asserts the outside file was never created.
- **Acceptance, `serat-app` (task #29, every platform):** `a_symlinked_note_is_refused_at_read_file_not_followed` and `a_symlinked_note_is_refused_at_write_file_and_the_target_is_untouched`, run through the `read_file` / `write_file` IPC commands — the boundary NFR-SEC-06 is written at and the one task #18 finding 4 was actually about. Deliberately *not* `cfg`-gated the way the mechanism tests are: a security acceptance test that silently does not exist on a runner is worse than one that says it could not run.

**Mutation-checked here rather than taken on trust, which is F-304's rule applied to F-304's own example.** Deleting the guard on this machine fails both acceptance tests, and fails them the right way (F-58): `read_file` returns `Ok` carrying the outside file's bytes and `write_file` returns `Ok(FileWritten)` — the escape actually happening, not an incidental error somewhere near it. Restoring the four lines returns both to green.

**What is still not covered, stated precisely rather than dropped.** The three mechanism tests are Unix-only, so a Windows developer run exercises the guard **only** through the two acceptance tests, and those need a symlink — which on Windows needs Developer Mode or elevation. Where that is unavailable they report `SKIPPED` and assert nothing. CI closes it: `ci.yml` runs `cargo test --workspace` on `ubuntu-latest` as well as `windows-latest`, and on Unix `make_symlink` panics rather than skipping (F-306), so **every push executes all five**.

**The two near-misses that prompted all of this are still there, and still near-misses.** `resolve_does_not_mistake_a_new_subdirectory_for_a_symlink` pins the false-positive edge and passes with or without the check, because it tests that the guard does **not** fire. The older `PathEscapesVault` assertions at the IPC boundary use `../outside.md`, `/etc/passwd` and the like — every one refused by `VaultPath::new` before `resolve` is reached, so they cover the *lexical* boundary while reading as coverage of the containment one. Neither was removed: they test real properties, and they are recorded here because **what made them dangerous was reading them as evidence of something they never touched**, which is a property of the reader rather than of the tests.

So T-07's control today is **a mechanism, a doc comment, and evidence at both the mechanism and the boundary** — which is what #30 and #29 were for, and both have landed. **Separating the two mattered and is worth keeping separate here (F-282):** whether the guard fires and whether the *product* refuses a symlink through `read_file` are different claims, and only the second is what NFR-SEC-06 is written at. The rule both halves implement is stated once in architecture.md, *§A symlink is not a vault file* — which also records that FR-VLT-01's lexical walk strip is sound **because** of this property, so a fix that unified the two paths by making the walk *follow* links would close T-07 and silently break a performance budget. Write side is bounded **and** guarded: `write_atomic` refuses a symlinked ancestor before `create_dir_all` or the temp file, and independently renames a temp over the target — replacing a link rather than writing through it — and requires `.md`. **Executed, not read: the acceptance test sets `base_hash` to the outside target's own hash so the optimistic lock is satisfied and containment is the only thing left refusing (F-305), which is what stops it passing for the wrong reason.** | — |
| T-06 | Binaries never rewritten — violation of FR-BIN-19 | Tampering | No write path accepts a non-Markdown target; content hashes of every asset compared before and after a scripted session. | **`serat-vault`'s `write_atomic`**, which refuses a non-Markdown target with `NotAMarkdownTarget` and cites T-06 at the refusal, with a second check at the IPC boundary (`serat-app/src/state.rs`, refusing a non-`.md`/`.markdown` target as `IpcError::NotWritable`). `a_binary_target_is_refused` covers `.pdf`/`.png`/`.xlsx` and asserts no file was created; **removing the vault guard fails it**, so that one can fire (F-40). The IPC check has not been mutation-tested, so it is a second barrier rather than a second *verified* barrier. The only non-vault writes are the startup trace and the settings file. | — |

**T-07 cited no requirement when it was written, and now cites NFR-SEC-06.** Every other row named an NFR-SEC or an FR; T-07 named two constraints and a design goal, because the baseline covered telemetry, network, extraction, credentials and listeners — every one about reaching outward over a *network*, none about reaching outward over the *filesystem*. **The vault boundary was the product's first design goal and the one boundary with no requirement to violate.** Product-analyst allocated NFR-SEC-06 for it at v1.1, phrased to cover a direct path, a relative traversal and a symlink alike, and satisfiable by a check at the read rather than a promise about callers.

The row was written and left citing nothing, deliberately, rather than inventing a requirement to fill the column: **a threat model may name a threat the requirements missed, and must not quietly mint the requirement to match.** Kept here because the empty column is what made the gap visible, and a table that had been tidied would have hidden it.

## Verification

Five items were named here as though they ran: a network capture over a full session, a scripted-session socket assertion, a filesystem scan for key material after configuring a key, a content-hash comparison of every asset before and after a scripted session, and fuzzing of the MIME dispatcher (RISK-004). **None of the five exists, in CI or in a release checklist.** They are the design for verification and they are listed as such, not as a description of what runs.

The one control that is verified is verified by a unit test rather than by anything on this list — T-06's `a_binary_target_is_refused` — and it was checked by mutation rather than by reading, which is the standard the other five have to meet before they count.

## What this model does not cover

Stated so the model is not read as broader than it is, which is the failure the rest of this document was just corrected for.

- The pass behind these entries was **entirely static**. No dynamic verification was performed, and only T-06's guard was mutation-checked.
- **Most of the wider Tauri surface is still not audited.** Per-window command allowlisting and the IPC origin check have since been read in the framework source and are stated under *Trust boundaries*; the asset protocol, the custom protocol handlers and the event system have not been. Given that the webview is the one network-capable component at P0, this remains the largest gap, and the CSP credited under T-02 is one control on a boundary still not examined whole.
- **Nothing ties a CSP edit to NFR-SEC-02.** The `tauri.conf.json` policy is enforcement this model did not know it had, which means it is also enforcement no test would notice being loosened.
- `contracts/ipc.rs` was not reviewed against **C-05**, because no AI or MCP path exists yet that could bypass the diff-review queue. That review is owed the moment one does.
- **T-07 is no longer in this list and T-02 still is.** The pass behind both entries was originally static, with no test to mutate — T-07's read path was traced by inspection and never executed, and "a test that creates a symlink inside a vault and calls `read_file`" was named as what would settle it. That test now exists, runs on every platform, and was mutation-checked while this section was being written. **T-02's CSP has had no such thing done to it**: it is still a control credited from configuration nobody has watched fail.
- **That claim was checked against the framework source and was half wrong, which is why it is recorded here rather than quietly fixed.** It held that Tauri v2 capabilities gate plugin commands only, so per-window allowlisting of Serat's six commands *did not exist and could not*. The framework does support it; Serat has not enabled it. The observable consequence today is identical and the remedy is not — one reading leaves nothing to do, the other leaves a decision open — and the difference was invisible from the documentation and from `capabilities/default.json`, both of which the original reading agreed with. **A second source that says the same thing is agreement, not confirmation**, and only the source settled it.
- **`capabilities/default.json`'s own description is now the misleading part.** It says every Serat capability arrives as an application command "so there is no plugin permission to grant", which is true and reads as though nothing *could* be granted. Anyone widening that file should read the *Trust boundaries* entry first. Correcting the file is `serat-app`'s, not this document's.
- **`app.security.assetProtocol` is absent, which is correct today and is the thing to watch.** FR-BIN's P2 viewing is what will make someone enable it, and `assetProtocol.scope` is then what decides whether T-07 reopens on a wider path than the IPC commands.
- The `withGlobalTauri` judgement in this model's favour holds, but **not for the reason first given**: the CSP does not gate `initialization_script` at all, since that is host-injected rather than fetched. What makes it safe is that `boot_info` is serialised with `serde_json`, and JSON is a subset of JS expression syntax, so the assignment cannot break out of its literal. Recorded because a control credited to the wrong mechanism survives the removal of the mechanism it was credited to.
- `webview/` itself, the bundler and the updater were not reviewed.
