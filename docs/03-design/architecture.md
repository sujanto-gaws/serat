## Context diagram

This document describes how Serat is built. It takes the 135 requirements of the requirements baseline as given and records the structures, algorithms and interfaces that satisfy them, together with the alternatives that were rejected and why.

It is a companion to the repo-ready design files, which carry the parts a compiler, a database or a test harness consumes: the runnable DDL, the SQ grammar and its lowering, the IPC contract, the extractor trait and the MCP tool schemas. Where this document describes a mechanism, those files define it; where they disagree, the files are correct and this document is stale.

### 1.1 Design goals, in priority order

When two goals conflict, the higher one wins. This ordering is the tie-breaker for every decision in the ADR register.

| \#  | Goal                                           | What it forbids                                                                                                                         |
|-----|------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| 1   | The vault survives the application             | No state that only the index encodes; no format only Serat can read; no write that rewrites a file the user did not ask to change.      |
| 2   | Nothing blocks the keystroke                   | No indexing, extraction, embedding or query on the editor's path. A feature that can stall typing is redesigned, not optimised.         |
| 3   | Correctness is provable, not argued            | No mechanism whose behaviour under concurrent edit is reasoned about rather than tested; no silent coercion anywhere in the query path. |
| 4   | The cost of a query is knowable before it runs | No user-supplied code in the render path; no traversal whose depth is unbounded at plan time.                                           |
| 5   | Capability degrades; nothing breaks            | No unsupported input that stops the vault indexing. A file with no extractor is still typed, linkable and queryable.                    |

### 1.2 What P0 may invalidate

The performance figures this design was shaped around were targets rather than measurements, and three structures existed because of a number nobody had taken. **P0 has now settled two of the three, and settled the first in a way the question did not anticipate.** Closed at task #103 against the final P0 numbers; the third is P4's.

**The parse pool — contradicted, and the pool is not built.** Parsing is 14–17% of a 20,000-note rebuild across two attested sessions (#83 and #96, both at `concurrent_build_processes: 0`). Eliminating parsing outright would save less than removing one implementation defect did. §2.2 carries the reasoning and open design question 1's answer.

**The single-writer actor — the assumption §1.2 nominated is not the one the actor rests on, and as stated it is unfalsifiable within this design.** Two things, and the second matters more.

*It cannot be tested here.* "Write contention is the bottleneck" is a claim about what happens when writers contend, and this design permits **exactly one writer by construction**. There is no contention to observe, so no P0 measurement could confirm or refute it. A structure that eliminates a phenomenon cannot also be evidence about it.

*And the actor never rested on it.* §2.2's own justification is lock ordering, handle poisoning, a single queue to reason about, natural backpressure and crash isolation — and it states outright that a shared connection behind a mutex has **the same throughput**. So the actor is justified by failure modes rather than by throughput, and **would stand unchanged if contention turned out to be irrelevant.** §1.2 attributed to it a dependency it does not have.

*What P0 did establish, which is narrower and real.* The writer was the dominant phase — `producer_wait` 45–51% of wall clock on the first run — and its cost was **internal rather than structural**: eight `INSERT`s through `tx.execute`, re-preparing on every call, roughly a million redundant prepares per rebuild (F-324). `prepare_cached` took the rebuild from 27.1 s to 17.5 s and left `producer_wait` at 19%. That is evidence the **actor** was not the problem, and no evidence at all about the counterfactual it was nominated to answer.

*And one more narrowing, which is not the same as an answer.* NFR-PRF-03 now reads **4.306 ms p95 over a thousand consecutive saves with zero ADR-0011 backpressure events** (#95), so **the writer keeps up comfortably at P0's one-buffer workload** — the queue never filled, so the structure was never asked the question. That is a floor under the actor's adequacy and it is still not evidence about contention, because the design admits one writer and one buffer was in flight. `submit_to_index`'s own doc names where that stops holding: the day two saves can be in flight together is the day the slot mutex stops being free. **The assumption remains untestable here for the same reason it always was**, and what has changed is only that the structure is now known to be sufficient for the load P0 actually applies.

**Brute-force vector search at 200,000 chunks — untouched, and correctly so.** A P4 question on a P4 structure; ADR-09 was written to be reversed cheaply and nothing has tested it. It stays open rather than being closed by silence.

The re-baseline this section promised has happened: NFR-PRF-01 is split into a platform term and a Serat term (ADR-0014), on the strength of P0 numbers rather than quietly amended.

## Components & responsibilities

One Rust workspace of eight crates plus a Vue front end. The decomposition is by capability, not by layer, and the dependency rule is strict enough to be checked mechanically.

Fig. 1 — Crate dependency graph. Every arrow means “depends on” and every arrow points down, so a cycle would be visible as an arrow pointing up. serat-core holds types and traits and no I/O, which is what lets serat-sq typecheck against a SchemaProvider without linking serat-index.

### 2.1 The dependency rule

serat-core contains domain types and trait definitions and performs no I/O. Every other crate depends on serat-core and on nothing else internal. serat-app depends on all of them and nothing depends on serat-app. Cross-crate needs are expressed as traits declared in core and implemented wherever the capability lives, so the graph stays acyclic without anyone having to remember that it should.

This is not architectural decoration. It is what lets serat-sq typecheck a query against a SchemaProvider without linking a database, serat-mcp serve a QueryApi it does not own, and every crate be tested without a running application — which in turn is what makes the conformance suite and the property tests cheap enough to actually write.

| Crate         | Owns                                                                           | Notably does not own                                              |
|---------------|--------------------------------------------------------------------------------|-------------------------------------------------------------------|
| serat-core    | Domain types, trait definitions, error taxonomy                                | Any I/O whatsoever                                                |
| serat-vault   | Watching, reading, atomic writes, ignore rules, path canonicalisation          | Knowledge of Markdown                                             |
| serat-parse   | Markdown to blocks, fields, links, tasks; custom syntax extensions             | Any file access — it takes bytes and returns structures           |
| serat-index   | SQLite schema, the single-writer actor, incremental upsert, FTS, vectors, and the pipelines that fill them | Query language semantics; any knowledge of Markdown or of the filesystem |
| serat-sq      | Lexer, parser, typechecker, SQL codegen                                        | Execution — it emits a statement and a plan, nothing more         |
| serat-extract | Extractor registry, cache, child-process supervision                           | The parsing of any specific binary format                         |
| serat-ai      | Chunking, embedding, retrieval fusion, provider clients, proposal construction | Applying a proposal — only the app can, and only on a user action |
| serat-mcp     | Tool schemas and transport over the same query API the UI uses                 | A second implementation of anything                               |
| serat-app     | Tauri commands and events, wiring, the review queue                            | Domain logic of any kind                                          |

Where the rebuild lives, and why the rule is not bent to put it there

A full rebuild walks, reads, parses and writes, and the rule forbids any crate from taking two of those as dependencies. It is the first thing built that has no obvious home, and the answer decides whether the rule survives contact with the product.

It lives in **serat-index**, as `rebuild(source: &dyn NoteSource, parser: &dyn NoteParser, index_dir: &Path)`, with `serat_vault::Vault` implementing `NoteSource`. This adds no dependency edge: serat-index still depends on serat-core and nothing else internal, and it links neither a Markdown parser nor a filesystem walker. It is the escape hatch this section already describes, used for the case it was designed for.

Two arguments decided it against a `serat-pipeline` crate sitting above vault, parse and index. The first is that such a crate would need an exception to the rule — *this one crate may depend on three others* — and the rule's whole value is that it is one sentence a test can check. An exception is not a small cost; it is the cost of the rule. The second is that `rebuild` is less of a pipeline than it looks: four of its six steps are the bulk-load sequence in `schema/001_init.sql` §4.4 — drop the FTS triggers, load, rebuild the index, restore them — and all four are SQLite's business and nobody else's. The walk and the parse are inputs to it. Reading it as "the index's bulk-load entry point, taking its input through traits" describes it more accurately than "a pipeline that happens to end in SQLite", and the crate table above was simply written too narrowly.

The ruling comes with a constraint that keeps it from becoming a licence, and it is mechanically checkable in the same way the dependency rule is: **serat-index may acquire no knowledge of Markdown, and no access to the vault.** Everything it learns about either arrives through a trait declared in serat-core. If `comrak` or `notify` ever appears in that crate, orchestration has stopped being a caller of traits and has started being a second implementation, and the placement is wrong rather than merely untidy.

The second half needs stating precisely, because the obvious phrasing — *no filesystem access* — is wrong, and was written that way here first. serat-index owns `.serat/`, and §3.4 requires it to delete `index.db`, `-wal` and `-shm` and recreate the directory when it rebuilds; a crate forbidden the filesystem could not implement the design's own recovery path. The line is not "no files", it is **whose** files: serat-index may create and delete the index directory it owns, and may not open, walk, stat or read anything under the vault root. A vault path reaches it only as a `VaultPath` inside a row, which is a string it stores, not a file it touches.

So the check has two halves and they need different instruments. A forbid-list of external dependencies — `comrak`, `notify` — catches the first at the moment someone adds the dependency, in the same file and the same shape as `CORE_ALLOWED_EXTERNAL`, which already proves serat-core does no I/O. The second is a source scan restricting `std::fs` to the module that owns the index directory's lifecycle: crude, but it fails when someone reaches for the filesystem in the writer or the apply path, which is where the mistake would actually be made.

The trigger to revisit is named so the decision cannot drift indefinitely: **the second orchestrator that must not link SQLite.** Extraction in P2 and embedding in P4 are the candidates. One orchestrator in the crate that owns the sink is a narrow reading of a table row; two, one of which has no business linking a database, is a `serat-pipeline` crate and an ADR amending this rule — and by then it will be written against two real callers instead of one imagined one.

### 2.2 Threading and ownership

Concurrency is designed by ownership rather than by locking. Each of the four concerns below owns its data outright, and they communicate over channels.

| Concern      | Model                                                                   | Why                                                                                                                                         |
|--------------|-------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| Webview      | The main thread. Runs the UI and nothing else.                          | Anything that shares this thread can stall typing.                                                                                          |
| Index writes | One thread owning the only write connection; work arrives on a channel. | SQLite in WAL permits one writer. Making that explicit removes lock contention from the design entirely — there is nothing to reason about. |
| Index reads  | A small pool of read-only connections, plus **one search connection per open vault, outside the pool** (§4.5). | WAL readers never block the writer, so views and queries proceed during indexing. Full-text search has its own connection so that a slow or superseded search can be interrupted without holding a pooled connection, and nothing else can be interrupted. |
| File tree stream | One `TreeSession` per open tree (`crates/serat-vault/src/tree.rs`, task #13, merged at `1e15a3d`): the model of what was sent, and the sink it is sent to, **behind one `Mutex`**. | A message is emitted while the model is mutated, under the same lock, so mutation order is stream order (ADR-0015). There is no second ordering to reconcile. |
| Tree rows from the index | `serat_index::tree::read_tree_rows` opens **its own read-only connection, outside the read pool**, runs one fixed `SELECT path, kind FROM notes`, and closes it (task #13). | It runs once per tree open, before the pool needs to exist, and holds nothing afterwards. It is not a pool exception that has to be managed. |
| WAL checkpoints | **One checkpointer per open vault: its own connection and its own thread**, running only `wal_checkpoint(PASSIVE)`, after 250 ms of writer idleness or when the WAL passes 4,000 frames. The writer sets `wal_autocheckpoint = 0` (§3.1.1, #53). **The WAL is bounded by an invariant: no reader holds a read transaction outside one read call (tested).** Past 64 MiB the WAL is reported as pinned, and one idle `RESTART` with a busy timeout of 50 ms or less may be tried. | Checkpoints were half of every hub save's cost (#53). A `PASSIVE` checkpoint on another connection takes nothing the writer waits for, and it writes no rows, so ADR-0001's single writer of content holds. |
| Parsing      | **Sequential today**, one file at a time on the rebuild's own thread.   | Parsing is pure and CPU-bound, so a pool remains available the moment a measurement asks for one — see below, and §Open design questions.   |
| Extraction   | Separate processes, supervised, capped at min(cores−1, 4).              | A security boundary and a fault boundary, both of which a thread cannot provide.                                                            |

**The search connection is the one read connection behind a lock** (§4.5, code-reviewer-2). It is a `Mutex<Connection>`, which ADR-0001's pool otherwise avoids. Two rules make it safe:

- **Lock ordering.** No other lock is ever taken while it is held, so it cannot form a cycle. That includes pool connections, the writer's channel and serat-app state. Only the generation `AtomicU64` and the `InterruptHandle` are touched alongside it, and neither is a lock.
- **Poisoning.** The connection is read-only, so a panic while it is held can leave no half-written state. A poisoned lock is recovered with `PoisonError::into_inner`, or the lock is a non-poisoning one. It is never `unwrap`ped into a panic of its own.

`crates/serat-index/src/read.rs`'s module doc says "never a connection behind a mutex", and it must change in the implementation (task #47) to name this one exception.

**Every SQLite connection has a page cache of its own, and its size is ruled per connection** (#53). SQLite's default is 2 MiB (`cache_size = -2000`). #53 found that under strict alternation between two connections, one of them runs about three times slower, whichever one is the search connection. At 256 MiB the effect disappears, and R1 improves from 105 ms to 71 ms for "due" and from 205 ms to 180 ms for "the". 256 MiB on every connection is not affordable, so the sizes are these:

| Connection | `cache_size` | Why |
|---|---|---|
| Search connection (one per vault) | **64 MiB** | It runs the only reads whose working set (a common term's doclist, plus the `blocks` and `notes` pages it joins) exceeds 2 MiB, and it lives as long as the index handle |
| Writer (one) | **16 MiB** | A hub save touches its 679 inbound links and the note's blocks and FTS rows. Its working set is a few MiB, and it is never repeated across the vault |
| Checkpointer (one) | default (2 MiB) | A checkpoint copies WAL frames to the database and reads nothing through the cache |
| Per-call readers (R2–R5) | default (2 MiB) | They are opened per call (`crates/serat-app/src/reads.rs`), so a cache never outlives one read, and every read on them is ≤ 20 ms |

- **The budget.** SQLite allocates cache pages on demand, so these are ceilings, not allocations. The page caches total **at most 64 + 16 + 2 + 2·k MiB**, where *k* is the number of reads in flight. At *k* = 4 that is about 90 MiB, and that ceiling does not grow with vault size.
- **The memory line it must respect is NFR-PRF-07: below 200 MB resident without the embedding model, and below 400 MB with it.** NFR-PRF-07 is a P4 requirement, but nothing landing in P1 may make it unreachable. NFR-PRF-07's one-hour measurement reports each connection's `SQLITE_DBSTATUS_CACHE_USED`, so that the page cache's share is a number, not an estimate. If it crowds the 200 MB line, the lever is `PRAGMA shrink_memory` on the search connection after a minute without a search, at the cost of a cold first search. Lowering the writer's cache is not the lever.
- **#53's gap bin confirms the value before it ships.** The remedy task runs the strict-alternation blocks again with the search connection at 64 MiB. The bistability must be gone, and R1 must be within 10% of the 256 MiB figures. If it is not, the next step is 128 MiB, and nothing above that. Past 128 MiB this comes back here, with `mmap_size` as the alternative to weigh. `mmap_size` reads through the OS page cache, which all connections share, but it turns an I/O error into a signal and interacts with the rebuild replacing the file. That is why it is not the first choice.

**The `TreeSession` lock has four rules** (task #13, from its review):

- **The sink takes only leaf locks.** The sink runs under the session lock, so it is a channel send that must not block. It may take a lock that takes no other lock, such as the channel's own. It never takes the session lock (that would be re-entry), and never takes serat-app state.
- **Progress is lock-free.** `TreeSession::progress()`, which `mark_tree` and the status read, comes from atomics updated beside the model. So a status read never waits behind a stream, and cannot deadlock with the sink. **At `1923a70`, `progress()` takes the session lock, so #13 changes it before it merges.**
- **A poisoned session is discarded, and the stream restarts.** It is never recovered with `into_inner`, unlike the search connection. The model is mutated before the emit, so after a panic the model may hold an entry the front end never received. A recovered session would then send diffs against a state the front end does not have. So serat-app drops the session, and the front end gets a fresh stream from a new `TreeSession`, as it does on any reopen (ADR-0015).
- **`read_tree_rows`'s connection is not a pool member.** It is read-only, it has `query_only` and `busy_timeout` set like the pool's, it runs one statement and it is dropped on return. So it adds no lock and nothing to tune.
- **`Corpus::from_index`'s connection is the second, under the same terms** (the switcher, §9.2, task #16). It opens its own read-only connection, with `query_only` and `busy_timeout` set like the pool's. It runs the corpus's three fixed reads: notes, aliases and headings, each a full read in a fixed order. It builds the snapshot and drops the connection. It runs on a background thread once per corpus refresh, which is at `Ready` and 500 ms after the last `index.changed`, **never per keystroke**. The keystroke path reads only the in-memory snapshot.
- **Which reads may skip the `STATEMENTS` plan test.** §4.5 requires every fixed read to be listed in `STATEMENTS` and plan-checked. A read is exempt from that list **only if all four of these hold**:
  1. it is a whole-table or whole-kind read by design, so a full scan is its plan, and an index would only add rebuild cost (§3.1's third-caller rule);
  2. it runs on a connection of its own, opened for it and dropped after it, never on the pool or the search connection;
  3. it runs off every interactive path: a background thread, or once per open, never per keystroke, per save or per user query;
  4. its cost is measured where it is paid, as the switcher's corpus build time and the tree's first-paint figures are.

  `read_tree_rows` and `Corpus::from_index` meet all four. A read that fails any one of them is listed in `STATEMENTS` and plan-checked like R1–R5. A future full read that wants the exemption cites this rule in its doc comment.

Why the parse pool is described in the past tense

§2.2 said *a rayon pool over cores minus one* until I5's rebase, and the pool it described is now implemented by nothing that runs. I5 originally carried one; main independently grew a sequential rebuild, and the rebase kept the sequential version because it is the one merged and being measured. `PARSE_CHUNK`, `build_parse_pool` and `parse_chunk` were then removed rather than left with no callers, which is this project's own standard on unconsumed mechanisms (F-228). `parse_pool_threads()` survives as sizing, documented as unwired.

**Recorded rather than quietly amended, because §1.2 names the parse pool as one of three structures P0 exists to test, and deleting a mechanism is not the same as testing the assumption behind it.** A rebuild number taken today measures the sequential design; presenting it as evidence about the architecture in this section would be a number honest about what it measured and misleading about what it means.

The measurement was taken without the pool, deliberately: a *sequential* run reports the ratio of the **work**, where a pooled one would report the ratio after one side had already been optimised — what the pool achieved rather than whether it was needed.

##### Open design question 1, answered: neither

**The answer is that at P0 scale neither structure is the constraint, and finding that out required going one level below the question.**

The first run named the writer: `producer_wait` was **45–51%** of the wall clock against **11–12%** for parse. Read carefully that says less than it appears to — `producer_wait` measures **the producer being blocked**, not what writing cost, so it means the writer could not keep up, and nothing about why.

**Why it could not keep up was none of the three things this design nominated.** Not the actor, not the transaction boundaries, and not `BATCH_SIZE`, whose own doc comment calls batching *"the whole of the tuning, and the number open design question 1 will move if the writer turns out to dominate."* The writer did dominate and batching was not the answer. A probe inside `commit()` put **16.0 s of a ~21 s writer inside `apply` itself**: eight `INSERT` statements issued through `tx.execute`, which re-prepares on every call, sitting in per-row loops over blocks, fields, links and tasks — **roughly a million redundant prepares per rebuild.** `prepare_cached` took `apply` to 6.6 s and the rebuild from **27.1 s to 17.5 s**, same build, same minute (F-324). Suppressing the opportunistic `ANALYZE` during a bulk load removed another 2.8 s of work that every later batch superseded (F-325).

With that gone the phases are **walk 9%, read-and-hash 16%, parse 17%, `producer_wait` 19%, FTS build 10%** — no phase above a fifth, and the rebuild 42% under NFR-PRF-04's budget. Those five do not sum to the wall clock and are not meant to: the gap is the producer and the writer overlapping, which is the actor doing its job.

**So the pool is still not built, and now for a measured reason rather than a deferred one.** It would attack 17% of the clock; eliminating parsing outright would save less than removing one implementation defect did. That is a stronger argument than the first number gave, because the first number's 45–51% was itself inflated by the defect.

**The methodological result is the one to carry, and it is F-10's own lesson one level up.** The phase split was built so the writer could be told from the parser, and it did exactly that. It cannot see inside the phase it names — and every hypothesis about what was inside was wrong. **Which phase and which line are different questions, and a phase split answers only the first.**

**One caveat that bounds all of the above (F-327).** The absolute figures move about 35% between sessions on unchanged code — 36.4 s, 37.6 s, 27.1 s, 24.4 s and 19.0 s have all been measured on the same binary and the same pinned vault. The **shares** are the durable result and the milliseconds are not, and a budget whose measurement noise exceeds its own margin is not yet a gate.

**What was given up, stated because the pool existed for a reason:** wall-clock rebuild time on a many-core machine, if parsing does turn out to dominate. Nothing else — and notably not this table's own stated reason for the pool. *"Leaving a core free is what keeps the UI responsive during a rebuild"* is a justification for a **bound on** parallelism rather than for parallelism, and a sequential rebuild satisfies it completely.

Why one writer, not a mutex

A shared connection behind a mutex has the same throughput and worse failure modes: lock ordering becomes a thing anyone touching the index has to think about, and a panic while holding it poisons the database handle. A channel to one owner has a single queue to reason about, natural backpressure, and a crash that takes down one thread rather than corrupting shared state. See ADR-01.

The channel is not the whole interface

Anything that must observe its own write needs a barrier, so the writer handle also exposes `flush()`, which blocks until the queue has drained. The rebuild uses it before `ANALYZE`; tests use it for read-after-write. It had to exist on the first day the writer existed.

This is the design's real shape: **one writer, asynchronous, with an explicit and expensive barrier** — not an interface with no synchronisation left in it, which is how the paragraph above reads on its own. The barrier must never appear on the save path, where blocking would put the index back on the keystroke path (goal 2). A caller there reads the pre-write snapshot and is corrected by `index.changed`; a caller that cannot tolerate that is telling you it belongs on the writer's thread, not that it needs a longer lock.

The test that keeps this honest: **if a message needs a reply, the channel is a lie and you have a mutex with extra steps.** That sentence was written against `IndexOp`, whose variants need no reply, and it is the right instinct stated one word too narrowly — `flush()` was carved out of it by name on the day it was written, and I4 added three more replies for the rebuild's phases. Four exceptions to a rule that names one is a rule about to be ignored, so here is the category rather than the list.

**A message may need a reply only if it is a barrier.** The distinction is not whether a reply exists but what it is for, and one question separates them: *would this message exist if the caller did not need to wait?*

- A **barrier** exists only because of the wait. Its reply means "the state you asked for has been reached", the caller is the code that owns the sequence, and the next step is invalid until the previous one has landed. `flush()` before `ANALYZE`, and the rebuild bracketing its own bulk load, are barriers. A barrier may carry a value — a count of what it completed — as long as that value is a fact about what the barrier finished and not an answer computed on the caller's behalf.
- A **request** would exist anyway, and the reply is the point of sending it: the caller wants a value the actor holds. That is the thing the original sentence forbids, and it is still forbidden. A request answered over the channel is a mutex with extra steps, and a per-operation completion handle is the same thing wearing a smaller hat — which is why callers still get none.

Two limits keep the category from swallowing the rule. No barrier may appear on the save path or on anything a keystroke waits for, because blocking there puts the index back on the editor's path whatever the message is called (goal 2, §3.1.1). And a barrier is a phase boundary in a sequence, so the number of them is small and each one is legible as such; a barrier that appears in the middle of ordinary work is a request that has been renamed.

The second limit needs a countable form, because the first real case put it in conflict with the category question. A proposed `apply_and_wait(path, bytes)` for the save-to-index harness is a barrier by the category — it is `submit` plus a wait and would not exist without the wait — and is called once per note in a thousand-iteration loop, which is the middle of ordinary work. So: **count the calls per unit of work at the call site.** A barrier appears a fixed number of times per phase; one that appears once per item is the signal to look harder, and it resolves one of two ways.

Either it is on a production path, and the first limit already forbids it — which is the case that matters and the reason this is a rule at all. Or it is a harness deliberately serialising in order to measure a latency, which is legitimate, because a benchmark is neither the save path nor anything a keystroke waits for. Note what this means: `flush()` called once per note *in a harness* is fine, so counting alone does not settle it and the first limit is the one doing the work.

What the harness case does require is that **the barrier stays visible where it is called**. `submit()` followed by `flush()` shows a wait; `apply_and_wait()` is a verb that reads like a write and hides one, and it is a single copy-paste from the save path, where the wait is forbidden. So the ruling on that command is that it should not exist — not because a harness may not block, but because a name that conceals a barrier is how a barrier reaches a path that forbids it. Composing the two existing primitives costs the harness one line and keeps the actor's command set at the barriers it already has, each of which is a thing ADR-01 obliges someone to reason about.

The rule earned its keep by catching its own exceptions: it is why the three new replies were examined at all, and the answer was that they are correct and the wording was too narrow. A test sharp enough to fire on the cases it should permit is worth more than one loose enough never to fire.

The queue's other under-specified half — what happens when it is full — is ADR-11. The short version is that the answer is different for each producer: the watcher may be dropped because it cannot be blocked without losing OS events silently, and the bulk producer may not be dropped because it can be blocked at no cost. Routing both through one policy is a measured defect, not a theoretical one.

## Data model

The full DDL is schema/001_init.sql and runs as delivered. This section records why it is shaped that way.

The file in the repository is the P0 subset — notes, blocks, fields, links, tasks, the full-text index and the index's own stamp — and it names, in a header comment, the phase that adds each of the tables it omits: assets in P1, types in P2, chunks and the sqlite-vec table in P4. Under ADR-02 there is nothing to gain from stubbing them now, because the upgrade path for a schema change is `rm`.

One table is in the DDL that is not in the requirements data dictionary. `index_meta` is a single row describing the index itself — schema version, indexer version, the vault root it was built from, a note count and whether the last build committed. It is what makes the open check of §3.4 cost two milliseconds instead of a second. Every column of it describes the index rather than the vault and is re-derived by a rebuild, so it does not breach C-02; nothing about the user's notes may ever be added to it. The data dictionary also names the full-text table `notes_fts`, which the DDL does not have: it is `blocks_fts`, over blocks, per §4.4 — a note-level FTS table cannot answer "which block" and so cannot serve a citation or a locator.

### 4.1 Block granularity is the pivotal decision

Serat indexes at block level rather than note level. One table of blocks, each anchored either by a byte range in a Markdown file or by a locator inside a binary, is what makes block references, precise AI citations, writable views and binary extraction all fall out of the same structure. Every one of those features would need its own machinery under note-level indexing; under block-level indexing they need none.

### 4.2 Three typed value columns

A field stores its value in val_text, val_num, val_date or val_bool, chosen at index time from the schema. The query compiler therefore knows at plan time which column a comparison touches, so a date range becomes an indexed scan rather than a per-row string parse. This single choice is most of the performance gap between Serat and a Dataview-style evaluator at scale.

### 4.3 Migration strategy: there isn't one

Because the index is derived and rebuildable, a breaking schema change drops the database and rebuilds it. No migration scripts, no versioned upgrade path, no partially-migrated states to debug. This removes an entire category of machinery from the project, and it is a direct and unglamorous consequence of the first design goal.

The one exception is the extraction cache, which is expensive to recompute and therefore does need care. It is keyed by content hash and extractor version, so a better PDF extractor invalidates PDFs and nothing else, and an index rebuild does not touch it at all.

Found by running it, not by reviewing it

Executing the reference query against a fresh database showed the planner choosing ix_notes_kind — which matches nearly every row — over ix_notes_type. Without ANALYZE, SQLite cannot know that kind='note' is almost the whole table while type='project' is a small slice, so every typed query degrades into a full scan. The DDL now ends in ANALYZE and the indexer re-runs it after every rebuild and after any batch touching more than 5% of notes. This is exactly the defect that would otherwise surface as “queries are slow on my real vault but fine in the tests” three months into P2.

### 4.4 Index strategy

| Index                               | Serves                                                    | Note                                                          |
|-------------------------------------|-----------------------------------------------------------|---------------------------------------------------------------|
| ix_notes_type                       | Every typed query's outer scan                            | Partial on type IS NOT NULL, and requires statistics; see above and below. |
| ix_notes_kind                       | Listing assets; separating notes from assets              | The index the planner wrongly preferred before ANALYZE existed. |
| ix_fields_note_key                  | The pivot join, one per referenced field key              | Becomes a covering index for the common projection.           |
| ix_fields_key_date / \_num / \_text | Range and equality predicates on a field across the vault | Partial indexes — only rows where that column is non-null.    |
| ix_links_src / ix_links_dst         | Rollups and the backlinks pane                            | Backlinks read dst; rollups read src.                         |
| ix_tasks_open                       | Every open-task query                                     | Partial on done = 0, which is the only side anyone queries.   |
| ix_links_src_block / ix_fields_block / ix_tasks_block / ix_tasks_note | No read. They serve the foreign-key cascade when a note or block is deleted (NFR-PRF-03, #47 ruling below) | **User_version 7.** Created after the bulk load, never maintained during it. The two on nullable columns are partial on `IS NOT NULL`. |
| blocks_fts (external content)       | Full-text over notes and extracted binaries alike         | Triggers keep it in step; verified including the delete path. |

Two of these were changed by writing the DDL and running it, and the file is now the correct copy. `ix_notes_type` is partial on `type IS NOT NULL`, because an untyped note is always valid and most of a real vault is untyped: on a 20,000-note fixture with 500 typed notes, the full index holds 20,000 entries and `ANALYZE` estimates 10,000 rows for `type = 'project'`, while the partial index holds 500 and estimates 500. Both give the same plan; only one gives the planner an estimate that is not wrong by a factor of twenty, which is the same failure §4.3 is about. The cost accepted is that `GROUP BY type` becomes a scan and a temp b-tree.

Running the DDL also settled how a full rebuild must load it. `blocks_fts` is kept in step by triggers, and for an incremental save that is exactly right — a note is a dozen blocks and the trigger is what makes the search index correct with no second code path. For a rebuild it is the wrong shape by a wide margin. Loading 26,000 blocks with the triggers live took 2.1 seconds in one transaction and 6.8 to 10.3 seconds spread across two to twenty-six; dropping the three triggers, loading, and then issuing the FTS5 `'rebuild'` command took 0.32 seconds, and produced a byte-identical search index. The same shape loaded 259,971 blocks in 5.6 seconds.

Those figures are calibration, not results: a development machine, through a Python harness, against SQLite 3.50.4 — the same caveat §3.4 carries for its own numbers, repeated here because these are the ones `serat-index` will be quoted at and they sit a long way from it. The ratio is what the decision rests on, and it reproduces: an independent run through rusqlite on 3.53.2 measured 5.8x against the 6.6x here, in-memory against on-disk, with an identical resulting search index. T2's numbers on the benchmark vault replace both.

So a full rebuild runs: recreate the schema, read the trigger definitions out of `sqlite_master` and drop them, bulk-load in batched transactions, `INSERT INTO blocks_fts(blocks_fts) VALUES('rebuild')`, re-execute the saved trigger text, then stamp `index_meta` and `ANALYZE`.

That last step is also what makes the sequence crash-safe, and the property is worth stating because the next person to touch it will not derive it. If the process dies anywhere in the middle — including in the window where the triggers are dropped and `blocks_fts` is therefore not being maintained — `index_meta.state` is still `'building'`, so the next open discards the file and rebuilds (§3.4). **That holds only because the final step is the sole place `state` becomes `'ready'`.** A second write of `'ready'` added anywhere earlier, for any reason, silently removes crash recovery from the rebuild path and leaves a half-built index that opens cleanly. Reading the triggers back out of the database rather than keeping a second copy of the DDL is what makes the recreated triggers identical to the delivered ones by construction, instead of by a test that has to notice a copy going stale. The incremental path never drops anything: at 100 blocks per transaction the trigger path cost 15ms, which is inside NFR-PRF-03 with room to spare.

The three `ix_fields_key_*` partial indexes were expected to need help from the query compiler — a redundant `val_date IS NOT NULL` emitted beside every predicate — on the assumption that SQLite's partial-index prover is too limited to infer it. It is not: `=`, `<`, `BETWEEN`, `IN` and a `LIKE` prefix on the typed column all select the partial index unaided. The lowering emits no redundant term. The one shape that cannot use them is a bare `key = ?` with no predicate on the value, which is why a merely *projected* field must be reached through the pivot join on `ix_fields_note_key`, never by selecting on `key` alone.

**Every foreign key's child column is indexed. Ruled on #47's measurement (user_version 7).** On the 20k vault, a content save of the highest in-degree note (`areas/Retention 2.md`, 679 inbound links, 13 blocks) took **788 ms p50 and 924 ms p95, against NFR-PRF-03's 50 ms**, on #47's branch `task/p1-47-search-limits` at `6b192bb`. About 800 ms of that was `DELETE FROM notes` in `remove()`.

- **The cause.** `links.src_block`, `fields.block_id` and `tasks.block_id` reference `blocks(id) ON DELETE CASCADE` with no index on the child column. `tasks.note_id` references `notes(id)` with no index either, because `ix_tasks_open` leads with `due`. With `foreign_keys = ON`, SQLite looks up the child table for every deleted parent row, and with no index each lookup is a full scan. So the 13 deleted blocks each scanned 220,367 links, 169,883 fields and 77,530 tasks.
- **Re-measured on a copy of a 20k index** (the scratch index from §4.5's search ruling: Python SQLite 3.45, 4 cores, inside a rolled-back transaction):

  | Variant | Time |
  |---|---|
  | Cascade as now | 808 and 819 ms |
  | Explicit child deletes by `note_id` first, foreign keys still on | 859 and 925 ms |
  | The three block-FK indexes | 21 and 25 ms |
  | **The three plus `tasks(note_id)`** | **7 and 13 ms** |
  | No block foreign keys at all (simulated with `foreign_keys = OFF`) | 13 and 18 ms |

- **Rejected: explicit child deletes instead of the cascade.** Deleting the children first does not help. SQLite still checks each deleted block against each child table, and that check is the scan, whether or not any child row is left. The measurement shows it.
- **Rejected: dropping the block foreign keys.** It is no faster than the indexes, it is the same ADR-0002 schema change, and it gives up an integrity check that a rebuild comparison would otherwise have to provide (goal 3).
- **The four indexes**, created by serat-index's writer after the bulk load, as `ix_links_unresolved` is (`writer.rs` captures, drops and recreates it). They are never maintained row by row during a rebuild:
  - `CREATE INDEX ix_links_src_block ON links(src_block) WHERE src_block IS NOT NULL;`
  - `CREATE INDEX ix_fields_block ON fields(block_id) WHERE block_id IS NOT NULL;`
  - `CREATE INDEX ix_tasks_block ON tasks(block_id);`
  - `CREATE INDEX ix_tasks_note ON tasks(note_id);`

  **Why a partial index is safe here.** SQLite runs each cascade as `… WHERE child = old.id`, one statement per deleted parent row. `=` implies `IS NOT NULL`, so the planner can use an index that is partial on `IS NOT NULL`, and the measurement above shows that it does. A child row whose key is NULL references nothing, so no cascade or check ever looks it up, and leaving it out of the index loses nothing. Being partial keeps those rows out: 91,445 of the 169,883 field rows and 7,989 links have no block.
- **The implementing commit re-confirms the figures and pins them with a test.** The timings above were taken with Python's SQLite 3.45, not with the SQLite bundled by rusqlite, so rust-core-dev repeats them on the bundled build. `EXPLAIN QUERY PLAN` does not show foreign-key actions, so a plan check cannot catch a regression, and a regression test is needed. It belongs to serat-index:
  - Build a fixture with thousands of rows in `links`, `fields` and `tasks`, and delete a 13-block note from it.
  - **Assert `SQLITE_STMTSTATUS_FULLSCAN_STEP == 0`** on the delete statement.
  - **First, show that the assertion can fail.** With the four indexes dropped, the same counter must be non-zero. That proves it counts the cascade's scans, which run as sub-programs of the delete. If it does not count them on the bundled build, the test asserts instead that the delete takes at most a small multiple of its time with the indexes, and records why.
- **Expected NFR-PRF-04 cost: about 140 ms per rebuild at 20k**, building the four after the load. On the same copy that was 62 + 32 + 24 + 18 ms, against 116 ms for a non-partial `links(src_block)` alone. That is about 1% of #15's 13.2 s on the 4-core box and of the 27.7 s reference figure. F-373's rule still holds. These are the first indexes added to `links` since that finding, and the per-link cost is paid once, by a sort after the load, not by 220,000 inserts. **rust-core-dev measures the rebuild with and without them in the implementing task. If the difference is more than 500 ms at 20k, this ruling comes back here.**
- **Each save pays a little more.** Every insert into `links`, `fields` and `tasks` during an incremental save now also updates one or two more b-trees. A note has a few dozen such rows, so this is expected to be within noise. NFR-PRF-03's benchmark reports it, and must show the 679-in-degree save under 50 ms at p95, **with that note in the save set**.
- **Delivery.** One commit changes `schema/001_init.sql` (the four statements, and `PRAGMA user_version = 7`), serat-index's `INDEX_VERSION`, and the writer's capture-and-recreate list, as `001_init.sql`'s header requires (ADR-0002, F-134). Every existing index is rebuilt on first open. `schema/001_init.sql` is not changed on this branch, because changing it apart from `INDEX_VERSION` would break the version rule for one commit.

#### 4.5 P1 read paths — fixed statements, no query language

P1 needs five reads and has no SQ (C-03, ADR-0010: SQ is P2). Each read is a **fixed-shape prepared statement** in a `read` module of serat-index. The statements run on the read-only pool (§2.2), never on the writer (ADR-0001). The user supplies values and never shape: a statement's text is chosen from a closed set in code, and every user string is a bound parameter. Before the index is `Ready`, every read returns the index state instead of rows (`contracts/ipc.rs` rule 1).

**Latency expectations are what task #15's benches report against.** No NFR budgets search, backlinks or property lookup, so these are **expectations, not gates**. A breach is a finding for architect and product-analyst, not a red build. Each is measured at 20k, with 50k reported beside it. **None of these figures is binding, and none borrows another requirement's budget** (ruled on #15's measurement, below). NFR-PRF-05's 100 ms covers an SQ query returning 500 rows, which is P2 and goes through the query compiler, not these statements. NFR-PRF-06's 50 ms covers the quick switcher (§9.2), which does not use `blocks_fts`. No NFR-USE requirement states a search latency.

**Every fixed read is in `STATEMENTS`, and the plan test checks each one.** `serat_index::read::STATEMENTS` lists every fixed statement by name, and `crates/serat-index/tests/read_paths.rs` runs `EXPLAIN QUERY PLAN` over each one and asserts that its plan uses the indexes in the table's *Uses* column. A read that is not in `STATEMENTS` has an unchecked plan, which C-03's "the cost of a query is knowable before it runs" (goal 4) cannot accept. **R5 is in that list**: at #17's fix-up head (`742bc86`) `STATEMENTS` holds six entries and not `ATTACHMENTS`, so #17 adds it before #17 merges. The plan test then asserts that R5's plan names `ix_notes_path_fold` and `ix_notes_file_name`, and that it has **no `SCAN` of `notes` inside the correlated subquery**, because a scan there would run once per asset.

**Ruling on #15's measurement: R1's common-term cost is accepted, not remedied (task #15 @ `695c236`).** R2, R3's single page and R4 met their expectations (5.5, 5.6 and 3.1 ms). R1 did not for common terms. Its p95 was 231.8 ms for "the" and 195.1 ms over a six-term set at 20k, and 562.8 ms and 521.0 ms at 50k.

- **Where the time goes.** FTS5 computes BM25 for every matching block before it can sort. "the" matches 161,130 of 313,610 blocks at 20k. The time does not come from the joins or the snippet. It was checked again on the 20k index (Python's SQLite 3.45, 4 cores, median and worst of 15 runs). The statement alone took 239 ms. Without `snippet()` it took 233 ms, because SQLite already evaluates the snippet for the 50 rows it returns, not for every match. **`SELECT rowid FROM blocks_fts WHERE blocks_fts MATCH ? ORDER BY rank LIMIT 50`, with no join, took 222 ms.** So no rewrite of the statement can recover the time, and a two-stage version (rank in a CTE, then join and snippet) was slower, at 290 ms. **The cost is about 1.4 µs per matching block**, which matches "of" (71,736 blocks, 105 ms) and "and" (15,349 blocks, 21 ms). A multi-term query costs about as much as its rarest term: `"meeting" "notes"` took 1 ms.
- **How many terms it affects.** At 20k, two terms match more than 70,000 blocks, which is about where 100 ms falls: "the" and "of". Seventeen terms match more than 30,000. The 20% line in the table is that boundary, expressed as a ratio so that it holds at 50k.
- **Rejected: stopword exclusion in the tokenizer.** FTS5 has no stopword option, so it would need a custom tokenizer, which is native code registered on every connection. It would be a schema change (ADR-0002). It would also break phrase search, since `"the end"` needs the positions of "the". It would be English-only in a vault that is not. And Obsidian finds "the", so Serat would silently find less than the application it is compatible with (NFR-CMP-01).
- **Rejected: a hard `LIMIT` before rank** (score only the first N matches). That returns the first N blocks by rowid and presents them as BM25's best. That is a wrong answer that looks like a right one, against FR-NAV-02's "BM25 ranking" and design goal 3. A higher goal is not traded for a figure that is not binding.
- **Rejected: a prefix or trigram index.** Neither addresses the cost. A `prefix=` index speeds up prefix queries, and P1 has none. A trigram index makes every doclist longer, which makes the common case slower. Both cost rebuild time against NFR-PRF-04.
- **Accepted, because no higher goal is at stake.** Search does not block the keystroke (goal 2): it runs on Enter or after 250 ms of idle typing, on the dedicated search connection (§2.2, and obligation 2 below), never on the writer. Its cost is knowable before it runs (goal 4): it is about 1.4 µs per block matched by the rarest term, which `fts5vocab` could count. No statement computes that yet, so the cost is knowable but not known in advance. Results stay correct and ranked. **Three obligations come with the acceptance.**
  1. **A newer search supersedes an older one, in the front end.** A 230–560 ms query can still be running when the next idle-typing search starts, so the search panel drops any response that is not for its latest request (vue-frontend-dev, `docs/03-design/ui/screens/search-panel.md`).
  2. **At most one full-text search is in flight per open vault, and a new one interrupts the old one, in Rust** (code-reviewer-2). Dropping a stale response is not enough. The superseded statement would keep a read-pool connection busy for its full 230–560 ms, so a few idle-typing searches could hold every pooled connection and queue R2 backlinks and the other reads behind them.
     - **Which connection.** serat-index's reader opens **one dedicated search connection** per open vault, read-only and configured like the pool's connections. That connection is not part of the pool. **R1 and R1 + R3, the statements with free text, run only on it.** R2, and R3 in both its field form and its `type` form (#15's bench calls that one R4), run on the pool as before. The pool's connections are never interrupted, so nothing except a full-text search can be cancelled.
     - **A search generation, not a one-shot interrupt** (code-reviewer-2). An interrupt alone is a lossy signal, in two ways. (a) If B's `interrupt()` lands before A's statement has started, it does nothing, so A runs its full 230–560 ms and B waits behind it. (b) With three quick searches, C interrupts A while B is waiting for the lock. `std::sync::Mutex` is not FIFO, so C may take the lock first, and B then runs a whole stale search. So each open vault has **one search generation, an `AtomicU64`**, and every full-text search does the following:
       1. **It increments the generation and keeps the new value** as its own.
       2. **It calls `interrupt()`** through the search connection's `InterruptHandle` (rusqlite `Connection::get_interrupt_handle()`, which is `Send` and held outside the lock), to stop whatever statement is running now.
       3. **It takes the connection's lock.** If the generation is no longer its own when it gets the lock, it returns `Superseded` without running a statement. This fixes (b): B finds that C's number has replaced its own, and returns at once.
       4. **It stores its number as the connection's current generation and runs the statement.** A **`progress_handler`** installed once on the search connection, **every 10,000 VM instructions**, interrupts the running statement whenever the vault's generation is no longer the current one. This fixes (a): a statement that started after the interrupt still stops within about a millisecond of being superseded. It is a callback, not an SQL function, so the statement's text and C-03 are unchanged. #47's bench reports R1 with and without the handler, and the difference must be within noise. **The interval was 1,000, and #47 measured it at +8–12 ms (about 10%) on 50–100 ms searches. It rises to 10,000.** The generation needs to be noticed within about a millisecond, not within a microsecond. Counted on the 20k scratch index, R1 executes about 14,000 VM instructions per millisecond: 3.39 million for "the" in 229 ms, and 1.51 million for "of" in 115 ms. So a check every 10,000 instructions still runs about every 0.7 ms, and there are a tenth as many calls. **The hard bound is deterministic, so CI load cannot fail it.** A superseded statement must stop **within two handler calls after the generation moves**, which is at most 20,000 VM steps. #47's test counts those calls through a test-only hook. Wall-clock stop latency is reported, and asserted only against a generous 50 ms, as a gross-regression net. **Only a failure of the deterministic bound lowers the interval.** A slow wall-clock figure on a loaded runner never does.
     - **#47's observation that the search connection was 15–30% slower than a pool reader was a matter of cache state, not of role, and #53 closed it.** With the handler off, "due" took 102 ms against 78 ms, and "the" took 192 ms against 176 ms. #53's diagnosis (`ecaeee0`; raw data in its archive) ran the three checks ruled here:
       1. **The pragmas were read back** from the pool reader, the search connection and a second pool reader, and they are identical.
       2. **`prepare_cached` hits on every call** on both connections.
       3. **Under strict alternation, one of any two connections runs about three times slower, regardless of role.** A pool reader against a second pool reader shows the same 3× gap as the search connection against a pool reader, and swapping the order swaps which one is slow. With batches instead of alternation, the gap is 1–4%.

       That is consistent with SQLite's 2 MiB default page cache being bistable when two connections alternate over a working set larger than either cache. **At `cache_size` = 256 MiB the gap disappears**, and R1 itself improves from 105 ms to 71 ms for "due" and from 205 ms to 180 ms for "the". So the remedy is a page-cache size per connection, ruled in §2.2 (64 MiB for the search connection, confirmed by #53's gap bin before it ships). It is not a change to obligation 2.
     - **The wait for the lock runs off the async executor.** serat-app calls search inside `spawn_blocking`, so a search waiting for the lock never holds an executor thread that IPC needs.
     - **The outcome.** serat-index maps both `SQLITE_INTERRUPT` on the search connection and a generation found moved in step 3 to `SearchOutcome::Superseded`, an outcome, not an `IpcError`, and never logs it as an FTS5 rejection. serat-app returns it as is. The front end discards it without showing anything, because by rule 1 it has already moved to a newer request. `SQLITE_INTERRUPT` anywhere else would be a defect, and it surfaces as one.
     - **Tests** (serat-index, task #47):
       - Start a common-term search, then a second while the first is running. The first returns `Superseded`, the second returns hits, and an R2 issued at the same moment returns without waiting for the first.
       - **Start three common-term searches back to back. Only the last returns hits**, and the other two return `Superseded`.
       - Increment the generation after a statement has been prepared but before its first step, which is case (a), and check that the statement stops.
  3. **Paging R1 re-scores.** A second page of 50 costs the same as the first, because `OFFSET` does not keep the scores. That is accepted for P1, where results are capped at 50 a page and loading more is a deliberate click.
- **It is reopened by the real vault, not by the synthetic one.** The generator's vocabulary is not the owner's, and its top terms include "due" and "est". The P1 gate's week in Serat on the real vault settles whether a common-term search is something a user waits through. This is recorded in §Open design questions.

**R3 returns up to 500 rows in one statement, not ten `OFFSET` pages.** R3 sorts the whole match set by `notes.path` before it can apply `OFFSET`, so every page of 50 re-sorts everything. Ten pages took 48.9 ms at 20k and 147.1 ms at 50k (#15). Re-measured on the 20k index for a 660-row `[tags:project]`: one page of 50 took 5.2 ms, ten `OFFSET` pages took 44.8 ms, ten keyset pages (`path > ?`) took 50.3 ms, because keyset pages still sort the full match set, and **one `LIMIT 500` statement took 4.8 ms, returning the same 500 rows**. This is still one fixed statement with the limit as a bound parameter, so C-03 and the closed set are unchanged. **`SearchArgs::limit` is capped per statement:** at most 50 when the query has free text (R1 and R1 + R3, which BM25 costs per match), and at most 500 for a property-only query (R3), which serat-index clamps. A property result of more than 500 rows still pages with `OFFSET` beyond the first 500. That is P2's table view's concern (NFR-PRF-05), not P1's.

**Search syntax, and the closed set it maps to.** The search box accepts free text, `"quoted phrases"` and at most **one** `[key:value]` term — Obsidian's own property-search syntax, so nothing new is learned. Free text only selects R1; a `[key:value]` term only selects R3; both select R1 + R3. A second property term is refused with a message and never silently dropped: statements stay a fixed set of three. Free text becomes an FTS5 query in Rust. Each bare word becomes a quoted FTS5 string (`"word"`, with `"` doubled), phrases stay phrases, and terms are ANDed. User text can therefore never be FTS5 syntax, and a stray `AND`, `*` or `NEAR(` cannot fail or reshape the query. There is no prefix matching in P1: `blocks_fts` has no `prefix=` option, and adding one costs NFR-PRF-04 rebuild time (the DDL's own comment). Search runs on Enter and after 250 ms of idle typing. It is not search-as-you-type; the switcher (§9.2) is.

**Degenerate input never reaches FTS5 as an error.** **An unbalanced `"` is refused, not repaired.** The search panel does not submit while a quote is open ("Close the quote to search a phrase", `docs/03-design/ui/screens/search-panel.md`). If one reaches Rust anyway, `search` returns `SearchOutcome::UnbalancedQuote` without running a statement. There is one behaviour, and it is the screen spec's. A query that tokenises to nothing — only punctuation, only quotes, or empty after removing the `[key:value]` term — returns no rows and a message ("nothing to search for"), without running a statement. If FTS5 still rejects a query, that is a defect: it is shown as the same message and logged, never raised as an error.

**Results never carry HTML.** The snippet is delimited with the control characters U+0002 and U+0003. The front end splits on them and builds **text nodes only**, with `<mark>` elements it creates itself between them. No string from a note is ever inserted as markup (T-09). U+0002 and U+0003 can occur in a note's own text, and there they mis-place a highlight. That is harmless precisely because only text nodes are built, and it is accepted rather than paid for with a second pass over every snippet.

**Location.** A hit carries its block's byte range and the `notes.hash` it was indexed from. Opening a hit maps `byte_start` to `{line, col}` with ADR-0016's function, over the bytes just read, when the hash matches. When it does not match (the file changed since indexing), the block's `ord` is used and the location is marked approximate. It is never a wrong line presented as exact.

**Backlinks detail (FR-NAV-04).** The acceptance case — three paragraphs across two notes gives three entries — is exactly "one row per distinct (source note, source block)": two links in one paragraph are one entry. A link with no source block, from frontmatter such as `owner: [[Person]]`, is one entry labelled *frontmatter*. The excerpt is the block's `text`, cut to 300 characters by Rust. **Unresolved links never appear in any backlinks pane**, because an unresolved link names no note. **Ambiguous names follow §9.3's resolver.** A `[[Meeting]]` with two `Meeting.md` files resolves to the shorter path, and only that note lists it, which is Obsidian's behaviour. Because it is a resolution rule, it must stay current in both directions:

- **A note appears** at path *P*. There are two steps:
  - **(A1)** `resolve_inbound(P)` (`crates/serat-index/src/apply.rs`) re-resolves the unresolved links whose `dst_path` is one of *P*'s four candidate spellings (path, path without `.md`, file name, file name without `.md`), through `ix_links_unresolved`.
  - **(A2)** The file-name-resolved links that point at *another* note with the same `file_name` may now prefer *P* as the shorter path. Find those notes through `ix_notes_file_name` and their inbound links through `ix_links_dst`, and re-run the resolver on the ones with no `/` in `dst_path`.
- **A note disappears** from path *P*. `ON DELETE SET NULL` unresolves its inbound links. They now have `dst_note IS NULL` and a `dst_path` that is one of *P*'s candidates, so A2 **cannot see them** — it walks `dst_note`. **(B1)** Run `resolve_inbound` with the removed path's candidate spellings. That lookup goes through `ix_links_unresolved` and re-points each orphan at a remaining same-named note, or leaves it unresolved. Without B1, the index after a delete differs from the index a rebuild would produce, which is exactly what C-02's *disposable* promise forbids.
- **A note is renamed** from *P* to *Q* (`rename` in `apply.rs`, which today updates `path` and nothing else). Four steps:
  1. Set `file_name` as well as `path`.
  2. **Unresolve the renamed note's inbound links** (`dst_note := NULL WHERE dst_note = id`), because a link written as `[[old/P]]` must stop pointing at *Q*.
  3. Run B1 for *P*.
  4. Run A1 and A2 for *Q*.
  Links whose written target still names the note resolve back to it in step 4, and links written for the old name go to another same-named note or stay unresolved. Every step goes through `ix_links_unresolved`, `ix_links_dst` or `ix_notes_file_name`.
- **Test:** for each of the three events, compare the index with a fresh rebuild of the same tree.
- No new index on `links` is added for re-resolution, because every index on `links` costs the rebuild once per link (F-373). The foreign-key indexes of user_version 7 (§4.4) are added for a different reason: an unindexed cascade made one save take 900 ms. They are built after the load, so they cost the rebuild one sort each.
- This is the per-save half of §3.1's third-caller rule. **Neither step runs during a bulk load**, where the rebuild's single final `resolve_links` pass supersedes both (F-371).

**Property lookup detail (FR-STR-03, FR-BIN-02).** List values are one `fields` row per item, so `[tags:x]` matches an item. **Values compare case-insensitively (ASCII fold, `COLLATE NOCASE`), as Obsidian's property search does — except `type`.** Keys compare exactly. **`[type:x]` compares exactly** and uses `ix_notes_type`. A `NOCASE` comparison would make that partial index unusable, and indexing it `NOCASE` would stop it serving P2's binary `type = ?` lowering (§4.4). A type is also the name of a type note, which the P2 schema registry matches exactly. So `[type:Contract]` does not find `type: contract`, and the search panel should say so in its hint, which is frontend-designer's to add. The key prefix of `ix_fields_key_text` still selects the rows, and the value comparison becomes a filter over one key's rows; #15's benchmark checks that against the 20 ms expectation, using the vault's largest key (`tags`). Non-ASCII case is not folded for property values in P1, unlike link resolution (below). Inline fields (`key:: value`) are FR-STR-04's and P2's, so R3 filters `source = 'frontmatter'`. **A sidecar hit is returned as its asset.** When the matching note is some asset's sidecar (ADR-0005: `x.pdf.md` for `x.pdf`), the row returned is the asset's path, kind and MIME, with the sidecar path beside it. That is FR-BIN-02's "the PDF is returned as a typed row". It needs `notes.sidecar_path` populated (task #17, per §7) and one partial index, `ix_notes_sidecar ON notes(sidecar_path) WHERE sidecar_path IS NOT NULL`. That index holds at most one entry per asset (200 in the benchmark vault), so its rebuild cost is negligible. It lands with task #17's writer, not before — an index nobody reads is a cost with no counterweight.

**Block references need no new index.** `[[note#^id]]` looks for `blocks.block_ref = ?` within one note, and `UNIQUE(note_id, ord)` already indexes `note_id` as a prefix, so the lookup is a scan over one note's dozen blocks. The DDL header's planned `ix_blocks_ref` is withdrawn on that ground. **Case-insensitive link resolution (§9.3) is one change in five places, all in one commit (task #15).** It folds full Unicode case through stored columns, not `COLLATE NOCASE`, which folds ASCII only (ruled below, NFR-CMP-01). A partial change is F-371 again: any comparison left on the raw column while its index is on the folded one turns the per-link join into a scan.

1. `notes` gains `file_name_fold` and `path_fold`, and `ix_notes_file_name` moves to `file_name_fold`.
2. A new `ix_notes_path_fold ON notes(path_fold)` serves the comparisons with `links.dst_path`. `notes.path`'s `UNIQUE` index stays binary and keeps its own job. The new index covers 20,000 rows, not 217,000 links.
3. `links` gains `dst_fold`, and `ix_links_unresolved` moves to `dst_fold`. It is dropped and recreated around the bulk load, as now.
4. Every comparison in `resolve_links` and `resolve_inbound` becomes a binary `=` on the folded columns. A link target supplied as a parameter is folded in Rust by the same function before it is bound. Each read stays one fixed-shape statement, and no SQL function is registered.
5. The rebuild benchmark runs in the same PR.

**The fold is one Rust function in serat-core, `fold_case`, and it is per-character Unicode lowercasing: `s.chars().flat_map(char::to_lowercase)`, then `ς` (U+03C2) mapped to `σ` (U+03C3).** It is not `str::to_lowercase`, not ICU and not full case folding. The base mapping is the one Obsidian uses, through JavaScript's `toLowerCase`.

- **Why not `str::to_lowercase`.** It is context-sensitive for Greek final sigma, so it is not compositional. The resolver compares `fold(file_name)`, where the file name carries `.md`, with `fold(target) + ".md"`, and `path_fold` is built across `/`. Under `str::to_lowercase`, `fold("ΟΔΟΣ.md")` is `"οδοσ.md"` but `fold("ΟΔΟΣ") + ".md"` is `"οδος.md"`. So an all-caps Greek name ending in `Σ` would never resolve, while Obsidian resolves it (code-reviewer-2, verified). The same split happens at every `/` in a path.
- **The property `fold_case` must have: `fold(a + b) == fold(a) + fold(b)` for all strings `a` and `b`.** Per-character mapping has it by construction. Mapping `ς` to `σ` makes the result independent of where in a word a sigma falls. Task #15 property-tests that equation over arbitrary Unicode strings, Greek included, and task #12's corpus includes an all-caps Greek note name ending in `Σ`, linked in lower case and in capitals.
- **The cost is accepted.** Two names that differ only in `ς` against `σ` fold to the same key, and the usual tie rule (shortest path, then byte order) picks between them. So `[[émile]]` resolves to `Émile.md`, as it does in Obsidian, and `ß` does not become `ss`, also as in Obsidian. Full case folding would resolve links Obsidian leaves unresolved, which is a compatibility defect in the other direction. ICU would add a native dependency to make SQLite do what one Rust call already does at write time. Task #12's corpus checks the fold against Obsidian, and where they disagree Obsidian wins and `fold_case` changes. A change to `fold_case` is a schema change (ADR-0002: drop and rebuild).

**Why in P1 and not deferred.** The cost is three short text columns and the same number of indexes as the `NOCASE` plan, which it replaces rather than adds to. The `dst_fold` column is the one per-link cost, written once per link and computed in Rust. The rebuild sits at 27.7 s against 30 s (NFR-PRF-04), so #15's benchmark decides whether that fits. **No fallback is designed, and an earlier draft's was withdrawn.** Without `dst_fold`, the bulk `resolve_links` join has no folded column on the links side, so the whole rebuild would degrade to ASCII. It would then need the `NOCASE` indexes on the notes side that this plan removes, which makes it a second plan rather than a fallback (code-reviewer-2). **If #15's benchmark shows the fold columns breach 30 s, the PR does not merge (C-06, ADR-0013), and this ruling comes back here with the measurement.** A non-ASCII vault (French, German or Turkish note titles) would otherwise see links that resolve in Obsidian and not in Serat, which is the NFR-CMP-01 defect a user notices first.

**Not covered by this ruling.** Property values (R3 above) stay ASCII `NOCASE` in P1. Unicode normalisation (NFC against NFD, which macOS file names can carry) is not applied to either side, and it is in §Open design questions.

### Indexing

The pipeline that turns filesystem events into index rows. Its design constraint is not throughput but isolation: it must be impossible for anything here to delay a keystroke.

Fig. 2 — The indexing pipeline. Backpressure lives in the bounded, path-deduplicating work queue; the hash check discards most events before any parsing happens. Nothing here sits on the keystroke path.

#### 3.1 Two paths into the index, and two budgets

There are two ways a note reaches the index, and conflating them is what made NFR-PRF-03 look unsatisfiable.

| Path                      | Trigger                                       | Budget                                   | Debounced?                       |
|---------------------------|-----------------------------------------------|------------------------------------------|----------------------------------|
| Save path (§3.1.1)        | Serat writes a file the user is editing.      | 50ms p95 — NFR-PRF-03                  | No. The watcher is not involved. |
| Watcher path (§3.1.2)     | Any other process writes a file in the vault. | 500ms — FR-VLT-04's acceptance criterion | Yes, 150ms coalescing.         |

Finding F-03 read the 150ms coalescing window as a design that misses a 50ms budget by construction, and the arithmetic was right: 150 > 50. The mistake was in taking both requirements to describe one path. They do not, and they never conflicted — FR-VLT-04, the requirement that actually governs an external change, allows 500ms precisely because it has a debounce to absorb.

Found by reading the design against itself

The save path is not a new mechanism invented to close a gap; it was already required by §3.2, and this document simply never said so. Echo suppression **drops** the watcher event for Serat's own write. If the index were fed only by the watcher, a note saved in Serat would therefore never be indexed at all, and the mechanism that exists to prevent duplicated work would instead prevent all of it. Echo suppression is only coherent if the write path has already submitted the rows itself — which §3.2's ordering now *enforces* rather than assumes, since nothing is recorded, and so nothing can be suppressed, until a submit has succeeded. F-03 did not find a missing 100ms; it found a missing paragraph.

##### A third caller shares this code, and its budget is the one that breaks

**The table above has two rows; `serat-index`'s row-writing path has three callers.** The save path and the watcher path each write one note's rows under a budget measured in milliseconds. The full rebuild drives the same `apply` over 20,000 notes under NFR-PRF-04's 30 seconds. So **a per-row cost added there is paid once by a save and about forty thousand times by a rebuild**, and it is the ratio rather than the cost that decides whether it matters. This section's own framing — two paths, two budgets — is what let that go unsaid.

**F-371 is the case, and it was measured rather than argued.** Task #13's link resolution is correct for the path it targets and lands on the shared one: a 20k rebuild gained roughly 40,000 `UPDATE`s, each carrying a correlated subquery whose `OR`-chain over `n.path` and `file_name` no index can serve. `prf04-full-rebuild --iterations 1` on the standing 20k fixture burned **1,269 seconds of CPU without producing a result**, against 30 seconds budgeted and the 21–27 seconds the same job took after F-324. That is a lower bound rather than a number: the process was still running when it was killed.

**Why this is a property of the design and not an incident to record elsewhere: no test could have caught it.** `serat-index` went from 76 passing tests to 77, the new test is mutation-verified, and nothing in the suite exercises more than a handful of notes. **A per-row cost is invisible in every test that writes one row, by construction.** Only the budget job sees it, which is what C-06 and the working agreement's rule — a change that adds an index write path adds or updates the benchmark that measures it — exist for.

**The rule this leaves, and it has to be wider than “work” suggests.** When adding work to the row-writing path, say which of the three callers pays it and how many times. **“Work” here is not only statements.** A gate of the form `if !bulk_load` reaches anything *apply* issues and nothing the database does on its behalf: an index maintained on every insert is a standing obligation SQLite discharges per row, and no branch inside `apply` can decline it. F-373 is that case, found after the paragraphs above were written and against the rule they state. Once #13's `bulk_load` gate was in place — correctly, and it is what makes the rebuild finish at all — a controlled A/B on one loaded machine still showed the writer 11.5 seconds slower on a 20k rebuild, 49,809ms against 61,335ms, with parse unchanged at 30,021 against 30,430ms. **Those are contended figures and should not be compared against attested ones:** task #83 later measured parse at a 3332ms median on the same fixture with no competing build, so the ~30s readings above are roughly 9x the quiet cost. The *delta* stands — both halves ran under the same contention, which is what makes a same-session A/B admissible at all — but the absolutes are a property of that afternoon. What remained was `ix_links_unresolved` being maintained across roughly 220,367 link inserts.

**The remedy's shape already exists in this codebase and should be reached for rather than invented.** `begin_bulk_load` reads the `blocks` triggers out of `sqlite_master`, drops them, and `end_bulk_load` recreates them (`crates/serat-index/src/writer.rs`). Per-row obligations a rebuild cannot afford belong inside that bracket, for the same reason the triggers do. Which of them belongs there is the implementer's call and not this document's.

**`schema/001_init.sql` predicted this before the code existed**, in the comment explaining why `ix_links_unresolved` was *absent*: “an index P0 never reads would still cost P0's rebuild benchmark (NFR-PRF-04) to build.” F-373 draws the generalisation and it is worth carrying here, because it governs every design file this repository keeps: **a comment explaining why something is absent is load-bearing in a way that a comment explaining what is present is not — the only person who ever reads it is the one about to remove it, and they are reading it having already decided the absence should end.** If the answer is *the rebuild, once per note*, then the budget job is not optional and reasoning about the per-row cost is not sufficient. F-371 also records what makes the remedy scoping rather than reverting: the rebuild already runs one full `resolve_links` pass at the end, which its author kept deliberately, so the per-row work is **redundant** during a rebuild rather than merely expensive.

##### 3.1.1 The save path

Serat knows what it wrote, so it does not wait to be told.

1.  The buffer is written by temp-file-and-rename (§6.1 step 5). The write records nothing: `write_atomic` writes bytes and returns the hash it produced, which is all its name claims.
2.  The file is loaded back through `NoteSource` and its bytes go to the parse pool. **This document said the opposite — *"the ones already in memory, not a re-read of the file"* — until I5 was built, and the code is right.**
3.  The rows go to the index writer on the same channel everything else uses.
4.  **Once that submit has succeeded**, and not before, the hash is recorded for echo suppression. §3.2 sets out why that ordering is the mechanism rather than a detail of it.
5.  `index.changed` is emitted and open views refresh.

Steps 1–4 are one sequence with one owner, and §2.1's ruling on `rebuild` already named it: the orchestration lives in **serat-index**, which reaches the vault and the parser through traits declared in serat-core and links neither crate. The suppressor arrives the same way, as a `&dyn EchoGuard` — a separate one-method trait rather than a fourth method on `NoteSource`, because recording an echo is write-path bookkeeping, and `rebuild`, which cannot produce an echo, must not be handed a method it has no relationship to. `serat_vault::Vault` implements both traits, so the call site passes the same object twice; that is explicit rather than elegant, and the tidier alternative would introduce a type whose only purpose is to hide the thing worth seeing there.

Why the save path re-reads, when it has the bytes in hand. The obvious optimisation is to parse what was just written, and the design asserted it for two revisions on the strength of a 50ms budget. What the implementation showed is that the read buys three things the optimisation would have to reproduce separately. **One entry point indexes a path, whoever asked** — the save path and the watcher path run the same function, so there is one place to get right rather than two that must agree. **A load that fails means the file is gone**, so `Remove` falls out of the same call instead of needing its own signal. And the hash recorded for echo suppression is **the hash of what is actually on disk**, which is the thing the watcher's event will carry.

The cost is a read and a hash inside NFR-PRF-03's window, and it is now **a measurement rather than an argument**: TC-021 times the real save path, and if the read is a material part of the 50ms then passing the bytes is a bounded change to one function. Recorded in §Open design questions rather than ruled, because ruling it from the budget alone is what produced the wrong sentence in the first place. The architect's position before I5 was that the source should not be passed to the save path at all; the implementation is a better answer than that ruling, and the ruling is withdrawn rather than deferred.

The watcher sees the event and, if step 4 has already happened, drops it (§3.2) — which is the whole of the interaction between the two paths, and is an optimisation rather than a load-bearing step. If the watcher gets there first it matches nothing, the event proceeds, and the note is indexed a second time from disk: wasteful and correct. Nothing is coalesced because there is nothing to coalesce: one save is one write is one set of rows.

Two consequences, stated because each looks like a bug otherwise. If another process modifies the file between our rename and our load, we index **their** bytes and record **their** hash as our echo — so the watcher event carrying those bytes is suppressed, correctly, because the index already holds exactly what is on disk. Under the in-memory variant the same race indexes *our* bytes and the watcher then corrects it, one reindex later. **Re-reading is the better half of that trade and it was not the reason the read was chosen**, which is worth saying so nobody removes it for performance without noticing what else goes. And the save path must never call `flush()`: waiting for the writer to drain would put the index back on the keystroke path, which design goal 2 forbids. The UI reports "saved" when the rename completes and learns "indexed" from `index.changed`. Those are two different facts and the interface should not pretend otherwise (§2.2).

##### What NFR-PRF-03's benchmark may enter, and the one branch it cannot see

`bench/budget/src/subject.rs`'s `SAVE_ENTRY_POINT` specifies `IndexHandle::apply()` submitted through `writer().flush()` returning, against **serat-index directly** — it never enters serat-app, so it skips `AppState::write_file`, the optimistic lock, `write_atomic`, the re-read, and #90's handle slot. NFR-PRF-03 governs *"a note saved through **Serat's own write path**"*, and the section below asks *"does the save path's re-read cost enough of NFR-PRF-03 to be worth removing"* against a harness that does not perform the write. Those read differently, and the difference has been ruled rather than left for whoever builds the job.

**The interval is right and does not change.** The clock runs from `apply()` submitted to `flush()` returning, and it should not be extended backwards over `write_atomic`. NFR-PRF-03's acceptance criterion starts its clock where the save *completes* — *"when it completes, then the index reflects it within 50 ms"* — and §3.1.1's closing paragraph is the reason that is right rather than convenient: **"saved" and "indexed" are two different facts and the interface does not pretend otherwise.** The UI reports the first when the rename returns and learns the second from `index.changed`. A benchmark that merged them would put a filesystem rename inside an indexing budget and would report one number for two facts this design spends a paragraph separating.

**`flush()` is the measurer's barrier and is forbidden in the product, and that asymmetry has to travel with the figure.** §3.1.1: *the save path must never call `flush()`* — waiting for the writer to drain would put the index back on the keystroke path, which design goal 2 forbids. The harness calls it because a *measurer* needs a barrier a *product* may not have. `SAVE_ENTRY_POINT` states this already and states it correctly. It is restated here because the benchmark is the most-copied code in the repository, and the copy that matters is the one into `write_file`.

**What the harness actually misses is not a span. It is a branch.** Checked against the landed code rather than against F-382's description of it, now that #90 has merged: `AppState::submit_to_index` (`crates/serat-app/src/state.rs`) has **three** silent exits, one more than F-382 named, and the extra one is not a slot problem at all.

1. No vault open — `None => return`.
2. The slot holds no handle yet. F-382's case, and itself three indistinguishable situations: the legitimate startup window before the open check finishes, an opener whose `into_handle` was never overridden (silent by construction — the trait default returns `None`), and an open that failed.
3. **`let _ = handle.apply(...)` — the error is swallowed**, including a refusal under backpressure.

In all three `write_file` returns `Ok` having indexed nothing, and **the harness cannot observe any of them, because it never touches the slot** — it holds an `IndexHandle` it opened itself. So the defect is not that the benchmark measures the wrong interval; it is that it cannot see the branches that would make the interval irrelevant. That is F-19 exactly: a job posting a fast p95 for saves that never reached the index.

**Landed, task #90 at `779ca8b`: all three are now counted.** `AppState` holds `save_handle_missing`, `save_writer_refused` and `save_submitted`, and `save_path_outcomes()` returns a snapshot to be diffed around a run. The `Err` from `apply` is still not propagated to `write_file`'s caller — correctly, for the reason below — but it is counted, which is the difference between *swallowed* and *unobserved*. Exits 1 and 2 share one counter, and that is right rather than a shortcut: `write_file` takes `self.vault()?` before it writes, so a save reaching `submit_to_index` with no vault open is only possible if the vault closed underneath it, and a counter that separated a race that narrow from the legitimate startup window would be finer than any decision anyone makes from it.

**What has not landed is reachability, and it is the half the dependency rule makes awkward.** `save_path_outcomes()` is a method on `AppState`, in serat-app, which `bench/budget` may not link. There is no IPC command carrying it and no trace field either, so **the counters exist in the program and no budget job can read them.** Observable is not yet reported, and the paragraphs below are what closes that.

**Each of the three is the right behaviour, and that is what makes this hard to see.** `write_file`'s contract answers for the vault write and not for whether the index heard about it, so a write that reached disk must never be reported as failed because the writer was busy — and the degradation is genuinely safe rather than merely tolerated: nothing recorded an echo, so the watcher's own event indexes the file a moment later (§3.2). **The failure is therefore a latency failure and not a correctness one** — the note arrives on FR-VLT-04's 500 ms path instead of NFR-PRF-03's 50 ms one. Which is precisely why it can run for a whole benchmark without anything going wrong that a reader would notice. `submit_to_index`'s doc comment stated all of this honestly before the counters existed, and **documented is not observable** — a budget cannot assert a comment. That is the sentence #90 answered.

**The obvious fix is unavailable and the dependency rule is why.** `bench/budget` links serat-core, serat-index, serat-parse and serat-vault; **nothing depends on serat-app and nothing may** (§2.1). The harness therefore cannot call `write_file`, and no amount of wanting a more honest benchmark changes that. This is a constraint on the answer rather than an excuse for the gap.

**So the gap is closed in the product, and the budget reaches it the way it already reaches the application.** The first half is done: the degraded path is **observable** — F-19's remedy, which F-382 names — and the outcome is counted rather than absorbed into an `Ok`. **The second half is not:** a counter no measuring job can read is observable to a debugger and not to a budget. `prf01-cold-start` already drives the real binary and reads what it writes, without linking it; the same mechanism serves here, and a subprocess is not a dependency. **The assertion is `submitted == saves attempted`, and that is sharper than "the degraded count is zero".** It checks the denominator rather than a symptom: a p95 over 1,000 saves means nothing unless 1,000 saves reached the index, and the equality says so in one comparison against a number the harness already knows. A figure taken without it is an instrument reading.

**The breakdown then says what to fix, and the two counters want different treatments.** `handle_missing` is a **hard zero** — those saves never reached the index at all, so any non-zero value invalidates the run. `writer_refused` is ADR-11's sanctioned backpressure, which is legitimate behaviour rather than a defect, and **a non-zero value there at NFR-PRF-03's own load is a finding about the queue rather than about the harness**: it would mean the budget's stated workload is enough to make the writer refuse, which is worth knowing on its own.

**An earlier version of this paragraph asked for all three exits to be counted separately, and that was based on a wrong model of the first one.** It assumed exit 1 could mean "the harness never opened a vault" — a setup error worth naming. It cannot: `write_file` takes `self.vault()?` before it writes, so that case returns `VaultNotFound` from the command and the harness sees an error loudly, by a better mechanism than a counter. What remains of exit 1 is a vault closed mid-save, which no decision distinguishes from the startup window. Hence the two share a counter (F-391), and the correction is recorded because the first version had already been sent to whoever was going to build it.

**The number has landed, and it arrives with the census this subsection spent its length asking for.** NFR-PRF-03 is **4.306 ms p95 over 1,000 saves against a 50 ms budget** — min 1.481, mean 3.002, max 8.218 — with **1,000 attempted, 1,000 submitted, 0 writer-refused, 0 handle-missing** (task #95, `docs/05-testing/reports/nfr-prf-03-save-to-index.md`; a replication immediately after read 4.4 ms with an identical census, and the pre-registered run is the one of record so that designating one cannot be read as choosing the better). **The census is the part this section cares about**: the two counters it demanded are the difference between 4.3 ms of real saves and 4.3 ms of saves that never reached the index, and `handle_missing` at zero is the hard-zero condition met rather than assumed.

**Two bounds travel with it, and the second is newly load-bearing.** `gate_eligible: false` — the scanner is off (RISK-012) — and the headroom is 11.6x, which makes a breach unlikely and not *measured*, a distinction this project has paid for. And **NFR-PRF-03 governs a warm, already-open vault**: the premise was implicit until F-450, which found a benchmark saving into a cold vault's first rebuild and reading design-correct behaviour as a 1000/1000 defect rate. Pre-warming is what makes the requirement's own words true rather than a slackening of them. **That clause belongs in the PRD beside NFR-PRF-01's bounds and is product-analyst's to write**; it is recorded here because the design is what makes it true.

**What this run is not, stated because a zero invites exactly one wrong inference.** The `0 handle-missing` is **not** a measurement of F-382's window. On the tree it was taken against it cannot distinguish the pre-warm working from #119's ordering fix from both, and **F-462's 35.4 µs median / 191 µs figure remains the measurement of record** for that window. Nothing in this document quotes a figure for it, and this paragraph exists so that nothing starts quoting this one (test-engineer, unprompted, with the number they had just produced).

**The number also closes an open design question, and it is worth saying what it closes and what it does not.** §Open design questions asked whether the save path's re-read costs enough of NFR-PRF-03 to be worth removing — *"this asks only whether the 50 ms budget can afford it"*. **It can, with room that is not close: the whole interval, re-read included, is 4.306 ms p95, 8.6% of the budget.** So the bounded change that would pass the bytes alongside the path is **not warranted**, and the single-entry-point property it would have cost is kept for free rather than defended. **What the number does not do is measure the re-read's own share** — nothing has, and nothing needs to while the total sits an order of magnitude under the limit. If the budget ever tightens or the interval grows, the question re-opens with its answer already scoped: it is a question about one component's share, not about the sum. Recorded here rather than left in the table, on the same principle as question 1 — an answered question belongs beside the design it settles.

**Until that exists, the label travels with the number.** Every NFR-PRF-03 figure states that it measures **serat-index's orchestration and not serat-app's routing** — the same discipline as `gate_eligible: false`, and for the same reason: a bound that is not written down is a bound the next reader will not apply.

**The figures.** After user_version 7's foreign-key indexes (§4.4; task #51 on `task/p1-51-schema-v7-fk-indexes` at `01e4aeb`, in review), consecutive saves of the 679-in-degree `areas/Retention 2.md` on the 20k vault measured as follows, over 50 iterations per run on the 4-core box:

| Note | p50 | p95 | max |
|---|---|---|---|
| `areas/Retention 2.md` (679 inbound links) | 35–43 ms | **58.7–60.4 ms** | 374–508 ms |
| Root `index.md` (301 namesakes) | 28–31 ms | 34–56 ms | (not reported) |

The fix was 15× (from 924 ms p95), but the hub-note p95 still misses NFR-PRF-03's 50 ms. The median is inside the budget. The miss comes from a few saves that take ten times the median. **No remedy is chosen until the outliers are attributed**, because each plausible cause has a different remedy, and one of them is not a defect at all.

**(b) What NFR-PRF-03 measures. It is already ruled, and the hub case is added as a scenario.**

- **The interval** is the one ruled above: `apply()` submitted to `flush()` returning, which covers the re-read, the parse, the submission, the index transaction and its commit. It is not the index transaction alone. A user waits on everything up to the commit, and a budget on the transaction alone would let parse or checkpoint time escape it.
- **The statistic** is the PRD's: p95 over 1,000 saves, with the census. **Fifty iterations cannot carry a p95.** With n = 50, the p95 is roughly the third-worst sample, so three outliers decide it. The figures above are diagnostic, not a measurement of NFR-PRF-03.
- **The hub note is a gating scenario, and the worst scenario gates**, as with NFR-PRF-02. The worst realistic case is a user typing in a hub note, so it is measured as consecutive saves of the highest in-degree note, 1,000 of them. #95's mixed workload stays as the second scenario.
- **Cadence.** Each save is submitted only after the previous `flush()` returns, plus a fixed gap that every run line records. The gap is **1 s, the editor's save debounce** (ADR-0016: a save is triggered by 1 s of idle). Back-to-back saves with no gap measure a backlog no user can produce, and they also leave the writer no idle moment, which hides or causes exactly the background work suspected below.
- **This states the workload more precisely, and the target does not move.** product-analyst records the scenario in NFR-PRF-03's acceptance note.

**(a) What the outliers most plausibly are, in order, and the one measurement that tells them apart.**

**#53 attributed them** (task #53, `task/p1-53-save-tail-attribution` at `ecaeee0`). The run was 1,000 hub saves at the 1 s cadence, on a box under about 93% foreign CPU load on average. So its absolute p95 of 98 ms is not a gate figure, but the structure it shows is. **The order below was the prediction. The corrections after each item are what was measured.**

1. **A WAL auto-checkpoint.** This was the leading suspect. `wal_autocheckpoint` is SQLite's default of 1,000 pages, and nothing in serat-index sets it. A hub save rewrites the note's blocks and FTS rows and updates 679 inbound links twice (set to NULL, then resolved again), so a few saves fill 1,000 pages. The commit that crosses the threshold then runs the checkpoint on the writer thread, inside the clock. Under `synchronous = NORMAL`, that checkpoint is also the only place the save path fsyncs. Its signature is periodic: the outliers recur every *k* saves, *k* is about the same each time, and the WAL frame count resets at each one.
   **Measured: it is the dominant cause, and it is not a tail. It happens on every second hub save.** A hub save writes about 682 WAL frames, so the 1,000-frame threshold is crossed on exactly every second save (500 of 1,000). Each checkpoint moves about 1,365 frames, at p50 31.6 ms and p95 81.9 ms inside the hook. Saves that carried one had a p50 of 58 ms, against 31 ms for those that did not. Of the 442 saves over 50 ms, 379 carried a checkpoint. With `wal_autocheckpoint = 0` and a `PASSIVE` checkpoint between saves, outside the clock, **the p50 fell from 46.6 ms to 21.0 ms.**
2. **An FTS5 merge.** Each save adds a small FTS5 segment. `automerge` does bounded work per write, but when a level reaches `crisismerge` (16 segments) a whole level is merged in one go. Its signature is also periodic, with a longer period than the checkpoint's, and the time is spent inside the transaction rather than at commit.
   **Measured: the spikes are real (40–330 ms), but they sit in `COMMIT`, not inside the transaction.** That is FTS5 flushing its pending terms and doing its merge work at commit, so the predicted signature was wrong about where the time is. Setting `automerge = 0` cut `COMMIT`'s p95 from 27.6 ms to 6.5 ms, but merging did not stop, because the crisis merge still runs. **This cause is not cleanly isolated.**
3. **The machine.** The 4-core box runs other agents' cargo builds. #95's figure of record was taken with `concurrent_build_processes: 0` attested, and these were not. Its signature is aperiodic outliers that move between runs and correlate with load.
   **Measured: load amplifies the tail but does not explain the periodic part.** Maxima of 400–1,269 ms occurred only at about 99% foreign CPU, and the correlation between load and save time is r = 0.10.
4. **The bench process itself.** That means allocation, first-touch page faults and the harness's own clock reads. This is least likely at 374–508 ms. Its signature is outliers in the first iterations only.

**The measurement rust-core-dev takes (task #51 or a sibling).** It is one instrumented run, then a bisection only if that run is ambiguous.

- **Per save, record the phases separately:** read, parse, the statements inside the transaction, `COMMIT`, and anything after the commit. **Also record whether a checkpoint ran and how many WAL frames it moved:** a `wal_hook` callback (`sqlite3_wal_hook`) on the writer connection reports the frame count at every commit. Also record the FTS5 segment count before and after (`fts5vocab`, or the `%_data` structure record), and the machine's load average and concurrent build processes per run, as `env.rs` already does.
- **Use 1,000 iterations at the cadence above**, on the hub note and on root `index.md`.
- **Read the outliers against the phases.** If the time is in `COMMIT` and coincides with a checkpoint, the cause is 1. If it is inside the transaction and coincides with a fall in the segment count, the cause is 2. If it is in no particular phase and correlates with load, the cause is 3.
- **Bisect only if that is ambiguous.** Make one run with `PRAGMA wal_autocheckpoint = 0` and an explicit `wal_checkpoint(PASSIVE)` between saves, outside the clock. Make another with `INSERT INTO blocks_fts(blocks_fts, rank) VALUES('automerge', 0)`. These are diagnostic settings only, and neither ships as found.
- **`sqlite3_status` is not the first tool.** Its counters are process-wide memory and page-cache figures, and they attribute none of the four causes. The phase timings and the WAL hook do.

**The remedies, ruled on #53's attribution.** These remedies were set out before the run, and the attribution confirms them, except for the FTS5 part.

- **(a) The checkpointer lands, and it is a new row in §2.2.** Checkpoints leave the save path entirely:
  1. **The writer sets `PRAGMA wal_autocheckpoint = 0` when it opens.** Without that, the writer still checkpoints every second hub save, whatever the checkpointer does. Readers commit nothing, so they never auto-checkpoint, and the setting matters only on the writer.
  2. **The checkpointer is its own connection on its own thread**, opened read-write, used only for `PRAGMA wal_checkpoint(PASSIVE)`. It writes no rows, so ADR-0001's single writer of content holds. A `PASSIVE` checkpoint takes no lock that the writer or a reader waits on.
  3. **The idle gate: 250 ms after the writer's last commit.** That is below the 1 s save cadence. A hub save is about 20–40 ms, so the gate is reached between every pair of saves, and the WAL is checkpointed in the idle part of each second.
  4. **The size bound: 4,000 frames (16 MiB at 4 KiB pages).** If writes never pause for 250 ms, the checkpointer runs when the WAL passes this, still on its own thread. It is set well above one hub save (682 frames), so that during normal typing the idle gate does the work and the bound only acts under sustained writes, such as a rebuild or a git checkout. `journal_size_limit` is set to the same 16 MiB, so a WAL that grew under load shrinks after the next reset.
     - **The size bound only triggers another `PASSIVE`, and a `PASSIVE` cannot pass a pinned reader** (code-reviewer-2). A connection holding an open read transaction pins the WAL at its snapshot. That could be a leaked or unreset statement on the long-lived search connection. Every checkpoint then stops at that point, and the WAL grows without limit. A blocking `RESTART` or `TRUNCATE` as the routine fallback would be wrong, because it holds the writer while it waits.
     - **So the WAL is bounded by an invariant, not by the checkpointer: no reader connection holds a read transaction outside one read call.** Every read statement is stepped to completion or reset before the call returns, and the search connection is no exception. Per-call readers are dropped on return. The search connection is the one that lives long enough to leak.
     - **It is tested.** serat-index asserts `sqlite3_txn_state(db, NULL) == SQLITE_TXN_NONE` (rusqlite's `Connection::transaction_state`) on the search connection and on a reader after every read type: R1, R1 + R3, R2, R3 and R5. That includes a search that returns `Superseded`, an interrupted statement, and a read that returned an error.
     - **The hard bound is 64 MiB of WAL.** Past it, the WAL is presumed pinned. The checkpointer then reports **"index WAL pinned"** as a status fact carrying the WAL's size, as one more optional `IndexStatus` field, which the implementing task adds to `contracts/ipc.rs` with architect. It never reports it as an error. **Then, during idle time only (250 ms after the writer's last commit), it may try one `wal_checkpoint(RESTART)` with a busy timeout of at most 50 ms**, so the most a save arriving at that moment can wait is 50 ms. If that fails, the status fact stays and nothing else is tried. A pinned WAL is a defect against the invariant, and the status fact is how it becomes visible rather than becoming disk use nobody can explain.
  5. **The rebuild keeps its own `wal_checkpoint(TRUNCATE)` at the end** (§4.4). The size bound means the checkpointer also runs during a bulk load. NFR-PRF-04 is therefore re-measured with the checkpointer running, and it must stay under 30 s.
  6. **Durability does not change.** Under `synchronous = NORMAL` in WAL mode, a commit does not fsync, and it did not before this change either. **The index side of the save path now does no fsync**, because the auto-checkpoint was its only one. The note side still fsyncs: `write_atomic` fsyncs the temporary file and the directory in serat-vault (#48). A power loss can therefore lose the last few index commits, but never the note's bytes. That exposure is not new, since commits were never fsynced.
     - **What recovers a lost index commit on the next open, stated precisely, because it is narrower than "reconcile".** The catch-up walk (ADR-0015 §2) runs after every open, and it compares **paths** with the index: a path that is in one but not the other is submitted on ADR-0011's bulk side. That recovers a lost create or delete. **It does not recover a lost content update of a path the index already holds**, because it compares no content.
     - **The rule.** After an unclean shutdown, which is the same signal that already schedules the background `quick_check` (§3.4), the catch-up walk also compares each file's mtime with `notes.mtime`. It puts the files that differ through the hash gate (§3.1.2 step 3), and submits the ones whose hash differs on the bulk side. A clean shutdown checkpoints and closes the WAL, so it skips this. The cost is one `stat` per file, which the walk already makes, plus a hash of only the files whose mtime moved.
     - **Until that lands, a power loss can leave a note's index row stale until the note next changes.** That is recorded in the remedy task (#56) as its own item rather than assumed covered.
- **The checkpointer does not run FTS5 merges.** A `merge` command writes to `blocks_fts`, so running it on the checkpointer's connection would make it a second writer, against ADR-0001. If FTS5 work is moved, it is moved as an idle work item on the writer's own thread: a bounded `INSERT INTO blocks_fts(blocks_fts, rank) VALUES('merge', N)`, issued after the same 250 ms of idle time. **It is not ruled in yet**, because #53 did not isolate the cause. The remedy task re-runs the attribution with the checkpointer in place. If `COMMIT`'s p95 is still a material share of the 50 ms, it comes back here with that table, and the idle merge (with `automerge` left as it is) is the remedy decided then. Neither `automerge = 0` nor a raised `crisismerge` ships on the strength of a cut that did not stop merging.
- **(c) The gate re-run is on an attested quiet machine.** `concurrent_build_processes: 0` and foreign CPU load are recorded in the run line, as in #95's figure of record. A run on a loaded box is diagnostic and is never quoted as NFR-PRF-03's number, because load roughly doubled the maxima in #53.
- **Bench process.** No finding. #53's outliers were not concentrated in the first iterations.
- **If the hub save still misses 50 ms at p95 on a quiet machine** with the checkpointer in place, the remaining cost is the hub save's own work. That comes back here with the phase table, as a ruling on that work, for example on the 679 two-step updates of inbound links. It does not come back as a re-baseline. The 21.0 ms p50 without checkpoints, measured even under load, suggests it will not need to.

##### 3.1.2 The watcher path

1.  The watcher coalesces events per path over a 150ms window. Editors that save via temp-and-rename emit several events per save; they collapse to one.
2.  The work queue deduplicates by path and is bounded, and when it is full the watcher's push is refused, a rescan flag latches, and the consumer reconciles by walking. A git checkout touching 4,000 files enqueues 4,000 entries, not 4,000 parses. The bulk producer is never dropped this way — see ADR-11, which is about which producer may be dropped rather than about whether dropping is allowed.
3.  The hash check reads the file and compares blake3 against notes.hash. Sync tools touch mtime constantly without changing content; this discards those for the cost of a hash.
4.  Changed files are parsed — sequentially today (§2.2), and the parser is pure: bytes in, structures out, no I/O, so it would parallelise across cores without coordination if a measurement asks for it. A file the parser cannot read is **indexed as a bare row, never skipped** — see below.
5.  Rows go to the index writer on a channel. It batches within a transaction, and runs ANALYZE when a batch touched more than 5% of notes. A full rebuild takes the bulk path instead — triggers dropped, FTS index built once at the end, triggers restored from their own definitions; see §4.4.
6.  The event bus emits index.changed, throttled to ten per second, and open views invalidate the rows they hold.

##### A symlink is not a vault file

One rule with two enforcement points, written here rather than inside either of them, because **each is a reason the other exists and neither implementation says so.**

- **The walk never sees one.** It `lstat`s every entry and skips any symlink, so a linked file is never enumerated and never indexed. **For most of P0 nothing asserted this**, and deleting the skip left `cargo test -p serat-vault` fully green at 64 passed — `walk_cost` included — so the rule below about who will be looking at what was a warning with no test behind it. **Task #62 closed that**: two tests now pin it, ungated rather than `#[cfg(unix)]`, and both were mutation-verified — deleting the skip fails them with the leaked path named. 66 pass. threat-model.md's T-07 carries the accounting.
- **The read path must refuse one for the same reason**, and it enforces the rule at `Vault::resolve` rather than at each caller — the narrowest point every filesystem access in serat-vault passes through, so `read` and `write_atomic` inherit it and a future caller cannot forget it. Components are checked from the root down with `symlink_metadata`, never `metadata`, which would follow the very thing being checked for. **Deliberately not a `canonicalize`:** that does more syscalls and returns a path which then has to be compared back against the root, which is a second mechanism for the same question.

  Both halves are now enforced; the read half arrived second, and T-07 in the threat model carries the history of the gap between them. A security document should carry the gap, a design document should carry the rule.

**Two separate things rest on the first half, and whoever changes it will be looking at only one of them.**

FR-VLT-01's fix rests on it. The walk is missed by 4.0x at 20,000 notes and 6.5x at 50,000, and the fix replaces canonicalising every entry with **stripping the root prefix lexically** — about 2.0s down to about 50ms. A lexical strip and a canonicalisation agree on every path *only while no symlink is enumerated*: canonicalising `vault/link.md` resolves to wherever the link points and is rejected if that is outside the root, while stripping the prefix off it yields a perfectly ordinary-looking `link.md`. **So the performance fix is sound because of a security property, and neither file mentions the other.**

T-07 rests on the second half, for the reason the threat model gives.

**What the read half costs, and the limit on that figure.** The containment check is O(path depth) `lstat` calls and sits on `NoteSource::load`, so a rebuild pays it once per file: **43,587 `lstat` calls over the 20,000-note vault, 1.08–1.37 s across four release runs**, 54–68 µs a file. A range rather than a point, because four runs do not support a point.

**Treat that as a floor, not an estimate.** F-203 established on this machine that an isolated walk benchmark understates — **1.85 s isolated against 3.1 s in situ, a 1.7x gap** — because one measures the crate on an idle machine and the other measures it against the disk and cores the rest of the application is using. The same instrument shape produced this number, and a rebuild runs a parse phase and a writer thread alongside it. TC-020's `read_hash` phase is where the in-situ figure will appear.

**The priority ruling does not depend on the number** — design goal 1 outranks 2 and 4, and narrowing the guard to the IPC path would restore the asymmetry it exists to remove. **The number matters for something else.** f12's strip removes about 1.42 s of a 1.85 s walk; this guard adds about as much back to the same rebuild, on the read side. They are different paths and different requirements — f12 is what makes FR-VLT-01 achievable and the guard does not touch it — but **for NFR-PRF-04 both land inside the same 30 s, and each was justified on its own.** That is F-212's argument arriving as arithmetic rather than as a caution, and it is the reason to hold the two figures side by side when NFR-PRF-04 is first measured.

**The likely way to break it is a tidy-looking fix.** The read path must refuse symlinks (task #20), and the obvious way to make the two paths agree is to unify them. Unifying them by making the walk **follow** links satisfies the containment requirement and silently invalidates the lexical strip. Unify them the other way — both refuse — and one sentence covers both, which is checkable in a way *"the walk skips them and the reader canonicalises"* is not.

##### A note that cannot be parsed is still a note

F-67, and the answer is design goal 5 applied to Markdown rather than to binaries. When the parser cannot produce structures — in practice a `.md` file that is not valid UTF-8, since CommonMark has no parse failures and broken frontmatter already indexes the note and records the problem — the note is indexed as a **bare row**: path, hash, mtime, size and a title from the filename, with no blocks, no fields and no links.

It is not skipped. Skipping is the option that looks safe and is not: the file exists, so an application that indexes nothing for it is one where the note is missing from the tree and from path search, links to it read as unresolved, and there is no surface anywhere that says why. The vault would contain a file the product denies. §7.3 already settles the identical question for a binary with no extractor — it "still indexes with its sidecar and stays typed, linkable and queryable", and only full-text over its contents is unavailable — and there is no reason for a Markdown file to be treated worse than a PDF nobody can read.

Nothing records the failure in the index, deliberately. It needs no column, because it is not a fact about the note that the index has to remember: anyone can re-derive it in the time it takes to read the file. P1's validation surface lists such notes by computing them, and a column would be a schema change — a rebuild, under ADR-02 — bought for a consumer that does not exist.

#### 3.2 Echo suppression

Serat's own writes produce filesystem events indistinguishable from anyone else's. When a save has been submitted to the index, the save path records the hash it wrote in a set; when the watcher sees an event whose post-hash is in that set, it removes the entry and drops the event. The set is keyed by hash rather than by path, so a genuine external edit that happens to produce the same bytes is indistinguishable from our own — and is correctly treated as a no-op, because it is one. Keying by path would instead drop a real edit that landed in the same window, which is a lost update.

##### The set is bounded by size, not by time

It held entries for two seconds until F-252. **The failure that number produces is silent and safe, which is why it would never have been reported:** the watcher's event reaches the suppressor only after the 150ms coalescing window *and* whatever backlog the work queue is carrying, and at ADR-11's own worked shape — 20,200 paths against a capacity of 8,192 — a path waits far longer than two seconds. Every entry has expired by the time its event arrives, nothing is suppressed, and every save Serat makes is reindexed from disk by the watcher. The index stays correct. The work merely doubles, indefinitely, with no symptom.

Two seconds was chosen for a reason that F-224 has since made void, and the module implementing it already contradicted itself on the point. The stated purpose was that a hash must not linger and swallow an unrelated edit made a minute later — but under late recording an entry exists **only after a submit has succeeded**, so at the moment it is created the index provably holds those bytes, and suppressing a later event carrying the same bytes is correct however late it arrives. That is the paragraph above, and it is now a guarantee rather than a usual case. **The correctness argument for expiring an entry does not survive the ordering change, and nobody re-read it when the ordering changed** — which is the same lapse F-226 corrected in this document, found in a doc comment instead.

What is left for the bound to do is stop entries leaking when a watcher event never arrives at all — dropped under overflow, or lost to the platform. That is a memory concern, and **a duration bounds memory only if you already know how long the consumer takes, while a capacity bounds it unconditionally.** So the set holds a fixed number of entries and evicts the oldest when full. Suppression then works whenever the consumer catches up within that many saves, whatever the wall clock says, and the memory cost is a number rather than an assumption.

The capacity is **at least the work queue's**, because the queue is what delays the consumer; sizing the set against the thing that causes the delay is the only figure here that is derived rather than guessed. Thirty-two bytes a hash makes ADR-11's 8,192 about a quarter of a megabyte, which is not a budget anyone needs to discuss.

One thing this deliberately does not do is keep a long duration as a second bound behind the capacity. That would reintroduce exactly the coupling being removed, at a length nobody could justify by measurement either — and an optimisation that can silently stop applying should not depend on a number that can be quietly wrong.

##### The hash is recorded after the submit, not before the write

This document said *before writing* until F-219..F-224, and the earlier wording had a stated and correct reason: an entry recorded too late suppresses nothing. That reason is true, and it is not the deciding one, because the two orderings do not fail comparably.

**Record early and the failure is lossy.** The entry exists from before the rename, so the watcher's event matches it whether or not any submit ever stands behind it. Anything that stops the save path short of the submit — a refusal under backpressure, or a caller that simply writes and returns — leaves the event dropped and the note indexed by nobody. This was not a corner case. `write_atomic` recorded the hash itself, and its only production caller wrote, re-read the file for its mtime, and returned without ever submitting, so record-early failed lossy on *every* call rather than on an interleaving.

**Record late and the failure is redundant.** The entry exists only once rows are with the writer. A refused submit records nothing, so the watcher's event proceeds normally and indexes the note from disk. A watcher that wins the race — its event handled after the rename and before the recording — matches nothing, and the note is indexed a second time. `upsert_note` is delete-then-insert by path, so the second pass produces the rows the first one did: idempotent, wasteful, correct.

That asymmetry is the argument, and it is why late recording **removes** the race rather than narrowing it. Record-late has no interleaving that loses a note, only interleavings that cost one redundant index. It also restores the mechanism to its proper rank: echo suppression is an optimisation — its job is to avoid indexing the same bytes twice — and an ordering that let it decide whether a note is indexed *at all* had given an optimisation an authority its failure mode could not carry. Under late recording the worst it can do is fail to save work, which is what an optimisation is allowed to do.

Three things follow, each of which the earlier wording implied the opposite of.

- **There is no `forget_echo`.** An intermediate version of this fix restored the watcher's event by removing the entry when a submit was refused. With nothing recorded before the submit there is nothing to forget — and the interleaving that version did not cover, where the watcher's event is handled first and consumes the entry before the refusal is seen, cannot arise.
- **`write_atomic` records nothing.** It writes bytes and returns their hash. The recording belongs to whoever owns the save sequence, which §3.1.1 puts in serat-index; it does not belong to the function that moves the bytes, whose name promises a write and should mean one.
- **A write with no submit behind it is watcher-indexed, not suppressed.** That is the correct outcome, and it changes which budget the write is measured against: FR-VLT-04's 500ms, not NFR-PRF-03's 50ms. A save benchmarked against a shell that has no direct submit will therefore produce a several-hundred-millisecond figure and read as NFR-PRF-03 missed by an order of magnitude, having in fact measured the watcher path working exactly as designed. Anything timing a save must record which of §3.1's two paths the write actually took; a save timing with no path on it is not a save number.

One limit, stated as reasoned rather than measured. A redundant index is read-only with respect to the vault, so it cannot move a byte range or change a hash under P2's patcher and cannot interact with the stale-hash guard of §6.1. What it can do is consume writer-queue depth at the moment the patcher wants to submit. That is a backpressure question, ADR-11's subject rather than this section's, and nothing has measured it.

#### 3.3 Reconciling an external change into an open buffer

This is FR-VLT-05, and the naive implementation — replace the document — destroys cursor position and the undo stack, which is the difference between a tool you can leave open beside Claude Code and one you cannot.

On an external change to an open file, the core diffs old bytes against new and emits a minimal edit script as ExternalChange.edits. CodeMirror applies it as a transaction, which maps the selection and the undo history through the change automatically. The whole-document path exists only as a fallback when the diff exceeds half the file, where preserving position is meaningless anyway.

The case that decides the design

You are editing line 400. Claude Code rewrites the frontmatter at line 3. With a document replacement you lose your place and your undo history; with an edit script you do not notice. Every reconciliation decision follows from wanting the second outcome.

##### What P1 specifies (ADR-0016)

The paragraphs above assumed a buffer with no unsaved changes. ADR-0016 covers the case they skip, and it also fixes the save direction, because both directions have to use the same coordinates:

- **Coordinates.** `{line, col}` in the base document. Lines split on `\r\n`, `\n` and a lone `\r`, exactly as CodeMirror splits them. `col` is in UTF-16 code units. One pure function in serat-vault maps a position to a byte offset.
- **The edit script** is computed in Rust by serat-vault: a line diff with character refinement, under a 50 ms deadline. serat-app emits it for any open note whose disk hash differs from the buffer's base hash, so an echo of Serat's own save is a no-op without any echo logic.
- **Applying it.** A clean buffer takes it as a transaction with `addToHistory(false)`: the cursor and undo are mapped through it, and undo never reverts someone else's edit. A dirty buffer whose changes are disjoint from the external ones takes the mapped edits and stays dirty. Overlapping changes are a **conflict**: nothing is applied, and a non-modal notice offers *Keep mine* / *Take theirs* (undoable) / *Compare*. Nothing is lost silently.
- **Saves are patch sets against the base hash, never whole documents.** CodeMirror joins lines with `\n`, so a whole-document save would rewrite every line ending of a CRLF or mixed-ending note — the re-serialisation C-04 forbids. `write_file` now only creates notes.

#### 3.4 Cold start, and how a broken index is noticed

Two requirements meet on this path and pull in opposite directions. NFR-PRF-01 wants an interactive window in 400ms and a usable vault in one second at 20,000 notes. NFR-REL-02 wants a corrupt index detected and rebuilt with no user action beyond restarting. Every thorough way of detecting corruption costs more than the entire window budget, so the two are reconciled by deciding what is checked *when*, rather than by checking less.

##### The critical path does not scale with the vault

| Phase                            | On the main thread                                                                                                                | In parallel                                                                                                                              | Budget                       |
|----------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------|------------------------------|
| Process start → window painted   | Read the settings TOML, create the Tauri window, load the embedded webview bundle, paint the shell with `IndexState::Opening`.        | Index actor opens the index and runs the open check below (about 5–8ms, task #68). Vault thread registers the watcher — and stops there.                    | 400ms (NFR-PRF-01)         |
| Window painted → vault usable    | Render the file tree and restore the last-open buffer as they arrive; the editor accepts keystrokes from the first paint. The restored buffer does not gate `t_usable`; the tree's *delivery* does — see the marker table.             | The walk starts and streams paths; the index answers the first queries; the last-open file is read from disk.                                 | 1s total (NFR-PRF-01)      |
| After usable                     | Nothing.                                                                                                                             | Catch-up reconciliation, `ANALYZE` if a rebuild ran, background `quick_check` if the last session ended badly, extraction and embedding (P2/P4). | Unbudgeted; must not stall the UI. |

The load-bearing property is in the first row: **nothing on the critical path is proportional to the size of the vault**. The main thread never opens the index — the index actor does, on its own thread (ADR-01) — and no IPC command blocks on it. The shell paints with whatever state the actor has published, which is why 400ms is achievable at 20,000 notes and still achievable at 50,000.

Two ordering rules that are correctness, not optimisation:

- **The watcher is registered before the walk starts.** A file changed during the walk then produces an event rather than being silently missed, and the walk reconciles anything that changed before the watcher existed. The gap between the two is now larger, because the walk waits for the first paint — which costs nothing, precisely because the watcher is already up and covering it.
- **The walk does not start until the window has painted.** It is the largest single cost at startup, and nothing before the first paint needs it. Leaving it running against the paint made `t_visible` depend on the size of the vault through CPU and I/O contention rather than through anything the main thread did — which is not a budget anyone can hold. This is safe only once the walk is not itself absurd: F-12 measured it at about 2.0 seconds on the 20,000-note vault because it canonicalises every entry, against about 50ms with the prefix stripped lexically. On the no-index path, where the tree comes from the walk, deferring it by one paint eats into FR-VLT-01's two seconds, so this ordering and that fix are one decision and not two.

  The deferral stays, and the reasons are not the ones first given for it. Both the size of the effect and the shape of the argument have been corrected by measurement.

  **The effect was overstated by about ten times.** The figures that first justified this — 808ms at two notes against 1410ms at twenty thousand, returning to 821ms with the walk delayed — came from blocked sampling, the design later shown incapable of deciding this class of question. Paired and interleaved, 40 pairs on the same binary, the walk's cost to the paint at 20,000 notes is a median of **+54ms**, not 600.

  **What survives is in the tail, and the budget is a p95.** The median moves 54ms; the p95 moves 271ms, a ratio of 1.20 — sitting exactly on the budget job's tolerance. A budget judged at the 95th percentile is judged on precisely the part the walk damages most, which is a better argument for the deferral than the one about medians it replaces.

  **My projection was wrong, not merely unmeasured.** This paragraph previously argued from arithmetic — a 50ms walk at 20,000 becoming 125ms at 50,000 — and 50,000 has now been run: the effect there is *smaller*, a median of +28ms with a confidence interval including zero. Walk duration and paint delay do not scale together, and the extrapolation had the direction wrong as well as the magnitude.

  **The strongest remaining reason is a case nobody can measure here.** Every cold-start figure this project has produced is a *warm-vault* figure: repeated spawns against one vault leave it in the page cache, so the walk is CPU-bound where a user's would be I/O-bound. Freshly generated vaults are write-cached rather than cold, and dropping the Windows page cache needs privileges this machine does not have. So **NFR-PRF-01 cannot be validated against a cold vault here**, and the case where the walk hurts most is the one case that cannot be tested. Deleting a mitigation on evidence that structurally excludes its worst case is not a decision the evidence supports — which is why the standing offer to delete it if it measured as worthless is withdrawn by the person who made it rather than overruled.

- **The file tree is rendered from the index when it is `Ready`, and from the streaming walk when it is not** — and in both cases it arrives as complete directory listings, root first, on an ordered stream (ADR-0015, §3.5). One query over `notes(path)` returns 20,000 paths in about ten milliseconds; a cold directory walk takes far longer. This is design goal 5 in miniature — with a warm index the tree is instant, without one it degrades to streaming, and neither case blocks.

Deferred deliberately, because none of it is needed to type: the catch-up scan, `ANALYZE`, the FTS integrity check, `quick_check`, extraction and the embedding model, which is never loaded at start.

##### The three marks, defined so they can be measured

A budget that is not defined as two observable events is a number that flatters whoever reports it. NFR-PRF-01 is therefore three marks on one timeline.

| Mark        | Definition                                                                                                                                                  | Why not the cheaper thing                                                                                                                                        |
|-------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `t0`        | Process spawn, taken by the harness from outside the process.                                                                                                | Not `Instant::now()` in `main`. The loader, the DLLs and the webview runtime are real cost the user waits through, and a t0 inside `main` hides exactly the part we do not control. The app also records its own `main` entry, so the pre-`main` gap is visible rather than absorbed. |
| `t_visible` | The first frame the webview actually paints, signalled by the front end from the first `requestAnimationFrame` after the shell mounts.                        | Not window creation. Window creation is much cheaper and would pass 400ms while shipping a blank rectangle. This is test-engineer's trap and they are right about it.                                                                                                              |
| `t_usable`  | The **latest** of: the open check having finished, so the index state is known; the file tree's **first listing (the root)** having been applied and painted by the front end — the mark `tree_first_screen`, from P1, per ADR-0015 §5; P0, with no tree, used `buffer_rendered`, which leaves `t_usable` and stays in the trace as a reported mark; the watcher having settled; and the window having painted. | Not "the index is open". A vault that is usable but unwatched silently misses every edit made in that window, which is a correctness bug dressed as a faster number.                                                                                                              |

The watcher clause is load-bearing and is why it is in the definition rather than in a note. It also fixes an ordering: the watcher is registered before the walk, so nothing that changes during startup is lost. "Settled" rather than "registered", because a watcher that failed to start is a supported outcome — a vault with no watcher is stale, not broken (goal 5) — and the trace records which it was, since a usable figure taken without a watcher is not comparable to one taken with.

"The index state is known" means **any state that is not `Opening`**, and that is not a detail. `Rebuilding` and `Unavailable` settle the term exactly as `Ready` does: the requirement is that the state is known, not that it is good. A shell that waited for `Ready` would hang for the length of a full rebuild — on precisely the vault where the window most needs to be up — and in P0, which never reaches `Ready` at all, it would never report usable at any time. The same applies to the watcher term, where `WatcherFailed` settles it and the trace records which outcome it was.

That imposes one requirement on the index actor, and I6 is where it can be lost: **the actor publishes its classification as soon as the open check produces one, before it starts any rebuild work.** An implementation that publishes nothing until the rebuild completes turns a 5–8ms term into a thirty-second one. Measured on the real shell, the term settles at 78–95ms against 800–970ms to paint — both pre-#98, and the paint figure is superseded by #100's 1575.6 ms p95, which only widens the gap — so it is nowhere near binding — but it is only bounded because the classification is published early, not because the check is fast.

And a precondition must not be derived from a channel that is allowed to drop or coalesce. S1 takes the index term from an observer on the actor's published state rather than from the event sink, because the sink is throttled to ten per second (§3.1 step 6): a `Rebuilding` whose event lost to the throttle would leave the mark waiting for a transition that had already happened. A precondition a throttle can swallow is a precondition in name only, and the failure is invisible — the mark simply never fires and the trace never exists. The general form is worth carrying into P1's views: throttled events are for invalidation, never for establishing that something has occurred.

It cuts the other way too, and the opposite mistake is one line away in any implementation that reuses the emit path for both. **The value must stay readable from a channel that cannot drop.** `index_status()` returns the newest state even when the event announcing it lost to the throttle, which is what makes a late or reloaded subscriber correct rather than merely eventually correct. A poll that throttled the value as well as the notification would be the same defect wearing the opposite hat: the notification may be coalesced freely, the state may not.

Taking the *latest* of the four rather than the last one to be reported is not pedantry, and S1 found out why on its first run. Both marks arrive as IPC round trips, so a fast disk can finish the buffer read before the paint mark's round trip completes; the process then exited with the paint still in flight and wrote no trace at all. Defining usable to include the paint term makes that structural instead of a rule the front end has to remember, and the same reasoning is why a trace whose watcher never settled does not exist rather than existing with a gap.

**A note being open is not one of the four, and the phase table above must not be read as saying it is.** That table's second row says the shell renders the file tree and *restores the last-open buffer as they arrive*, which describes work that **starts** inside this window rather than a precondition that ends it. Read as a precondition it contradicts the four marks, and it was read that way — by the budget harness, which threaded an `open_note` through the cold-start subject and justified it in a comment ("`--exit-after-ready` refuses without one, and rightly: 'vault usable' over a shell that rendered nothing is not the number NFR-PRF-01 is about"). **That comment was reporting the binary rather than interpreting this table, and it was right about it** — see the correction below. **The worry behind that sentence is right and is already answered by two of the four clauses:** the window must have *painted a real frame*, and the file tree must have been *delivered to the front end*. A shell that rendered nothing fails both. What a restored buffer adds beyond that is one note's content, and that is where the argument stops carrying, for three reasons.

- **The requirement is a usable *vault*.** NFR-PRF-01's words are "a fully usable vault within 1 second, at 20,000 notes"; every clause of `t_usable` is a vault-scoped precondition, and a particular note is not one.
- **One note's render cost is constant in the size of the vault.** The whole purpose of this budget is to bound the work that *does* grow with the vault — which is the load-bearing property stated two paragraphs above. Folding in a constant makes the number larger and less informative at the same time, and it is the one addition that cannot fail the way the budget is meant to fail.
- **No requirement covers note-open latency.** NFR-PRF-02 is keystroke-to-paint in a note that is *already* open. A budget for opening one would be a new Must arriving through a bench harness rather than through the PRD, which is the product-analyst's call and not a measurement decision.

**Correction, task #60: this ruling is a change the implementation must make, not a description of one it already has.**

What this paragraph claimed is kept, because how it went wrong is the more useful record. It read: "The implementation already behaves this way, which is worth recording because the harness assumed the opposite. `crates/serat-app/src/cli.rs` refuses `--exit-after-ready` when `--vault` is missing — a cold start with no vault would report a number that measures an empty window — and **not** when `--open` is missing." Every word of that is true of `cli.rs`. **It is false of the program.** `crates/serat-app/src/lib.rs` holds a second enforcement point inside `setup`: under `--exit-after-ready` with no note resolved it stores exit code 2 and exits with "`--exit-after-ready` needs `--open <note.md>`". The requirement lives in two files, this ruling read one of them, and **"does this program require `--open`" is not a question the argument parser can answer alone.**

**The harness author was right, and this section recorded them as mistaken.** The comment quoted two paragraphs above — "`--exit-after-ready` refuses without one, and rightly" — is a correct report of what the binary does, and its justification is a near-quotation of `lib.rs`'s own refusal message rather than a reading of the phase table. The `open_note` in the cold-start subject followed from the product's behaviour, not from an ambiguity in this document. The ambiguity in this document is real and is what the paragraphs above fix — it was simply not what the harness was going on.

**The ruling itself is untouched.** It rests on the three arguments above — the requirement names a usable *vault*, one note's render cost is constant in vault size, and no requirement covers note-open latency — none of which depends on what the binary does today. What changes is its status: `lib.rs`'s refusal now contradicts an accepted design decision, and removing it is task #59 against `serat-app` (F-359). `cli.rs`'s refusal is **not** part of that and stays — `--exit-after-ready` without `--vault` still has nothing to measure.

**One behaviour must survive #59, and it is what makes #59 safe.** `AppState::note_to_open` (`crates/serat-app/src/state.rs`) returns `None` under `--exit-after-ready` with no `--open`, deliberately declining the settings-file fallback so that a budget job cannot start passing on a developer machine that once ran the application interactively while still failing in clean CI (P0 finding F-169). Dropping the refusal *and* letting the fallback supply a note would put the measurement back on per-machine state, which is the one outcome worse than the refusal being there. So `--open` is **session restore for a user, not a readiness precondition for a measurement**, and it stays in the CLI for that reason.


`t_usable` as defined is the warm-index case NFR-PRF-01 names. With no index the file tree comes from the streaming walk instead, and that case is bounded by FR-VLT-01's own two-second criterion, not by this one — a cold vault and a warm vault are different measurements and the gate report must not average them. §3.5 defines FR-VLT-01's interval and marks.

The mechanism is one environment variable, so the harness measures the application rather than itself: with `SERAT_STARTUP_TRACE=<file>` set, `serat-app` writes one line of JSON — `t0_to_main_ms`, `t0_to_visible_ms`, `t0_to_usable_ms` and the index state at `t_usable` — and exits. It exits because a harness that has to kill the process adds its own timing noise to the number it is trying to measure, and `t0` is handed in by the harness so that the pre-`main` cost is inside the number rather than beside it. The same marks are available in a normal session through `IndexStatus.since_process_start_ms` in `contracts/ipc.rs`, reading the same monotonic clock. The trace file is the gate number for P0, because a process that exits at `t_usable` leaves no window in which to observe an event stream; if the two ever disagree, that disagreement is a finding rather than a rounding difference.

##### The split: which term is ours, and which is not (ADR-0014)

The owner ruled on 2026-09-08 that NFR-PRF-01 is re-baselined **with** the webview term rather than by opening C-07, and that **the re-baseline is a split rather than a slackening.** The paragraphs above are the diagnosis; this is the decomposition the new requirement is written against, and ADR-0014 is where the decision, its alternatives and its objections live. What follows is the design record.

**It is a partition, not an attribution.** Every millisecond between `t0` and `t_usable` belongs to exactly one term, and every term is the interval between two marks the application already emits (`crates/serat-app/src/startup.rs`). The terms therefore sum to the mark by construction, with no residual and nothing composed.

| Term | Interval, as fields of the trace | Owner |
|---|---|---|
| `P_load` | `t0` → `t0_to_main_ms` | platform — loader, DLLs, runtime init |
| `S_pre` | `t0_to_main_ms` → `t0_to_state_ready_ms` | **ours** — arguments, settings TOML, `AppState` |
| `P_builder` | `t0_to_state_ready_ms` → `t0_to_runtime_ready_ms` | platform — `tauri::Builder` construction |
| `S_setup` | `t0_to_runtime_ready_ms` → `t0_to_setup_done_ms` | **ours** — event sink, `open_vault`, thread spawns, boot info |
| `P_webview` | `t0_to_setup_done_ms` → `t0_to_window_created_ms` | platform — `WebviewWindowBuilder::build` |
| `S_shell` | `t0_to_window_created_ms` → `t0_to_window_visible_ms` | **ours** — our bundle in their renderer, to the first composited frame |
| `S_settle` | `t0_to_window_visible_ms` → `t0_to_vault_usable_ms` | **ours** — the remaining preconditions of `t_usable` |

**Platform term** `P = P_load + P_builder + P_webview`. **Serat term** `S = S_pre + S_setup + S_shell + S_settle`. `P + S = t_usable`, exactly, on every run — an identity a budget job can assert rather than a claim a reader has to accept. **It could not assert it when this was written**, and the distinction is F-381's: the application stamped all seven marks while `bench/budget/src/trace.rs` parsed four, so the harness could compute three terms and not the Serat term. **Task #106 closed that — all seven marks are required and the identity is asserted — so this paragraph now describes a check that runs.** What the check is worth is smaller than this paragraph originally hoped, and ADR-0014 §Objections carries it: given the other checks the identity is a telescoping sum, true of any seven numbers, so it guards the harness's field-to-term mapping rather than the application's marks. One-line re-check: `grep -n 'fn sum_ms' bench/budget/src/trace.rs`. Time cannot leave the Serat term without arriving in a named platform term at a named mark.

**The attribution rule is one sentence: a term is ours if a change confined to this repository can move it.** Two boundaries follow from it against the easier alternative. `S_shell` is **ours** although it executes inside WebView2's renderer — the renderer is theirs, what it renders is ours — because booking it to the platform would make a front-end regression invisible to the budget. That is the flattering measurement the spike keeps recording: a paint mark wired to window creation, passing 400 ms while shipping a blank rectangle (this section's own `t_visible` definition, and `trace.rs`'s fourth rejection); a `t0` taken inside `main`, undercounting everything the loader did (its first); and a cold start measured against a shell with no editor framework in it, which is the owner's ruling that put S2 back inside the P0 gate. `P_builder` is the **platform's**, with the caveat stated rather than rounded off: `tauri::Builder`'s cost is partly a function of a Serat decision, the size of `generate_handler!` and the plugin set, so it is the one term where a regression of ours could hide in the platform column. It is watched rather than budgeted, and moving materially with command count is the signal to re-book it.

**The Serat term is binding; the platform term is recorded and carries no budget; the total is reported beside both.** Deleting the total would remove the only figure describing what a user actually waits through, and the aspiration it states is not withdrawn — it is marked unmet on WebView2 and handed to P1.

**The Serat term is allocated between two sub-terms, and the allocation lives here rather than in the PRD.** `S_main = S_pre + S_setup` is Rust on the main thread, and is the one term this section can measure cleanly: 5.2 and 5.6 ms across a vault ten thousand times larger, against a p95 of 9.4 and 9.6 — **a central statistic and not a median, because F-455 found this clause and ADR-0014 §Decision 4 both naming one the basis cannot support.** `S_front = S_shell + S_settle` is the front end inside the platform's renderer, ~121 ms at two notes and ~138 ms at twenty thousand *before* task #98 mounts Vue 3 and CodeMirror 6 into it — **both composed from the phase table, and a reading across its columns, so both carry F-452's bound** — **now measured after the mount, at 197.6 ms median and 230.4 ms p95 against `S_main`'s 3.4 and 4.0 (#100). The allocation survives its own test: `S_front` is 98% of the Serat term, so a sum would have hidden the entire front end behind four milliseconds of quiet Rust.** One binding number in the requirement, because a requirement with three numbers in it is one nobody quotes correctly; the allocation here and in the budget jobs, because a single sum lets a hundred-millisecond front-end regression hide behind five milliseconds of quiet Rust.

**The partition cannot catch a misplaced mark, and this is the one thing not to hope about it (F-386).** `Startup::vault_usable()` takes the maximum of four marks, and `painted` is not the one that settles it — `painted → usable` is the smallest term there is, **1.1 ms median / 1.7 ms p95** (#100, attested; the 4.7–7.5 ms this sentence used to quote read the phase table's last row across its columns, which F-452 rules inadmissible). So a paint mark taken Δ early shrinks `S_shell` by Δ, grows `S_settle` by exactly Δ, leaves `t_usable` untouched, and every sum stays invariant. **The identity says nothing about whether a mark fired at the right event — and it constrains less than that sentence first claimed.** With all seven marks required and monotonicity checked separately (task #106), the identity is a *telescoping sum of consecutive differences*, equal to the last minus the first for any seven numbers at all, ordered or not; it cannot fail on real data. What it guards is the harness's own field-to-term mapping, proven by breaking that mapping deliberately (test-engineer, correcting this section). What the split buys instead is a *diagnostic*: `S_settle` goes from an attested 1.1 / 1.7 ms to roughly the window-build-to-paint interval — ~100 ms in F-86 pre-#98, 196.1 / 229.2 ms in #100 after it — which is an anomaly of orders of magnitude in the smallest term in the table. **The 13–21× first written here is withdrawn rather than recomputed**, because it divided one unattested figure by another and the diagnostic does not need a multiplier and is invisible to a harness that does not compute it. It is not a rejection, and bounding `S_settle` to make it one would be wrong — that term grows legitimately in P1 with a real file tree, and on Linux with one inotify watch per directory.

**Making `S_shell` binding raises the stakes on the paint mark, and the guard it needed did not exist when this split was written (F-377).** The only check was `the_placeholder_bundle_exists_and_carries_the_two_marks`, which asserts that `mark_first_paint`, `mark_vault_usable` and `requestAnimationFrame` appear *somewhere* in the bundle and nothing about where; a mark hoisted to script start survives it, and the harness's 5 ms paint-gap floor does not see that mutation either, because it is sized for a Rust-side rewire to window creation. **A mark taken at script start does not merely flatter the total — it empties `S_shell`**, which is the term this split hands the front end to own.

**What now stands, and what still does not.** #108 emits post-composite evidence from the Vue mount (`app/src/startup.ts`), #112 validates it in `crates/serat-app` (`startup::validate_paint_evidence`), and #114 waits on the `PerformanceObserver` rather than sampling for the entry. That test moved to a shallow bundle check and the mechanism guard moved beside the source. **Two of the table's five properties are unenforced and a third is enforced as a diagnostic rather than a rejection — ADR-0014's table is where they are listed**: the static check that `app/index.html` stays contentless (nothing), whether the frames were scheduled after our mount (nothing, and nothing can), and the paint value being the browser's entry, which F-406 demoted to a printed diagnostic because at a 200 ms tolerance it could not fire. **This sentence said *one* until product-analyst checked the table against the tree**, which undercounted by naming the row nobody had built and skipping the row that was built and then demoted — the more misleading of the two, because a demotion leaves a function with the right name in place. **Two others have since landed and this section said otherwise until each was corrected.** #113 moved the forwarding into `AppState` with a test that the call site passes the real evidence rather than a constant, and code-reviewer verified it by mutation before it merged — discarding the three arguments and fabricating evidence turns it red, as does forwarding the real paint entry while hardcoding the frame pair.

**Every claim in this subsection about what the front end does is a claim about the last vite build, not about the source it names (F-470).** The paragraph above cites `app/src/startup.ts`; the running binary does not read it. `tauri.conf.json` sets `frontendDist: "webview"` and declares no `beforeBuildCommand`, so `crates/serat-app/webview/` — three committed build artifacts — is compiled into `serat.exe`, and `cargo build` never invokes vite. **The gap is not theoretical and was measured rather than inferred**: a stub that never calls `mark_first_paint`, launched without a rebuild, produced exit 0, a complete trace and `paint_evidence_ms` 352.0 — indistinguishable from an honest run; the same stub after `cargo build --release` gave exit 2 and no trace. **So a front-end mutation needs `npm ci`, `npm run build` and `cargo build --release`, in that order**, and any check that changed front-end source without all three tested nothing while reporting cleanly. The remedy is a positive control that costs one rebuild — apply the stub, rebuild, confirm exit 2, restore — and it belongs in front of any run that claims to exercise these mechanisms. **This is a basis clause and it is ADR-0014 §Decision 6's sixth**, added there in the same commit, because a claim whose basis is unstated on this axis is the class that document exists to catch. One-line re-check: `grep -n 'frontendDist' crates/serat-app/tauri.conf.json`.

**And the frame-precedes-paint condition (F-406) is no longer a rejection at all — task #406 landed the conversion ADR-0014 pre-committed, and it is a diagnostic rather than an absent check.** `frame_precedes_paint_diagnostic` in `crates/serat-app/src/startup.rs` returns `Option<String>`: `Some` at a gap past the 200 ms tolerance, `None` inside it, `eprintln!`'d at the call site rather than returned as `Err`. The prior state — the tree rejecting on a condition F-406 showed cannot fire, since the honest renderer-to-compositor gap sits at 51–65 ms and the attack band is bounded above by the paint entry itself — read as coverage and was worse than an absent check; that is what made this the tenth guard-that-cannot-fail on record. The diagnostic itself does not repeat that shape: code-reviewer found by deletion mutation that the first version could be deleted with the workspace staying green (F-424, a twelfth instance one level down), so both arms — the gap past tolerance, and the honest gap inside it — are pinned directly against the function's return value rather than observed only as a side effect. One-line re-check: `grep 'fn frame_precedes_paint_diagnostic' crates/serat-app/src/startup.rs`.

**The convention this replaces has two halves, worth keeping as a record of how the sentence above stayed honest while it was still provisional.** A claim about tree state should carry **the commit it was true at**, which makes it honest — it can then only become history, never false. And it should carry **the one-line re-check**, which makes it useful: the commit alone tells a reader the claim may be stale without telling them how to find out, and a reader who cannot cheaply check will assume rather than look. The prior wording anchored itself to `35a4cb2` and to the branch `task/406-frame-precedes-paint-diagnostic` rather than to the branch's state, because a branch reference stays checkable after it merges and "not merged" does not. That branch has now merged with the pinning fix folded in, which is why this paragraph describes the landed state directly rather than pointing at it.

**F-406's arithmetic rested on three samples from one sitting, and now has a second reading behind it.** The real binary emits `raf2_ms` since #115: **155.9 ms against `paint_evidence_ms` 208.0, a 52.1 ms gap** — a different session, vault and build, landing inside the same 51–65 ms band. That is the corroboration the ruling was taken without, and where it came from is what makes it independent: **a smoke test of #115's wiring, not a measurement run at all** — no shared machine state, no shared build, no shared intent with the sitting F-406 was ruled in. **And the harness cannot help with any of them**: `paint_evidence_ms` and `window_visible` are co-emitted by one IPC call, so their difference is invariant under exactly the mutation that would matter, which is why #106's third goal is closed as not achievable rather than built (F-411, ADR-0014).

**`Trace::serat_main_thread_ms()` computes `S_main`, and `S_main` is not the Serat term.** It is the sub-term, and the distinction is the one most likely to be lost, because the ruling's own grounds quote it — *"Serat's own main-thread work is 4.7–5.6 ms"* — as the measure of what Serat costs. It is: on the main thread, before the first paint, excluding the loader, `tauri::Builder` and the webview build. It excludes `S_front` entirely. A budget set at that figure would leave the editor outside the budget on the day it arrives, which is the one outcome a split is supposed to prevent.

**How the number gets chosen, since this section does not choose it.** Let `s95` be the Serat term's p95 from task #100, taken after #98. The budget is **≤ 400 ms** — the original 400 governed a window containing the platform term too, so applying it to a strictly smaller quantity can never be a slackening, which makes 400 the ceiling and never the number — and **≥ `s95` × 1.3**, with the measured spread stated, because a tolerance sized against the effect and never against the noise is a job that goes red for no reason and is disabled by the third person it wakes. **If those two bound an empty interval, the split has failed to produce a binding budget and that is the finding**, escalated rather than repaired by widening the ceiling.

**The rule has since been applied and the interval is not empty.** #100 measured `s95` at **233.8 ms**, so the floor is 233.8 x 1.3 = **304 ms** against a ceiling of 400: **[304, 400], 96 ms of room.** The escalation clause is therefore not reached. **The number inside that interval is product-analyst's to choose and is not set here** — 350 ms was recommended to task #104 as the midpoint with the spread stated, and a recommendation is what it stays. The interval is this section's; the number is not.

**Six clauses of basis travel with every figure above, and all six are conditions under which the number is better than a user's.** *(Five when this paragraph was written; the sixth is F-470's, below.)* Warm vault, and no cold-vault figure is obtainable on this machine (F-154). Scanner disabled, `gate_eligible: false` (RISK-012) — which bites less here than on NFR-PRF-04, because this critical path does no per-file work by design, but still bites on `P_load` and on everything after `t_usable`. **One platform: WebView2, with WKWebView and WebKitGTK unmeasured (F-96)** — the partition and the attribution rule are platform-independent, every figure is Windows. One machine, which is part of the measurement (F-327), so figures carry `cpu_load_percent` and `concurrent_build_processes` or they are not comparable with each other. And which build: everything quoted above predates #98, #100's figures are the post-#98 ones, and the two must never appear in one table. **And which *front-end* build, which is the sixth and is set out below** — a claim about front-end behaviour cites `app/src/*` while the binary embeds `crates/serat-app/webview/`, so it describes the last vite build rather than the source it names (F-470).

The first three push the number the same way. **A re-baseline attested on this basis is a bounded claim and is written as one.** It is the bound on which NFR-PRF-01 was deliberately not re-baselined earlier; the ruling is to proceed, so the bound is recorded rather than resolved.

##### What P0 hands P1

**On WebView2 the 400 ms first-paint budget is unreachable whatever Serat does.** The platform term is **1117 ms median and 1687 ms p95** at twenty thousand notes with no code of ours in it (#100, attested; the ~966 ms this paragraph used to quote came from the unreconstructable phase table) — 2.8× the entire budget at the median and 4.2× at p95 — and no allocation of the Serat term touches that. Stated here rather than left in an ADR because a deferral outlives the people who took it.

P0 cannot distinguish the two futures, and both are P1's. If WKWebView and WebKitGTK carry a platform term of the same order, **the requirement was wrong rather than the design** — F-96's predicted shape — and this split is the permanent fix. If they do not, the budget is reachable on two platforms of three and Windows is the outlier, which is a WebView2 question before it is anything else: whether the term responds to a fixed-version runtime, to bundle size, to navigation ordering, or to nothing at all. **Only if it responds to nothing does it become a C-07 question — and then it is one**, because a platform on which a Must-priority requirement is structurally unmeetable is a constraint being tested rather than a budget being missed. What settles it is running this same seven-term partition on the other two webviews; it is in §Open design questions until someone has.

##### Which mark is constant in the size of the vault, and which is not

This distinction decides what a budget job may assert, so it is stated rather than left to be inferred.

`t_visible` is **constant in the work the main thread performs**, which is the claim the design can actually keep. Nothing the main thread does before the first paint is a function of note count: it reads a settings file of a few kilobytes, creates a window, loads a bundle compiled into the binary, and paints with `IndexState::Opening`. It does not wait on the index actor, enumerate anything, or read a directory.

It is not constant in *wall clock*, and the difference matters to whoever writes the budget job. `t_visible` is measured from `t0`, so it includes contention from whatever runs in parallel — and on a two-to-four core CI runner with a virus scanner enabled, scheduler and I/O contention move that number on their own. Deferring the walk past the paint removes the largest such source deliberately, but it does not remove them all.

So the assertion a budget job may make is that the mark does not grow **beyond a stated tolerance** between a 20,000-note vault and a 50,000-note one; 20% is the agreed figure. A path that had become proportional to vault size would show around 2.5x, so the tolerance has better than a factor of ten of headroom against the effect it exists to catch. **Which mark that assertion is made against was reopened by task #118 and is ruled at the end of this subsection** — it was `t_visible` when this paragraph was written, and the paragraphs between here and there are the evidence the ruling rests on.

That headroom is about the effect, and it says nothing about the noise — which is the half that decides whether the job survives, and the half the first draft of this paragraph ignored. Measured after the walk fix: two back-to-back batches of twenty spawns gave `t_visible` p95 of 1146ms at two notes against 940ms at twenty thousand — the larger vault came out faster. Run-to-run variation is therefore about 20%, the same size as the threshold, and a tolerance chosen against the effect and never against the noise is a job that goes red for no reason and is disabled by the third person it wakes.

The claim about **main-thread work** is a different matter and is now measured directly rather than inferred from wall clock: 5.2ms against 5.6ms across a vault ten thousand times larger. That is the one term in the table where the property can be checked cleanly, because it is the only one not dominated by a platform cost that moves with the weather, and it holds there.

**That claim is weaker than it reads, and the reason is the same one this subsection uses two paragraphs on.** The 5.2/5.6 pair is a column-to-column reading of the phase table above, and that table's two columns are a **blocked** comparison — two vaults, not interleaved, on a machine whose within-arm spread this subsection measures at about five times the effect being tested. Blocked sampling is exactly what is discredited below for the wall-clock version of the same claim, and it was applied forward only: the main-thread version was never re-run under a design that could decide it. The observed difference is +7.7% against a 20% tolerance, so nothing here contradicts the claim; what is missing is a design under which it could have. **The scale-check ruling at the end of this subsection is what closes it** — moving the check's subject to the Serat term puts `S_main` inside an interleaved, paired comparison for the first time. Until that runs, this is a bound (the difference is small relative to the term) and not a demonstration (that there is no growth).

**What this does not do is leave the design claim unsupported, and the distinction matters to anyone auditing what F-452 reaches.** The claim two paragraphs above — nothing the main thread does before the first paint is a function of note count — is argued from what that code *does*, item by item: a settings file of a few kilobytes, a window, a bundle compiled into the binary, a paint against `IndexState::Opening`, and no wait on the index actor, no enumeration, no directory read. That argument stands on its own and F-452 does not touch it. What the finding removes is the *corroboration* — the design keeps its reason and loses its only measurement, which is the weaker position of the two and is worth saying rather than leaving a reader to infer that the claim itself is in doubt.

The wall-clock claim is what the noise defeats. The wall-clock claim is decidable, and it is decided — but only under a sampling design that can see it. Measured as **30 interleaved pairs** at two notes and twenty thousand, alternating which arm spawns first: the paired difference has a 95% confidence interval of **[-123, +45]ms** against the budget job's tolerance of +20%, which is 180ms. The interval excludes the tolerance, so the claim holds. It is not the stronger claim that there is no effect at all — the interval does not exclude a small one, and nothing in the design needs it to.

The supportable form is therefore: **wall clock to first paint does not grow with vault size beyond the budget's tolerance.**

An earlier draft of this paragraph said the claim was unfalsifiable *at this iteration count*, which was wrong in an instructive way. The obstacle was never the count; it was blocked sampling — all twenty spawns of one arm, then all twenty of the other — which lets machine drift settle on one arm and be read as an effect. That is how the twenty-thousand-note vault came out *faster*. Within-arm spread is about 830ms, five times the effect being tested, so no number of blocked samples decides this and thirty interleaved pairs do. This section named interleaving as the fix two paragraphs above and then mis-attributed the cause to the sample size, which is the kind of thing that survives because both halves read plausibly on their own.

Hence the third rule this section has had to learn, after *name the basis* and *measure, do not compose*: **a negative result names its design, not just its basis.** "Not decidable" without "under blocked sampling at n=20" attached reads as a fact about the system rather than about the method, and it is the form of claim least likely to be challenged, because it sounds like caution.

And a fourth, which cost this section its largest number: **when you invalidate a method, re-run what it produced.** Blocked sampling was discredited here and then applied forward only — the walk's 600ms cost had already been banked from a blocked run, and it survived a day after the design behind it was known to be unsound. Conclusions a broken method has already delivered are harder to find than the ones it is about to, because they have stopped looking like open questions.

Four rules in one section is not a method anyone has earned the right to claim. The same rule was broken four times here and recovered four times because someone else re-opened it, which is a property of having a reviewer and a register rather than of having a discipline. The narrower claim is the one worth carrying: **a document that accumulates measured claims needs an owner for retiring them.** Every one of the four survived not by being defended but by nobody going back to it.

The tolerance is therefore not the whole instrument, and widening it is the wrong repair, because it trades away the detection it was sized for. Two things fix the measurement instead. **Interleave the two vault sizes within one batch** rather than running them as separate batches, so machine drift lands on both arms equally rather than being read as an effect — the 940ms-at-20k result is what drift looks like when it is free to masquerade. And **take enough iterations for the statistic to settle**, or compare medians, since a p95 over twenty samples is an estimator noisier than the thing it is estimating.

The miss itself is not in doubt and needs none of this care: 2.4 to 2.9 times over a 400ms budget survives any amount of noise. It is only the proportionality signal that the instrument has to be good enough to see.

##### Ruling (task #118): the scale check keeps its job and changes its subject

Task #118 demotes `PRF01_WINDOW_VISIBLE` and `PRF01_VAULT_USABLE` from CI gates to reported figures, because PRD v1.2 gates only the Serat term (F-443, F-407). That leaves this subsection's proportionality check as the only surviving assertion on `window_visible_ms`, and the question — mine to answer, and answered here rather than in a message — is whether it moves to the Serat-term job. **It is two questions, and they get different answers: the *subject* moves to the Serat term; the *job* stays in `prf01-cold-start`.**

**The subject moves, on five grounds, and the first is the one that would still hold if the noise were zero.** *Attribution.* The defect this check exists to catch is a critical-path step whose cost is proportional to note count, and only a change confined to this repository can introduce one — which is, word for word, ADR-0014 §Decision 2's test for what is ours. Asserting on the aggregate is asserting mostly on a term no change of ours can move. *Sensitivity.* At #100's attested p95s the aggregate mark is 1575.6 ms and the Serat term is 233.8 ms, so the same regression is 6.7 times smaller as a fraction of the aggregate; at the 20% tolerance in force, the aggregate cannot see a vault-proportional step under about **315 ms**, where the Serat term catches one at about **47 ms**. The "factor of ten of headroom" claimed earlier in this subsection was computed when the mark being read was dominated by the path being caught — a 2.0 s walk — and it does not survive a mark whose platform share is about six times its Serat share (#100 medians, each reduced from its own series rather than composed: 1116.7 ms against 201.1 ms). *Noise.* F-407 measured the aggregate moving ~19% between attested batches against ~8% for the Serat term, and `judge_scale` asserts on each arm's p95, so batch-level movement lands directly on the comparison; interleaving cancels drift within a pair, not the estimator noise of a 20-sample p95. A threshold the size of its own noise cannot decide a pass, which is #118's own reason for existing, and it applies to a ratio exactly as it applies to a budget. *Coverage gained.* `S_settle` is where a regression that made the shell wait for the index to be *good* rather than *known* would land, and that wait **is** proportional to vault size — F-450 records the design that forbids it and why. On the aggregate that signal is diluted by the same 6.7. *Consistency.* Leaving the assertion on `window_visible_ms` would re-introduce F-443 in a narrower form: CI enforcing a series the requirement says is not enforced.

**What does not move: the aggregate ratio stays measured and printed, unasserted.** One channel of vault-size dependence does not land in any Serat term. This subsection records that an undeferred walk made `t_visible` grow with the vault "through CPU and I/O contention rather than through anything the main thread did", and contention of that kind lands mostly in `P_webview`, which `S` excludes by construction. So the 20k-vs-50k ratio of both aggregates is reported beside the verdict and gates nothing — #118's own principle, keep the figure and remove only the assertion, applied to the check as well as to the two budgets.

**The job stays, and not for reasons of naming.** `prf01-serat-term` is defined by a property that hosting this check would destroy: it is a *second reduction of one batch of traces, not a second measurement* (#107, F-446). The scale check is a second measurement — two vaults, interleaved spawn by spawn, its own vault guards (F-401), and the 50,000-note fixture. Folding it in would make the one NFR-PRF-01 figure the PRD gates depend on generating and verifying a 98 MiB vault, and would roughly double the runtime of the job most likely to be run on every change. So **`prf01-serat-term` asserts the level of `S` and `prf01-cold-start` asserts its shape across vault size**; neither substitutes for the other. The scale check is not a `Budget` and never appears in `P0_BUDGETS`, so #118 removing two entries from that list does not remove it — which is precisely why it needed a ruling rather than following along.

**The tolerance stays at 20% and its basis changes, which has to be said or the number looks unexamined.** 20% was sized against the *effect* (a proportional path shows ~2.5x) and never against the noise of the series it was asserted on — this subsection's own recorded mistake, one paragraph up. Against `S`'s ~8% cross-batch movement it has roughly 2.5x of headroom over the noise, and the same better-than-tenfold headroom under the effect that the paragraph above computes. **No batch has yet been taken on this subject under the interleaved design**, so that headroom is inferred from F-407 rather than measured: the first run under the new subject reports `S`'s observed spread beside the verdict, and if the spread is not comfortably inside the tolerance, that is the finding and it is escalated rather than repaired by widening — ADR-0014 §Decision 5's floor rule, applied to a ratio instead of to a budget.

**One precondition, which the current subject does not have and this one does.** `S_settle` is inside the compared quantity, so both arms must enter with the same index state and the run must record which. A `.serat/` present on the 20k arm and absent on the 50k arm measures fixture preparation rather than code, and against a cold 50,000-note vault the first spawn starts a rebuild that outlives the process it was spawned in (F-450). The existing `ColdStartVaultGuard` equalises cleanup and not starting state.

**Anchor and re-check.** As of `e9212e6` the check reads `trace.window_visible_ms`, and the quantity this ruling moves it to is already on the same trace — `StartupTrace::terms()` in `bench/budget/src/trace.rs`, whose `Terms::serat_term_ms()` is ADR-0014 §Decision 3's binding sum, landed by #106 — so the change is the body of one closure and not a new measurement. The one-line re-check, which stays useful after the change lands because it names the line rather than the state: `grep -n 'map(|trace| trace\.' bench/budget/src/lib.rs`.

`t_usable` is **not** constant, and asserting that it is would eventually fail for a legitimate reason. Two of its three preconditions grow with the vault. The file tree is one query returning every path, so it grows linearly in note count — cheaply, but it grows. And watcher registration grows in the number of *directories* on Linux, where inotify takes one watch per directory, while it is a single call on Windows and macOS. So `t_usable` is bounded and sub-linear rather than flat, and the way to hold it is the absolute budget NFR-PRF-01 states, measured at 20,000 notes with the 50,000 figure recorded beside it — not a growth ratio.

The recovery journal of §10.1 is read after `t_usable`, not before. Its cost is proportional to the number of unsaved buffers rather than to the size of the vault, so it would not breach either budget; it is deferred because nothing about it is needed in order to type.

This enforces the table above rather than adding to it.** `crates/serat-index/src/schema.rs` ran it inside `inspect`, mapping a non-`ok` result to `UnusableReason::Corrupt` — candidate 1 above, rejected here at 1310ms against NFR-PRF-01's 400ms window, and not one of the six steps below. The line predates the measurement: rust-core-dev wrote it in I4's first half, when `inspect` had no caller and there was nothing on the other side of the scale. **A correctness-completeness choice made with nothing to weigh against is the right choice at the time, and becomes the wrong one when a number arrives.**

**The grounds are C-06 and C-02, deliberately not the goal ranking.** The ranking was offered — goal 2 over goal 3 — and it is declined here, because a cold-start window is not a keystroke and a ruling should not lean on a clause that does not quite fit. What carries it instead: C-06 makes NFR-PRF-01 binding, and C-02 makes the index disposable, so what this check uniquely catches degrades to wrong query results until a rebuild and never to a lost byte. **Design goal 1 is untouched precisely because the index is not the vault.** A 3× budget breach on every cold start does not buy its way past that.

**The objection, in the words it was raised in, because it is a confirmation with a reservation attached and the reservation is right.** rust-core-dev holds that the original reasoning was sound as far as it went: `integrity_check` is the general catch-all for page and btree-level corruption, and `CountMismatch` is its complement for the one thing it structurally cannot see — a torn transaction, where the file is perfectly sound and semantically wrong. The two cover different failure classes and neither substitutes for the other. Their recommendation was to move the coverage “off the critical path entirely — an explicit ‘verify index’ maintenance action, or a background check after the window that NFR-PRF-01 governs has already closed — not something every open pays for whether or not anything is wrong.”

**What the removal does not pay for, stated rather than rounded off.** Page-level damage in `blocks_fts`, in the indexes, and in pages nothing else reads becomes uncovered at open. This section already anticipated that: the lazy `IndexFault` path is named below as mandatory regardless, on the strength of a 4KB mid-file overwrite that passes all six stamp steps and is caught only by `quick_check`, at 1150ms. And the onward home just proposed is the same one candidate 2's verdict already names — which task #58's correction directly above has marked *(planned)*, because neither the background check nor the on-demand path exists. **So the honest state after this ruling is one named future home, still empty, now owed two checks instead of one.**

No ADR: the decision this would record is already in the table above with its measurements, and accepting the residual is cheap to reverse — adding a background check later costs nothing that removing this now spends. The code change was to travel on `task/i6-open-or-rebuild`, where `inspect_for` lived with its tests. **That is no longer the route:** I6 has since landed on main (F-366), by cherry-pick, and the branch is deleted — so `inspect_for` and its 305 lines of tests are here, and the removal is an ordinary change to `schema.rs` covered by those tests in place. The reasoning that chose the route is unaffected; only the route is. **Landed at `56c8dc4`, as exactly that ordinary change:** `integrity_check` is off both `inspect` and `inspect_for`, and the open check is now the six stamp steps alone.

**Measured, task #68: the shipping path costs roughly 5–8ms, not the 2.4ms the table used to carry.** That older figure predated I6 and did not include step 5's `vault_root` read, which `inspect_for` performs as its own statement; this one is `open_or_rebuild` itself, timed on the same 20k fixture and the same live index the other four candidates were measured against, warm OS cache. Five runs: 4.7, 4.9, 5.9, 6.6, 7.0ms — a range, not a point (F-138), and still two orders of magnitude under the rejected checks. **Reproduced independently at merge on a different machine state: 7.15ms**, just outside the original five, which is why the figure above is written as a band rather than as that band's endpoints (F-327: the machine is part of the measurement). The four rebuild-triggering states (`Absent`, `SchemaChanged`, `Interrupted`, `VaultMoved`) were measured too, at the check alone rather than through a full rebuild: all four resolved in single-digit milliseconds — 0.1–4.1ms across two independent runs, `Absent` fastest and `SchemaChanged` slowest — confirming "fails early" with a number rather than assuming it. The test guards them at 300ms rather than at the observed figure, deliberately: a tight wall-clock assertion inside `cargo test` fails under load and tells you about the machine rather than the code (task #44). **So the headroom question the residual above turns on is now answerable: NFR-PRF-01's 400ms window has roughly 393–395ms left after the open check, which is the number a background or on-demand `quick_check` (1150ms, rejected above) would have to fit inside — and does not, on its own, without moving off this window entirely.** That placement decision is not made here; this only supplies the number it would be made against.

The stamp is the open check. In order, and stopping at the first failure:

1. `.serat/index.db` absent → rebuild, reason `NoIndex`.
2. Opening it fails, or any statement below returns `SQLITE_CORRUPT` or `SQLITE_NOTADB` → rebuild, reason `Corrupt`.
3. `PRAGMA user_version` differs from the version this build writes → rebuild, reason `IndexVersion`. This is the whole of ADR-02's upgrade path.

    That stamp covers more than the schema, and the name it had invited the opposite reading. An index is wrong if the DDL changed *or* if the indexer now extracts something different from input that has not changed — a parser recognising an inline field it used to ignore, a block-kind mapping that stops dropping HTML, a different tokenizer. Both make the stored rows disagree with what the current code would produce; neither is visible to any other step of the check, because the schema matches and the vault matches and the row count is whatever the old code wrote. So the constant is `INDEX_VERSION`, bumped in the commit that changes either, and the option of a second constant for the derivation layer was declined: it would carry the same discipline and the same absence of any test that could enforce it, while adding one more thing to forget, and both cases cost the user the same single rebuild. The single number looked insufficient because of its name, and a name is cheaper to fix than a mechanism is to add (F-134).

    The reason the *user* is shown is renamed on that argument and no other. `SchemaChanged` was the constant's old name one layer down: it tells someone their schema changed when what moved may have been the parser, and since this enum is what the front end switches on, a wrong name here becomes a wrong sentence on screen. A **second** reason for the derivation case was considered and declined. The check cannot draw the distinction — one number cannot say which of the two things moved — and the user does not need it, because *"this index was built by a different version of Serat; rebuilding it"* is the same sentence in both cases. The distinction that does matter, *rebuilding because the indexer changed* versus *rebuilding because your index is damaged*, is `IndexVersion` against `Corrupt`, and the enum already drew it (F-175).
4. `index_meta` is missing or `state <> 'ready'` → rebuild, reason `Interrupted`; the previous build did not commit.
5. `index_meta.vault_root` is not the canonical root being opened → **report it, then ask the index whether it describes this tree, and adopt or rebuild on *that* finding** (ruling below, task #120, as corrected by its objection). A path comparison never triggers a rebuild.
6. `count(*) FROM notes` differs from `index_meta.note_count` → rebuild, reason `Corrupt`. This is why the schema requires the count to be updated in the same transaction as any change to the row count: a lag between them is indistinguishable from damage, and must be.

##### Ruling (task #120): what `index_meta.vault_root` is for, and what it may cost

F-459 found that identity is compared as a path *string*, so a mapped drive, a junction, a UNC form, a differently-cased root or a trailing separator each read as a different vault and buy a full rebuild — measured at **28.6 s on the 20,200-note fixture** with no index for its duration (F-458). Three repairs were on the table: canonicalise before recording, canonicalise at comparison, or record an identity that is not a path. **The first two are one repair and the design already asked for it; the third is unavailable; and none of the three is the important half.**

**The two questions this column is being asked are not the same question, and only one of them is worth a rebuild.** *Is this index this vault's index?* is worth acting on. *Has this vault's path changed?* is not — because `notes.path` is **vault-relative** by the DDL's own words (`schema/001_init.sql:134`, *"vault-relative, canonical, / separated"*), so a vault that moved carries an index in which every row is still exactly right. The check's own rationale in `crates/serat-index/src/schema.rs` says the opposite — *"every path in it describes files that are not there"* — and that sentence is **true of an index from a different vault and false of a moved one**, which is F-107's shape: the variant is named `VaultMoved`, after the single case in which its stated reason does not hold.

**So the ruling has two halves, and the second is the binding one.** *(1)* Canonicalise on record **and** on comparison. This is not a new decision — `schema/001_init.sql:120` already documents the column as *"canonical vault path this index was built from"* and step 5 above already says *the canonical root* — it is the code catching up with a design that was written before it. Both sides, because indexes recorded before the fix hold a `to_string_lossy()` of whatever was handed in. *(2)* **A mismatch stops being a rebuild trigger on its own.** Canonicalisation shrinks the false-mismatch set; it cannot empty it, because a canonical path recorded today can canonicalise differently tomorrow through no user action at all — a remapped drive letter, a reconnected share, a changed mount point. The cost of each false mismatch is a silent full rebuild, and NFR-REL-02's log cannot tell it apart from one triggered by real corruption. **Keep the signal and drop the punishment**: record the new root, report the change, and decide on evidence from the index itself rather than from its `vault_root` string.

**What that costs in the case the check exists for — and this paragraph was wrong, in the way that matters most about a cost.** It said reconciliation would discover that every file differs and cost about what the rebuild would have cost, so the rare bad case degraded to the price we were paying anyway. **rust-core-dev raised the objection this ruling had recorded as absent, and it does not land where I said it would: the cost was never the problem, because the open path performs no reconciliation at all.** Three checks they ran and I did not: this section's own table puts catch-up reconciliation in the *after usable* column with nothing built in it; `serat_vault::walk::paths_of` is documented *"for reconciling against the index"* and has no consumer in the workspace; and `serat_app::vault::run` reports `Stage::WalkComplete(n)` and drops the entries, its own module doc saying *"what P0 does with the events — nothing, and it says so"*. **Taken literally, the demotion would have served a genuinely foreign index as `Ready` for the life of the session with no mechanism that could ever notice**, which is worse than the 28.6 s rebuild it replaced.

**The remedy is the one this ruling itself named as the acceptable repair, so the decision survives its own objection.** Keep a rebuild and trigger it on reconciliation's finding rather than on a string comparison — and where there is no reconciliation, ask the one question a trigger needs: **does any of a bounded sample of the index's own `notes.path` rows name a file that is here?** `identity::describes` samples sixteen rows from each end of `notes.id`, and **one survivor is enough to keep the index**. That bar is deliberately the weakest that can refute anything, which is what makes it a strict improvement rather than a second judgement call: the ruling as written adopted every mismatch unconditionally, and this adopts a subset of them.

**Costed with numbers rather than argued, which is the half the original paragraph should have had.** On the real 20k index: the six stamp steps **6.95 ms**, inside this section's 5–8 ms band, and the whole adopt branch — stamp, probe, write-back — **23.59 ms** against the 28,600 ms it replaces (rust-core-dev, `measure_the_open_check_on_the_20k_vault`; taken during a build freeze, so indicative rather than gate-quality). The common good case stops paying the rebuild; the rare bad case still pays it, and now something can tell them apart. Design goal 5, arrived at by a mechanism that exists.

**What the objection does not close, stated because it is the part a reader will assume away.** The probe is a bounded substitute for one question, not a reconciliation. The open path still has no catch-up mechanism, `paths_of` still has no consumer, and an index that *describes* this tree while being stale in every row is still adopted — which is correct for a warm index and unexamined for anything else. That gap is P1's and it is named here rather than in a task, because a mechanism assumed to exist is exactly what this paragraph got wrong the first time. **Assigned in P1 by ADR-0015 (§3.5):** the tree walk that follows every open is the catch-up, and its disagreements with the index enter on ADR-0011's bulk side — implemented by task #13, and until that lands this paragraph still describes the tree.

**Why an identity that is not a path was rejected rather than deferred.** A non-path token has to survive a move and still distinguish two vaults, so it has to be stored *in the vault* to have anything to compare the index's copy against. **Writing a marker file into a user's vault to protect a structure C-02 calls disposable inverts the priority order** — design goal 1 against a thing whose whole premise is that losing it is survivable. The only other form, an identity derived from content, costs what a rebuild costs and therefore cannot be a cheap precondition. Both are closed rather than left in §Open design questions, because the reasons are available now and a deferral with no owner is indistinguishable from a decision nobody took.

**That rejection was wrong as stated, and test-engineer's own suggestion is what shows it.** A third form exists that needs no write to the vault at all: the **volume serial plus the directory's file id** — `dwVolumeSerialNumber` with `nFileIndex` on Windows, `st_dev` with `st_ino` elsewhere. The vault-side half is supplied by the filesystem rather than by us, so *"it has to be stored in the vault"* is false of it. It is also strictly better at the case F-459 found: a mapped drive, a junction, a UNC form, a differently-cased root and a trailing separator all resolve to one file id, which is the whole of that bug.

**It does not change the ruling, and the reason it does not is the ruling's second half.** A file id is unstable in a different set of legitimate cases rather than in none — a vault moved across volumes, a vault restored from backup, a reformatted or cloned disk, and network filesystems where the pair is neither stable nor guaranteed unique — and each of those is a false mismatch, which is the same class of failure that made the trigger worth demoting. **Once a mismatch is reported rather than punished, the identity's job is diagnostic**, and a diagnostic is read by a person debugging why their vault rebuilt. A canonical path is legible to that person and an inode pair is not. So the recorded identity stays the canonical path — chosen now for readability rather than for correctness, which is a different reason than the one it had before.

**Recorded as an objection that improved the reasoning without changing the outcome, since that is the kind least likely to be written down.** It came from test-engineer, who found F-459 by hitting it rather than by looking for it.

**Two conditions on the implementation, and one is a check I could not make from the DDL.** The variant and its doc comment are renamed to say what the condition is — the index was built somewhere else — rather than naming the one case where the rationale fails. And `notes.path` is documented vault-relative while `asset_path` and `sidecar_path` (`schema/001_init.sql:154-155`) are not documented either way: **the first half of this ruling depends on their being vault-relative too**, so #120 confirms that rather than assuming it, and if either stores an absolute path then that is a second finding and this ruling's demotion does not apply until it is fixed.

**The consultation this ruling owed has since been taken, and it changed the mechanism while leaving the decision intact — the paragraph below is kept in the tense it was written in because what it predicted is instructive: I named the wrong objection.** I expected a cost argument; the real one was that the mechanism I costed against does not exist. **An objection recorded as absent is not a placeholder for the objection you would have made yourself.**

**The original note, unedited.** rust-core-dev owns `serat-index` and is not a live session as this is written, so the objection an ADR-shaped decision is supposed to carry is **absent, not waived**. The place I expect it is named rather than left for them to find: the demotion means an index from a genuinely foreign vault is *reconciled* rather than *rebuilt*, and if reconciliation-on-open assumes the index broadly matches the tree, discovering twenty thousand differences through it may be worse than a rebuild rather than merely equal. If it is, the repair is to keep a rebuild and trigger it on reconciliation's own finding rather than on a string comparison — which keeps this ruling's point and drops its mechanism.

**Anchor and re-check (F-442).** As of `1b3287b` the comparison is `found == expected` over two `String`s in `crates/serat-index/src/schema.rs`, and the rationale this ruling contradicts is the doc comment on `UnusableReason::VaultMoved` in the same file. One line, and it stays checkable after the fix lands because it names the comparison rather than its state: `grep -n 'VaultMoved' crates/serat-index/src/schema.rs crates/serat-index/src/open.rs`.

**No ADR, and the reason is stated so the omission is visible.** This modifies one branch of one function inside ADR-0002's existing rebuild-trigger set; nothing is baselined against it, no budget job asserts it, and reverting it is the same one-line change as making it. Recorded here beside the six steps it changes. If the lead reads the demotion of a documented rebuild trigger as ADR-scale, it becomes ADR-0015 and this section cites it instead.

Measured before it was decided

The acceptance criterion for NFR-REL-02 is a *truncated* index file, so the file was truncated — by 0.1%, by half, to 5%, and to 100 bytes — and every statement failed instantly, including `PRAGMA user_version`, with "database disk image is malformed". SQLite derives the page count from the length of the file, so truncation is caught by step 2 at no cost at all, and the expensive checks buy nothing for this case.

With one boundary that has to be stated, because the sentence above was first written as though it were general and it is not. **The threshold is one page, not a percentage.** SQLite derives the page count by integer division, so a truncation that removes *less than a whole page* leaves that count unchanged and is invisible to the stamp: at 4KB pages, cutting 100 bytes or 2,048 bytes passed all six steps, while cutting one page was caught immediately by every statement, as was everything larger. That boundary reproduces on databases of 1.2MB, 1.4MB, 15.6MB and 124MB, which is the point — it is a property of the cut, not of the file. A percentage misleads only because 0.1% of a large index is thirty pages and 0.1% of a small one is half of one.

Whether the *expensive* check catches a sub-page truncation is undetermined, and the honest answer is that it depends on what the removed bytes held. On the 124MB fixture `quick_check` returned a single row, `ok`, for both sub-page cuts; on a 1.2MB and a 15.6MB database it reported real corruption for the same 2,048-byte cut. Free space at the tail of a file goes unnoticed; live cell data does not. Neither result generalises, so neither belongs in an argument.

The lazy `IndexFault` path is mandatory regardless, and rests on firmer evidence than this: a 4KB overwrite in the *middle* of the file passes all six stamp steps, passes `count(*)` over notes and blocks, and passes a full-text match, and only `quick_check` catches it — at 1,150ms, which is why it cannot be on the open path whatever it can detect. That argument is made above and needs no help from the truncation case.

One calling convention the background check must get right, because each half of it was found the hard way and neither run showed both. **`PRAGMA quick_check` signals corruption in two different ways.** Sometimes it raises: the one-page truncation failed the statement outright with "database disk image is malformed". Sometimes it succeeds and returns its findings as rows, where a healthy database is the single row `ok`. An implementation that runs it, sees no error and carries on is wrong for every case of the second kind. Treat a raised error and a first row that is not `ok` as the same outcome.

##### What the stamp cannot see

Page-level damage deeper in the file survives the open check and is detected when a statement reads the damaged page. Therefore **exactly one function classifies index failures**, and it is reachable from every index read and write: any `SQLITE_CORRUPT`, `SQLITE_NOTADB`, "malformed" error, missing table, or failed FTS integrity check — at open or in the middle of a session — becomes one `IndexFault`, and `IndexFault` has exactly one handler.

That handler closes every connection, deletes `index.db`, `index.db-wal` and `index.db-shm`, recreates the schema from `schema/001_init.sql` and rebuilds. There is no repair path and no code that attempts one (ADR-02), and the rebuild is bounded by NFR-PRF-04.

`quick_check` runs in two places, never on the open path: in the background after the window is interactive when the previous session did not shut down cleanly, and on demand from the command palette. Clean shutdown checkpoints with `TRUNCATE` and closes every connection, which removes `-wal` and `-shm`; a `-wal` file present at open is therefore the unclean-shutdown signal, and it costs a `stat` to read.

Crash safety needs no mechanism of its own. WAL recovery replays the journal on first open, and `synchronous = NORMAL` is safe *here* — not in general — precisely because the index is derived: the worst case of a power cut is losing the last committed transactions, and those are re-derived from files that were never at risk. C-02 is what pays for the pragma.

##### What the user sees

A rebuild is a status line, not a modal and not an error: *"Rebuilding index — search and queries are incomplete until this finishes"*, with a count. Editing works throughout, because editing reads and writes files and never the index (goals 1 and 2). Views and search render the partial index and refresh as `index.changed` arrives.

A rebuild is never retried in a loop. If a rebuild fails to complete twice in one session the state becomes `IndexState::Unavailable` with the path and the operating-system error, and the application runs on as an editor with no search — for the same reason a malformed binary is never re-extracted automatically (§7.1). An indexer that spins forever is worse than an index that is missing, and the vault is unharmed either way.

The states and reasons in this section are the enum the front end renders; they are defined once, in `contracts/ipc.rs`, as `IndexState` and `RebuildReason`.

##### Three things this path deliberately does not depend on

**Per-file work.** Nothing on the critical path opens, stats or hashes a note. This matters more than it reads: the reference machine measures with Windows Defender real-time protection disabled, so every per-file operation is cheaper there than on a stock machine, and a startup path that touched 20,000 files would pass the gate and fail the user. The design's answer is not that per-file work is fast; it is that there is none. The walk, which does touch every file, is after `t_usable` on the warm path.

**Git.** Whether the vault is a git repository is the user's business and not ours. `.serat/` is ignored by C-02 and NFR-CMP-03, the recovery journal is a directory of files rather than a commit, and no part of the cold-start path or the index-open check looks for a repository. A vault under git, under Syncthing, or under nothing at all takes the same path.

**An FTS index that is present and valid.** The open check does not touch `blocks_fts` — an FTS integrity check costs 390ms, which is most of the window budget, and rebuilding the whole index because the search index is stale would be a disproportionate response to a recoverable state. Full-text search degrades to unavailable and the FTS index is rebuilt in the background; the vault stays usable meanwhile, which is design goal 5.

##### Why no ADR

Recorded because an absent ADR should read as a judgement rather than an oversight. An ADR is for a decision that is expensive to reverse. Reversing "check cheaply at open, thoroughly in the background" means adding one call at one site, and nothing is built on top of it. Deferring the index off the main thread is not a new decision at all — it is ADR-01's actor. And `index_meta` is a table, so under ADR-02 changing a column costs a rebuild, which is the sanctioned move rather than a cost. Nothing here has the property that makes an ADR worth its weight.

> The costs above were measured on a development machine, not on the reference machine, and through a Python harness rather than the real pipeline. They are three orders of magnitude apart, so the decision is safe; the numbers that go into the baseline are T2's, on the benchmark vault.

#### 3.5 The file tree (FR-VLT-01, ADR-0015)

P0 measured FR-VLT-01 at 4180 ms median / 8099 ms p95 at 20k (F-193). That figure ran from process spawn, so it carried ADR-0014's platform term (1117 / 1687 ms), and it predates F-12's lexical strip; what was left was the shape — a walk that returns a sorted `Vec` makes the first row visible only when the last one is found. ADR-0015 removes the shape and moves the clock. The mechanism in one paragraph:

- **Unit:** a complete, final-order `DirListing` for one directory, whose entries are a name and a kind only (no size or mtime, so a save never changes one). Order is decided in Rust per directory (folders first; case-insensitive by Unicode simple case fold; byte order breaks ties). A listing replaces any earlier one for the same directory and is used for initial population, catch-up listings that differ, directory renames and overflow rescans.
- **Transport:** an ordered, lossless per-session stream (Tauri `ipc::Channel`), never the throttled `index://` event bus. Initial population ends with `TreeComplete { entries, source }`.
- **Sources:** index `Ready` → one fixed-shape read over `notes(path, kind)` on a read connection, grouped by a pure function in `serat-core`; otherwise a breadth-first streaming tree walk in `serat-vault` (same ignore rules, symlink refusal and lexical strip as `walk`). The index tree is sent only if no walk listing has been. `Vault::walk` is unchanged for the rebuild.
- **The walk always follows the first paint and is authoritative.** On the warm path its listings replace any that differ, and each disagreement between walk and index is submitted as catch-up on ADR-0011's bulk side — the open-path reconciliation this section's task #120 ruling recorded as absent.
- **Live:** after the 150 ms window, a create sends one `TreeUpsert { dir, entry, after }` (Rust names the preceding sibling, so the front end never compares names), a delete sends one `TreeRemove { dir, name }`, and **a content change sends nothing** (FR-VLT-04's 500 ms). A save in a 5,000-entry folder costs the tree zero messages (goal 2, NFR-PRF-02).
- **Front end:** a virtualised list; a folder whose listing has not arrived is shown pending.

**"Populated and navigable", measurably.** `T_open` is the later of `window_visible` and `open_vault` returning, so the platform term is outside the interval by construction. `tree_first_screen` = root listing applied and painted, taken after the tree component's post-flush watcher for that commit, on the second `requestAnimationFrame`; `tree_complete` = `TreeComplete` applied and painted. **Binding: `tree_complete − T_open` ≤ 2000 ms p95 at 20k, on a warm arm (`source = index`) and a no-index arm (`.serat/` removed, rebuild running concurrently, `source = walk`), never averaged.** A run is rejected unless the delivered and front-end entry counts equal the vaultgen manifest's `notes + assets` (20,200 at 20k), `source` matches the arm, and the marks are ordered. Reported, not gated: `t0 → tree_complete`, `tree_first_screen − T_open` at 20k and 50k, and the 50k `tree_complete`. ADR-0015 §3 is the normative text.

**NFR-PRF-01 consequence (amends ADR-0014).** `t_usable`'s tree clause is now `tree_first_screen`, not the whole tree and no longer `buffer_rendered`, so `S_settle` stays constant in vault size (§3.4, *The three marks*). `prf01-serat-term` and `prf01-cold-start` must require the new mark, and the Serat term is re-measured on the first build that renders a tree. Until then, the attested 233.8 ms is labelled as a *buffer-rendered* figure.

### Query compilation

SQ is specified in grammar/sq.ebnf, its lowering in grammar/lowering.md, and its behaviour in grammar/conformance.md. This section is the rationale.

#### 5.1 Two properties enforced by shape, not discipline

The grammar admits no user-defined functions, no loops and no host-language escape, and it fixes rollup traversal depth at exactly one hop. Neither property is a rule someone has to remember: both are structural, so violating them is a parse error rather than a review comment.

They buy two things. Because no query can execute arbitrary code, the engine can always answer “which note and which byte range produced this cell” — which is precisely what writable views require. And because no traversal is unbounded, cost is knowable at plan time, so a dashboard cannot silently become the reason the application is slow.

#### 5.2 Lowering

Seven passes, none of which can loop: resolve the source, collect referenced field keys, plan one LEFT JOIN per key, lower rollups to correlated scalar subqueries, bind let-expressions inside a CTE, choose the value column from the schema kind, and emit. The output is one statement. The worked example in lowering.md was executed against a fixture during design and returns the rows it should.

    -- fragment of the emitted statement for the reference query
    SELECT note_id, path, base_hash, title, status, owner, due, remaining,
           (due < date('now','+7 day') AND remaining > 8) AS slipping,
           status__fid, owner__fid, due__fid
    FROM base
    WHERE status IS NOT 'done'
      AND EXISTS (SELECT 1 FROM fields fl
                  WHERE fl.note_id = base.note_id AND fl.key='lens' AND fl.val_text='pm')
    ORDER BY slipping DESC, due ASC NULLS LAST;

- IS NOT rather than != — a missing field pivots to NULL, and NULL != 'done' drops the row. A project with no status set is exactly the row a status filter should surface.
- \_\_fid columns — every editable cell ships the fields.id that produced it. With base_hash this is the cell anchor the write-back patcher needs; computed columns have none, which is why the UI renders them read-only.
- EXISTS for list membership — a list-valued field is many rows, and joining it would multiply the result set.
- NULLS LAST — an undated project must not float to the top of a due-date sort.

#### 5.3 The typechecker is load-bearing

Lowering is only sound because types are known. If due were Text, pass six would pivot it to val_text and the date comparison would compare strings, returning plausible and wrong rows in silence. The type rules are not ergonomics; they are what makes the emitted SQL correct. This is also why unknown fields are an error on a typed source rather than a warning.

### Write-back

Editing a source note by changing a value in a view is the highest-risk mechanism in the product: it is the only path where a user action can corrupt a file they did not have open. It is designed by constraint rather than by care.

#### 6.1 The algorithm

1.  The cell carries an anchor: note id, field id, and the file hash at the time the row was read.
2.  The core re-reads the file and verifies the hash. A mismatch refuses the write and returns Refused{StaleHash} with the current hash — an expected outcome, not an error.
3.  It verifies that the recorded byte range still contains the field it claims to. A mismatch returns Refused{RangeMoved}.
4.  It replaces exactly those bytes with the serialised new value. Nothing else in the file is touched — no reflow, no key reordering, no re-serialisation.
5.  It writes to a temporary file and renames. The write records nothing (§3.2).
6.  The patched bytes are parsed and submitted, and the new hash is recorded for echo suppression only once that submit has succeeded; the watcher's event is then dropped, the note is reindexed alone, and the affected row refreshes without re-running the query. If the submit is refused, nothing was recorded and the watcher indexes the note instead — one path or the other, never neither.

#### 6.2 Invariants

| Invariant                                            | How it is enforced                                                                                             |
|------------------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| No byte outside the field's range changes            | Property test over a corpus of real notes; this is NFR-MNT-03 and the single most important test in the suite. |
| A concurrent external edit never loses data          | Optimistic lock on the file hash; the write is refused and the view refreshes.                                 |
| The document is never re-serialised                  | The patcher's only operation is byte-range replacement. It has no serialiser to call.                          |
| Creating an absent field is the only structural edit | Appended to frontmatter at the position the type declares — which is why FieldSpec carries an order.           |
| Undo crosses the boundary                            | A view edit enters the editor's undo stack; undo re-patches the file.                                          |

Why this is not solved by parsing and re-emitting

An AST round-trip would be simpler to write and would lose the author's formatting on every save: list markers normalised, table padding rebuilt, YAML key order rearranged. Every save would become a diff, which destroys git history and fights every external tool. Not round-tripping at all is the design, not an approximation of it. See ADR-08.

### Binary extraction

The full contract will be `contracts/extractor.rs`. It is not written yet, so §7.1–§7.3 are the whole of the design until it is — stated in the future tense because the present tense here is what made five absent files read as existing ones (F-239). An extractor turns a binary into the same block rows a Markdown parser emits, which is why search, backlinks, embeddings and citations work on a PDF with no parallel code path.

#### 7.1 Isolation

Extraction runs in a short-lived child process with a wall-clock limit, a memory cap and no network. Parsing untrusted binaries in the main process is how a notes application becomes a CVE, and a thread cannot provide that boundary. The supervisor communicates over newline-delimited JSON on stdout, so a partial read is never a partial block.

A malformed file is never retried automatically. It will fail again, and a retry loop on a broken PDF is an indexer that spins forever on a vault the user cannot fix. The failure is recorded in assets.extract_error and the pipeline moves on.

#### 7.2 Two caches, deliberately separated

The index is disposable by principle. Re-OCRing four hundred scanned PDFs is not. Extraction output therefore lives outside the index, keyed by content hash and extractor version, and survives an index wipe. Deleting the index stays a seconds-long operation; the expensive artefact is kept separately and is invalidated per format when an extractor improves.

#### 7.3 Degradation is a supported state

When no extractor claims a file, the asset still indexes with its sidecar and stays typed, linkable and queryable — only full-text search over its contents is unavailable. ExtractionState::Unavailable is a normal value in the IPC contract, not an error, and the UI shows it as a fact about the file rather than as a failure.

#### 7.4 P1: assets without extraction (FR-BIN-01/02/03, FR-VLT-08, FR-BIN-11/12)

P1 indexes, pairs, lists and displays binaries. It does not extract them (P2), so every mechanism below works on metadata and on bytes served untouched.

- **Asset rows (FR-BIN-01).** An asset is a `notes` row with `kind = 'asset'`, as today (`upsert_asset`). A new table `assets(note_id INTEGER PRIMARY KEY REFERENCES notes(id) ON DELETE CASCADE, mime TEXT NOT NULL, bytes INTEGER NOT NULL)` carries MIME and size. It is the P1 slice of the table the DDL header already names; the extraction columns arrive with P2's schema change, which under ADR-0002 costs a rebuild and nothing else. **MIME comes from the file extension**, through one table in `serat-core` (unknown extensions become `application/octet-stream`). Sniffing content was rejected: it would read every binary on every rebuild, a per-file I/O cost on NFR-PRF-04's path, for a distinction P1 displays and does not act on. Size comes from the walk's stat, which is already in `SourceEntry`. Both the rebuild and the incremental path write the row in the same `upsert_asset` call, so no second path exists. The DDL lands with task #17 as one change that bumps `user_version`.
- **Sidecar association (FR-BIN-02, ADR-0005).** The pairing is derived from names alone: `x.pdf.md` is `x.pdf`'s sidecar when both exist in one directory. The names are compared **byte for byte**, deliberately: `X.PDF` and `x.pdf.md` are not a pair (ADR-0017 records why). It is recorded as `notes.sidecar_path` on the asset row, and nothing is copied from the sidecar to the asset. The sidecar stays an ordinary note, carrying its own `type` and fields, and R3 (§4.5) reaches the asset through the join. **In a rebuild** one `UPDATE` pairs every asset after the load, beside `resolve_links`. It touches only the ~200 asset rows through `notes.path`'s unique index, so NFR-PRF-04 pays nothing measurable. **Incrementally**, upserting a note whose path is `<asset path>.md` sets that asset's `sidecar_path`; upserting an asset checks for its sidecar; deleting either clears the pairing. Each is one lookup through the same unique index.
- **Paired presentation (FR-BIN-03).** The fold happens in Rust, in the pure listing function ADR-0015 puts in `serat-core`. When a directory holds `x.pdf` and `x.pdf.md`, its listing carries one entry, `x.pdf` with kind `asset` and `sidecar: true`, and no entry for `x.pdf.md`. Creating or deleting the sidecar sends one `TreeUpsert` for the asset entry, and deleting the asset sends a `TreeUpsert` that turns `x.pdf.md` back into an ordinary note entry. Because the index and the walk share the function, they cannot disagree about a fold. The sidecar remains a note everywhere else: in the switcher, search and backlinks. Opening a folded entry opens the viewer with the sidecar available as its metadata note.
- **Attachments are listed and linkable (FR-VLT-08).** Listings include assets. **The attachment list is R5, the fifth fixed read of §4.5** (`Reader::attachments()`, task #17). It is one statement, and it carries each asset's shortest resolving link form as a column computed by the resolver's own rule, so the front end never computes a link target itself. Inserting a link to one — a command on the tree entry, or dragging it into the editor — writes the shortest resolving form of §9.3: `![[name.png]]` for an image or PDF, `[[name.ext]]` for anything else.
- **Viewer bytes (FR-BIN-11, FR-BIN-12): ADR-0017 (proposed).** Bytes come through one read-only custom scheme, `serat-asset`. The handler:
  - accepts GET and HEAD only, on host `localhost`, and decodes the path exactly once;
  - builds the path under task #34's rules (no `:`, no device names, no trailing dot or space), and **must not ship before #34 lands**;
  - serves viewable types only (PDF and images);
  - resolves every request through `Vault::resolve` and checks `starts_with(root)`, then re-verifies the opened handle's real path and requires `is_file()` (T-10);
  - sends CORS for the exact app origin only;
  - serves PDFs in spans capped at 1,000 KiB, with pdf.js given its length from `assets.bytes`, set to `disableStream`/`disableAutoFetch`, and sending `If-Range`;
  - serves images whole up to 64 MiB, because `<img>` sends no `Range`; a larger image gets 404 and "couldn't be displayed";
  - sends `nosniff` and a sandboxing per-response CSP.
  The app CSP gains that one first-party origin in `img-src` and `connect-src`, and nothing else. pdf.js, with its worker, cMaps and fonts, is bundled and runs without `eval` and with `enableScripting: false`, so the viewers make no network request (NFR-SEC-01). **Tauri classifies the scheme as local, not remote**, so three controls keep a scheme document from IPC: §9.3's `on_navigation` guard (top-level navigations only; it never sees frames), the script-free `sandbox` CSP on every response, and the app CSP's explicit `frame-src 'none'; object-src 'none'` pin, backed by the sanitiser stripping `iframe`/`object`/`embed`. There is no origin-classification control (ADR-0017, corrected). Downloads are refused, and the default context menu is off in release builds. pdf.js is pinned at ≥ 4.2.67 (CVE-2024-4367). **If a webview will not deliver a custom-scheme 206**, that platform falls back to a span-serving `read_asset_range` command with the same checks, so PDFs still load per page (ADR-0017 §Fallback).

### AI retrieval and MCP

Three separable pieces: retrieval, which is always local; generation, which is provider-agnostic; and exposure, which is the MCP server. Only the middle one ever touches the network.

*(figure — see the original in docs/_source/serat-design-description.html)*

Fig. 3 — Hybrid retrieval. Three signals computed independently, fused by reciprocal rank. The structural signal is the one competitors lack and the reason a graph-connected note can outrank a lexically closer one.

#### 8.1 Chunking and embedding

Chunks span block boundaries with the heading path prepended as context, so an embedded paragraph carries the section it came from. Chunks are keyed by a text hash and only changed chunks are re-embedded, which is what keeps a one-word edit from re-embedding a long note. Embedding runs in-process against an ONNX model downloaded on first use — never bundled, so the installer stays small and the application is fully usable with the AI layer never enabled.

#### 8.2 Fusion

Lexical, semantic and structural rankings are computed independently and fused by reciprocal rank, with fixed per-signal weights and no tuning knob exposed. The structural signal — proximity in the link graph to the strongest seeds — is what makes retrieval feel different from a semantic-search plugin, and it is available only because the link table exists for other reasons.

Exclusions are applied before retrieval, not after. A note carrying ai: false, or living outside the configured scope, is never a candidate, so its text cannot reach a request payload even as a discarded low-ranked result.

#### 8.3 The proposal lifecycle

Every AI-originated change becomes a Proposal: a summary, a set of unified diffs each carrying the base hash of its target, and the citations that justify it. Proposals from the agent panel, the capture agent, synthesis and external MCP clients all enter the same queue. There is exactly one function that writes a proposal to disk, it is reachable only from a user action, and adding a second path would violate a constraint rather than merely a preference.

The MCP server is a second front door onto the same query API, not a wrapper around the application. That is why an external agent can never see a staler vault than the window does, and why propose_edit returns queued and never applied. apply_edit, write_file, delete_note and shell are recorded in the schema file as deliberately absent, so their omission reads as a decision.

#### 9.2 The quick switcher (FR-NAV-01, NFR-PRF-06)

A different control from §9's lens switcher: it changes note, not role. Designed in P1 (task #3); it had no design element before (§Traceability, *Musts with no design element yet*, now cleared).

**Where it runs: in Rust, one IPC command per keystroke.** The corpus and the matcher live in a `switcher` module of **serat-index**, beside the rows they are derived from; `serat-app` exposes one command. The webview alternative was rejected on goal 2 — matching tens of thousands of strings on the webview's main thread shares a thread with the editor — and on cost: shipping the corpus to JavaScript is megabytes per refresh. FTS5 with the trigram tokenizer was rejected because it is substring rather than subsequence matching and because it is one more index maintained on every row of a rebuild that sits at 27.7 s against 30 s (NFR-PRF-04, task #96).

**Sources, and the one query that loads them.** Per note: `notes.title`, the vault-relative path without extension, and every alias — `fields` rows with `key IN ('aliases','alias')` and `source = 'frontmatter'`, one row per list item as serat-parse emits them (Obsidian accepts both keys). **Known gap: block-style aliases never reach the index today.** An `aliases:` list written one item per line (`- name`) produces no `fields` rows, so those aliases are not switcher candidates. Flow-style lists (`aliases: [a, b]`) and a single scalar are indexed. That is a serat-parse defect against NFR-CMP-01, and task #57 fixes it. Until then, the switcher's query-set check excludes block-style alias queries and names how many it excluded, so a known miss is neither hidden nor counted as a failure of the switcher. Headings are `blocks` with `kind = 'heading'`. **No schema change**: the corpus is loaded by fixed-shape reads on a read connection, the heading read is a scan of `blocks` that runs off every critical path, and adding an index for it would put a per-row cost on the rebuild for a read that happens once per refresh (§3.1's third-caller rule).

**Two modes, decided by the query.** Without `#`, the candidates are titles, paths and aliases — about 45,000 strings at 20k notes. With `#`, the text before it filters notes as above and the text after it matches those notes' headings; an empty prefix matches every heading. **About 35,000 were measured on the 20k benchmark vault** (#16). The earlier estimate of about 70,000 was twice that. Keeping headings out of the default mode is what keeps them from flooding ordinary results, and matches Obsidian's `[[note#heading]]` idiom.

**Matching and ranking — deterministic, so it is testable (goal 3).** Subsequence match, smart case (a query with no capitals is case-insensitive), no diacritic folding in P1. Each note appears once, under its best-matching candidate. Results are ordered by:

1. **Match class:** exact match of a title, alias or file name › prefix of one of those › contiguous substring or all query characters at word starts › scattered subsequence.
2. **Frecency**, descending — recency and frequency, as FR-NAV-01 requires.
3. The scorer's score, descending (an fzf-v2-style scorer; `nucleo-matcher` is the candidate, subject to the licence check — tests assert this ordering, not a crate).
4. Shorter candidate, then path in byte order.

**The scorer is bounded, and where it gives up exactness is stated** (task #16).

- **The exact pass.** Candidates are capped at 256 characters. For a query of *m* characters, the matcher runs the exact dynamic program only over the window of the candidate from the first occurrence of the query's first character to the last occurrence of its last character.
- **When the exact pass is skipped.** The matcher falls back in two cases:
  - **the window is too large**: *m* × window exceeds 2,048 cells. Given the 256-character cap, that happens only for queries of 9 characters or more;
  - **the query's budget is spent**: a per-query budget of cells, value in the code, has been used up across the candidates already scored.

  Then the score and the word-start class come from the **leftmost greedy alignment**.
- **What the fallback costs, and in which direction.**
  - Greedy scores sit on a lower scale than exact ones. That biases long candidates downward, which is the same direction as the shorter-candidate tie-break (rank 4), so it never promotes a long candidate over a short one.
  - The greedy alignment can miss a word-start alignment that exists, so a candidate can drop from the word-start tier ("all query characters at word starts") to the scattered-subsequence tier.
  - **The substring class is still exact**, because it is decided by a substring search, not by the alignment. Exact, prefix and contiguous-substring matches never move class.
- **Results stay deterministic.** Candidates are consumed in a fixed order (corpus order, which is note path order), so the budget runs out at the same candidate for the same query and corpus on every run, and two runs return the same 50 results in the same order (goal 3).
- **The adversarial worst case is reported, not gated.** That is 50k notes with 100–200-character titles dense in `e`, queried with `e`-heavy queries. It is reported beside the NFR-PRF-06 bench and the `Switcher::query` allocation, and labelled as adversarial. The benchmark vault's titles are not like that, and a cap that made the adversarial case gate would be tuning the switcher to a vault nobody has.

At most 50 results, by partial selection rather than a full sort. Each result carries its note path, the candidate that matched (`title` | `alias` | `path` | `heading`), the heading's text and byte offset when it is one, and the matched character ranges for highlighting. **An empty query returns 20 notes: the most frecent first, then, to fill the 20, the most recently modified (`notes.mtime` descending, then path in byte order), with no note listed twice.** As #16 first built it, an empty query returned only notes with history. On a fresh vault, or after `.serat/` is deleted, that left the switcher blank until a note had been opened, which is a control that shows nothing where US-04 promises any note within reach, and against goal 5.
- Modification time is derived from the vault, so the fallback depends on nothing that lives only in `.serat/` (C-02).
- It is a good proxy for the notes the user has been working on. A sync tool that touches mtimes can reorder it, and that is accepted for a list whose only job is to be a useful start.
- The corpus load carries `notes.mtime`, which is one more column in its fixed read.
- **Before `Ready`**, the tree-built snapshot has no modification times, so an empty query shows frecent notes only, and the panel's hint ("Type to find a note") when there are none.
- **Test** (serat-index): a fixture with no history returns 20 notes in mtime order. With history for 3 notes, those 3 come first, followed by 17 by mtime.

**Recency and frequency live in `.serat/history.json` — ruled, closing the open question.** Keyed by vault-relative path; up to the last 10 open times per path, at most 2,000 paths; frecency = Σ 0.5^(age_days / 7) over the stored opens. A note counts as opened when the front end reports it opened in an editor pane — never when a file is read for an embed, a preview or a search snippet. **The record and the write are split across two crates, as the dependency rule requires.** serat-index cannot depend on serat-vault (§2.1), and only serat-vault does file I/O.
- **serat-index keeps the pure record:** `History`, which turns bytes into a record and back, computes frecency, applies the 10-opens and 2,000-path caps, and moves a key on a rename. It does no I/O.
- **serat-vault does the write:** `Vault::update_history`, a sibling of `Vault::update_prefs` on the same guarded atomic read-modify-write path (`update_serat_file`). That path refuses a symlinked `.serat/` or file, and it passes the current bytes to a pure closure that may run twice.
- **serat-app joins them:** it passes `History`'s encode function to `update_history`, debounced by 2 s.
- **The `std::fs` source-scan allow-list of §2.1 needs no new entry.** The write lives in serat-vault, which is already on the list. serat-index gains no file I/O.

- **Why `.serat/` and not the vault:** writing a file the user did not ask for into their vault is what design goal 1 forbids.
- **Why this is C-02-compliant:** nothing depends on the file. Missing, unreadable or of an unknown version, it is ignored and replaced, and ranking falls back to classes 1, 3 and 4 alone — *capability degrades* (goal 5).
- **Why it is not in `index.db`:** it is not derived from the vault and cannot be re-derived, so putting it in the index would make a rebuild destroy it. The rebuild removes only `index.db`, `-wal` and `-shm` (`crates/serat-index/src/rebuild.rs`), so a sibling file survives it — which makes *"degrades to lexical after a rebuild"* unnecessary rather than merely acceptable. It is lost only when the user deletes `.serat/`.
- A rename done in Serat moves the key. A rename done outside Serat loses that note's history, which is acceptable for a ranking signal.

**Freshness.** The corpus is an immutable snapshot swapped atomically by generation. It is built when the index publishes `Ready`, and rebuilt on a background thread 500 ms after the last `index.changed`, so queries never wait for a refresh and results are at most about a second stale. **Before `Ready`** — first open, or a rebuild — the snapshot is built from the paths the vault thread has already enumerated for the file tree: paths and file names only. That holds whichever tree-delivery design lands. Under ADR-0015 that source is its directory listings. So the switcher works from the first listing, and gains titles, aliases and headings when the index arrives (goal 5).

**Stale responses.** Each query carries a sequence number. The Rust side answers the newest query and discards any older one still waiting; the front end drops any response whose sequence is not its latest. A slow keystroke therefore never paints over a faster one.

##### NFR-PRF-06: what is measured, where

**Binding: keystroke to painted results, under 50 ms at p95, at 20,000 notes, measured in the real binary.** The interval runs from the `input` event's `timeStamp` for the keystroke that completes the query's third character to the second `requestAnimationFrame` after the Vue commit that renders that query's results — the response whose sequence number is that keystroke's. It is driven by a `--bench-switcher-list <file>` flag on `serat-app`, the same shape as `--bench-save-list`: with the vault open and the index `Ready` (pre-warmed, F-450), the front end types each query from the file one character at a time through synthesised input events and records one line per keystroke.

**Typing cadence is fixed, and every run line records it:** a keystroke is sent only after the previous keystroke's results have painted, *or* 100 ms after it, whichever comes later. Without that, keystrokes queue behind slow responses and the figure measures the queue. With it, each keystroke is measured on an idle pipeline, as a user typing at about ten characters a second would see it. Each line records `cadence_ms` and whether the wait was for the paint or for the interval.

**"Third character" counts every typed character, `#` included.** This is ruled, and it was first made by test-engineer in the module comment of the switcher budget job (`switcher.rs` in bench/budget, on `task/p1-10-switcher-budget`). The rule names a position in the raw input, not a position among letters, so a mode switch is a keystroke like any other. Its consequences for heading mode:

- `abc#heading` is gated at `c`, before heading mode begins.
- `ab#heading` is gated at its third keystroke, `#`. The gated query `ab#` is in heading mode with empty heading text, so it matches every heading of the notes that `ab` matches. That is the widest heading-mode query shape.
- **Heading mode with non-empty heading text is gated only when the note prefix is at most one character**: `#ab…` (empty prefix, heading text `ab`) and `a#b…` (prefix `a`, heading text `b`).

**So the query set must include `#ab…`, `a#b…` and `ab#…` queries.** Otherwise heading mode is never exercised at the gate, and its figure is all reported keystrokes and no gated ones.

**The figure is slightly low, and says so.** A synthesised `input` event skips the browser's native key handling — hardware and OS input queueing, IME, and the native `keydown` default actions — so the interval starts later than a physical keystroke's would. The bias is small next to 50 ms, and it is one-directional. Every figure carries it as a basis clause. Keystrokes 1, 2 and 4 onwards are reported and not gated. This is the aggregate, measured directly and not composed from its parts, which is the rule §3.4 learned twice.

**Allocation, a diagnostic that runs locally without the application (CI budget jobs do not run while RISK-013 stands): `Switcher::query` ≤ 20 ms p95 at 20k**, measured in `bench/budget` against serat-index directly over the same query file, with the corpus built from the 20k vault's index. The remaining 30 ms is IPC plus render. A breach of the allocation with the aggregate green is a finding, not a failure. Also reported and not gated: the time to build the corpus snapshot, and all figures at 50k.

**Ruled on #16's numbers (`task/p1-16-switcher-index` at `df4edac`, in review).**

| Measurement | Figure | Machine |
|---|---|---|
| 20k, keystroke 3, default mode | p95 17.8–18.7 ms against the 20 ms allocation | loaded box |
| 20k, keystroke 3, heading mode | p95 19.4–21.7 ms | loaded box |
| 50k | p95 56 ms | load average 3.6–9.6 |

- **20k gates NFR-PRF-06, and 50k does not.** The requirement names its own size ("at 20,000 notes"), as do FR-NAV-01's criterion and US-04's. C-06's "20k/50k vault" names the synthetic vaults the budgets run against, and a requirement that states its vault size is enforced at that size. 50k is reported beside every 20k figure as the scaling signal.
- **The 50k figure is not a measurement of record.** It was taken on a loaded box. The 56 ms is about three times the 20k figure for 2.5 times the corpus, consistent with a linear scan, and that is all it is evidence of.
- **The allocation applies to each mode separately, and heading mode is reported as its own row.** There is one number, 20 ms p95 for `Switcher::query`. It is held per mode, as R1's most common term is reported apart from its query set (§4.5), so that the default mode's larger keystroke count cannot hide heading mode. **Heading mode's 19.4–21.7 ms is a finding now**, even on a loaded box. Its widest gated shape, `ab#`, matches every heading of the notes `ab` matches.
- **The margin is thin, so the remedy order is decided now, and either remedy needs a breach on an attested quiet machine** (`concurrent_build_processes: 0`, load recorded in the run line, as NFR-PRF-03's gate is):
  1. **First, a pre-lowercased candidate array.** Each candidate's lowercase form is built once, at corpus build, beside an ASCII flag, together with the matcher's own pre-converted form of it. A case-insensitive query, which is the common case under smart case, then matches without converting or folding a candidate per keystroke. It costs memory once per refresh and per-keystroke work nowhere. It stays single-threaded and deterministic, and it takes no core from the writer or the webview.
  2. **Second, and only if the first is not enough, a parallel scan on the rayon pool.** The corpus is split into chunks, each chunk keeps its own top 50, and the chunks merge under the same total order (match class, frecency, score, length, path). That is still deterministic, because the order is total. It is second because it competes for cores with the writer and the webview on a 4-core machine, which is the machine where the switcher is slowest. It is also the step 50k would need first if it ever became a gate.
  3. **Heading mode is remedied first in either case**, because it is the mode at the line.

**Query set** (test-engineer, task #10): derived from vaultgen's manifest and titles. At least 200 queries: three-character prefixes of titles and aliases; three-character subsequences spread across a title; path-segment queries; queries that match nothing; and `#` heading-mode queries, including the three shapes above that put heading mode on the gated keystroke (`#ab…`, `a#b…`, `ab#…`). The benchmark vault draws headings from a small fixed vocabulary, so heading-mode figures overstate the match count and must be labelled with that.

**A run is rejected, not recorded, unless:** `.serat/history.json` is in a declared state — absent, or a fixed fixture committed with the query file — and the run line names which, because frecency changes the order and a history left over from a developer session is per-machine state (F-169's shape); every query constructed from a known note's **full title** returns that note in its top 10, and **every three-character prefix or subsequence query returns at least one result** — a switcher that returns nothing is fast, which is F-19's shape. A three-character prefix can tie more than 10 notes on match class, so asserting its source note in the top 10 would fail on a correct ranking. The non-empty check is the one that catches F-19 there — every no-match query returns zero results, and the number of measured keystrokes equals the number of queries.

**No ADR.** Every choice here sits behind one command and one module. The one on-disk artifact, `.serat/history.json`, is disposable by construction: changing its format costs users their ranking once and nothing else.

#### 9.3 The editor (FR-EDT-01/02/03/10, FR-NAV-06, NFR-PRF-02)

Designed in P1 (task #5). Saving and reconciliation are ADR-0016 and §3.3. Everything else is below. **The editor has no IPC on the keystroke path.** Saves are debounced and asynchronous, link resolution is batched per viewport, and the preview render is scheduled off the keystroke. This is design goal 2 stated as a rule a reviewer can check.

##### Decorations (FR-EDT-01, FR-EDT-02, ADR-0006)

- **Parse.** Lezer markdown through `@codemirror/lang-markdown` with the GFM extensions (tables, task lists, strikethrough, autolinks). Custom inline extensions for what Lezer lacks: footnotes, `[[wikilink]]`, `![[embed]]`, `^block-id`, `key:: value`, and `==highlight==`. The parse is incremental, and it is time-sliced by CodeMirror, so a long note never parses on one keystroke.
- **Inline decorations** come from a `ViewPlugin` over `view.visibleRanges` only, so their cost follows the viewport rather than the note. The previous `DecorationSet` is mapped through each change, and only the changed lines plus newly visible ranges are recomputed.
- **Block widgets** — tables, embeds, callouts — come from a `StateField`, because CM6 permits block decorations only from state. Each widget implements `eq` so that an unchanged table is never rebuilt in the DOM.
- **Reveal rule (FR-EDT-02).** Syntax markers are `Decoration.replace`d except on lines that intersect any selection range. A selection change recomputes only the lines it enters and leaves, which is how "within one frame" is kept.
- **Obsidian syntax that Serat does not render** (for example Dataview blocks and plugin fences) is left as source text. It is never rewritten (C-01, NFR-CMP-01).

##### Links and embeds (FR-EDT-03, NFR-CMP-01)

**Resolution has one implementation, in serat-index, used by the writer and by the editor.** A link resolves by:

1. the vault path exactly, with or without `.md`;
2. then, only if the target has no `/`, the file name anywhere in the vault. Ties go to the shortest path, then byte order. This is the rule `resolve_links` already implements (`crates/serat-index/src/writer.rs`).

**Matching is case-insensitive, as Obsidian's is.** The current SQL compares with `=`, so `[[my note]]` does not resolve to `My Note.md` today. The comparison and the index both use the stored, Rust-folded columns of §4.5, and they **must land in one commit with the rebuild benchmark**: changing either one without the other turns the per-link join into a scan, which is F-371 again. The fold is Unicode lowercasing, as Obsidian's is, not `NOCASE`'s ASCII-only fold. So `[[émile]]` resolves to `Émile.md`. **Task #12's compatibility corpus is the check of both rules against Obsidian.** Where Obsidian disagrees, Obsidian wins, and the rule changes in this one place.

**Subpaths.** `#Heading` matches a heading of the target case-insensitively; `#A#B` matches `B` under `A`; `#^id` matches `blocks.block_ref`; `[[#Heading]]` targets the current note. `|text` is display text only. An unresolved link renders as unresolved and is never "fixed" in the file.

**The editor resolves through one batched command per viewport change.** Results are cached for the session and invalidated by `index.changed`. Before the index is `Ready`, links resolve by file name against the ADR-0015 tree listings (goal 5).

**Autocompletion.** `[[` followed by two characters queries the §9.2 switcher in link mode: same corpus, same ranking. Choosing an entry inserts the shortest link that resolves back to it — the file stem if its name is unique, otherwise the vault path without `.md`. Then `#` completes that note's headings and `^` its block ids. FR-EDT-03's "inserts a resolving link" is tested by re-resolving every inserted link.

**Embeds.** `![[note]]`, `![[note#Heading]]` and `![[note#^id]]` render the target's Markdown read-only, as a block widget, through the preview renderer below. Nesting is capped at depth 2 and cycles render as a link. `![[image.png|300]]` renders the image through the asset path of task #6. PDFs and other binaries render as a link chip that opens the viewer (FR-BIN-11). The widget yields to raw source when the selection enters its line, as any other syntax does.

##### The preview renderer, and what it may not do (T-09)

Split preview and embeds share one renderer: `markdown-it` with GFM, footnote and wikilink plugins, plus the resolver above. That makes three Markdown parsers — comrak for the index, Lezer for the editor, markdown-it for preview. They are kept rather than unified because each one is the standard tool for its job. Their divergence is checked by task #12's corpus rather than assumed away.

**Rendered HTML passes a strict allowlist sanitiser before it reaches the DOM.** It keeps no `<script>`, no event-handler attributes, no `style` attributes, no `iframe`, `object` or `embed`, no `download` attribute, and no `javascript:` or `data:` URL of any kind. An inline `data:image/*` renders as a labelled placeholder, like a remote image. That keeps the app CSP free of a `data:` source: its only P1 addition is ADR-0017's `serat-asset` origin. **It loads no remote resource**: a remote image renders as a labelled placeholder with its URL, and is never fetched (NFR-SEC-01). The CSP in `tauri.conf.json` (`default-src 'self'`) already refuses both, so the sanitiser is the first barrier and the CSP the second. A note is untrusted input: git, sync tools and agents all write into the vault.

**Navigation is guarded separately, because the CSP does not cover it.** A rendered `<a href="https://…">` that the webview follows would navigate the app window to a remote origin. The window would then be showing remote content, which breaks NFR-SEC-01, and `connect-src` does not stop a top-level navigation. So:

- **serat-app installs an `on_navigation` handler on every webview.** It refuses every URL that is not the app's own origin — **including `serat-asset://…`, which Tauri treats as local and which must never become the top-level document (ADR-0017)**: `tauri://localhost` and `http://tauri.localhost`, plus the dev server in debug builds only.
- **The front end intercepts clicks on rendered external links** (`http`, `https`, `mailto`). A click hands the URL to the system browser through the opener plugin, and only on that explicit click. **The opener capability is scoped to exactly those three schemes (ADR-0012)**: `file:`, custom schemes and anything else are refused by the capability itself, not only by the front end. Hovering shows the URL, and nothing ever opens one automatically.
- Internal wikilinks never navigate the webview. They are routed by the editor.
- `window.open` and new-window requests are refused the same way.

The guard is part of T-09, and #12's hostile corpus includes an external link, a `javascript:` link and a meta-refresh, each of which must leave the window on the app origin.

##### Split preview (FR-EDT-10)

With `editor.live_preview = false`, the editor is source mode (syntax highlighting only) beside a read-only rendered pane. The pane re-renders 150 ms after the last change. The render is scheduled in idle time and chunked, so a 5,000-line note never renders in one frame. Scroll sync maps source lines to the rendered blocks' `data-line` attributes. Editing capability is identical in both modes, because it is the same editor.

##### The command registry (FR-NAV-06, NFR-USE-01)

One front-end module owns every user-invocable action: `register({ id, name, defaultBinding?, when?, run })`. The palette lists the registry with each command's effective binding. **The CodeMirror keymap is built from the registry**, including the default editing and history commands, which are re-registered under Serat ids. `keymap.of` appears in exactly one place, and a test asserts that. User rebindings live in the settings TOML (FR-PLT-05) under `[keybindings]`, keyed by id. A unit test asserts that ids are unique, that every command has a name, that no two commands share a binding in the same `when` context, and that every entry in the NFR-USE-01 primary-action list is registered. That test is the "Inspect" the requirement names, made repeatable.

##### NFR-PRF-02: what is measured — frames, not milliseconds

**"Keystroke to paint ≤ 16 ms at p95", read literally, cannot be met at 60 Hz by any editor.** A keystroke lands at a random point in a 16.7 ms frame, so the wait for the next vsync alone averages 8 ms and reaches about 16 ms at p95. code-reviewer measured it on a **bare `contenteditable`**: timestamp to the next main-thread paint was 17.1 ms p95, and 16.2 ms of that was the vsync wait. An earlier draft of this subsection used the Event Timing API's `duration`, which contains the same wait and would have failed a bare `contenteditable` too. It is withdrawn. **16 ms is one frame at 60 Hz, so the requirement is read as a frame budget.**

**Binding: at least 95% of keystrokes are painted in the first frame after the keystroke, in every scenario, in a 5,000-line note.** In other words, the p95 of `frames_to_paint` is 1, and the worst scenario gates. The figure is independent of refresh rate and of how fast the machine is at anything but our own work. That is what a user perceives: typing either keeps up with the display or it drops frames.

**The rule below was chosen after the data, not before it.** Three earlier definitions were written first and then failed on recorded frames. test-engineer's task #11 recorded raw frames, keys and browser timing entries with no rule applied (branch `task/p1-11-editor-latency` @ `a616def`, `record/` under the editor-latency bench: README, `data/summary.txt`, `data/et-margin.txt`, and the raw recordings beside them). Every candidate rule was then scored offline against the same recordings. Basis: headless Chromium 141.0.7390.37, R = 16.70 ms, trusted `keyboard.press`, 100 ms cadence and a phase-swept (jittered) cadence.

- **The anchor.** Before the run, the harness measures the refresh interval `R` as the median of 120 consecutive `requestAnimationFrame` deltas, and records it. **`R ≥ 16 ms` is a validity condition of a gated run. A run with `R < 16 ms` is rejected, not scored.** The absent-entry rule below needs `16 ≤ R`. At 120 or 144 Hz, a key with no entry can present up to `16 − R` after `D` (9.1 ms at 144 Hz) and would still be scored on time. A continuous `rAF` loop records each frame's timestamp. For a keystroke whose `keydown` has `timeStamp` `t`, `ts_j` is the last recorded `rAF` timestamp at or before `t`.
- **The deadline.** `D = ts_j + 2R`, the end of the display frame after the keystroke's frame.
- **The paint (rule E0).** A `PerformanceObserver` with `type: "event"` and `durationThreshold: 16` collects Event Timing entries. **A key's entries are those whose `startTime` falls in `[t, t + 4 ms]`, excluding `keyup`.** In practice those are `keydown`, `keypress`, `beforeinput` and `input`. That window is the rule as measured, because it is what `analyze.mjs` applies. **They are not grouped by `interactionId`.** In Chromium 141, `beforeinput` and `input` entries carry `interactionId` 0, so grouping by it silently drops them. Under that grouping, graded run 3 falls to 83.8% late, outside its band. `ET_end` is the maximum over the key's entries of `startTime + duration`. The browser measures `duration` up to the presentation of the next paint after the event was processed, and rounds it to 8 ms.
- **An absent entry is on time.** No entry means that every one of the key's events reached presentation in under 16 ms. Because `ts_j ≤ t < ts_j + R`, `D` is more than `R` after `t`, so a paint that comes less than 16 ms after `t` is before `D`. **Beside every figure, the run reports the number of keys scored this way and the worst-case margin of an absent key, `min(D − t) − 16 ms`.** In the positive arm, 190 of 297 keys had no entry strict (`pos.json`), with a worst-case margin of 0.80 ms. Jittered (`posj.json`), 185 of 297 had none, with a worst-case margin of 0.70 ms. code-reviewer-2 computed these from the raw recordings, and architect reproduced them. So most on-time verdicts rest on this argument rather than on a timestamp, and the argument's slack is under a millisecond. An observer that silently drops entries would score every key on time. That is why the negative controls below are required and not optional.
- **Two per-run invariants, asserted by the harness.** If either fails, the run is rejected. They are what makes the absent-key bound hold.
  - **`keydown` is present whenever any entry is present.** A key whose later events have entries and whose `keydown` does not would mean the window or the observer is losing entries, and then an absent key would no longer be safe to score as on time.
  - **The spread of a key's entry ends is at most 8 ms.** All of a key's events reach the same paint, so their ends may differ only by the 8 ms rounding.

  Both hold on every arm of the #11 recordings: no key with an entry lacked `keydown`, and the widest spread was 7.9 ms.
- **The verdict.** A key is late if and only if `ET_end > D`. For reporting only, `frames_to_paint = 1 + max(0, ceil((ET_end − D) / R))`.
- **A stale anchor.** If `t − ts_j ≥ R`, the `rAF` loop missed a frame and `D` sits earlier than the real deadline. Such keys are still scored, and their count is reported. This bias can only make a key late, so it never flatters the editor. Neither positive run had one. Graded run 1 had one key with a phase of 1.07R. The paint arm had stale anchors too, with a phase up to 4.98R, because its main thread was too busy to run `rAF`.
- **Rounding.** The 8 ms rounding of `duration` puts up to ±4 ms on `ET_end`. On the controls, a threshold of 0 is unbiased, because their margins clear that amount on both sides. `ET_end − D` is at most −5.3 ms on every positive key that had an entry (−7.0 ms jittered). It is at least +7.9 ms on every negative key (+8.1 ms jittered) and on every `render2` key. An editor run is not a control, though. **So the editor run also reports its on-time share with the threshold at −4 ms and at +4 ms. If 95% falls between those two shares, the scenario is INDETERMINATE rather than PASS.** **INDETERMINATE does not pass the gate** (C-06, ADR-0013). The rounding bias is systematic, not sampling noise, so typing more keys will not resolve it. The editor's distribution has to move clear of `D`. The graded arm shows the gap is real: it is 92.9% late at threshold 0 and 71.6% at +4.
- **Keystrokes go through the browser's input pipeline**, using Playwright's `keyboard.press` (CDP `Input.dispatchKeyEvent`), never synthesised DOM events. Each arm runs at a fixed 100 ms cadence (strict), and again with per-key jitter so that keystrokes sweep the frame phase. Both are recorded.

**Why not the three earlier rules.** Each paragraph records the measurement that ruled a definition out, so a later editor does not bring it back.

- **Counting recorded `rAF` callbacks between the keystroke and its frame.** The idea was that blocking would show up as extra frames. It does not: a blocked main thread runs no `rAF` callbacks, so there is nothing to count. On the recordings this rule scored the 2.2R negative arm **0% late**, `render2` 0% and the paint arm 0%. It cannot see what it exists to see.
- **Summing `round(Δts / R)` over the same frames.** This assumed that a blocked vsync leaves a gap in the timestamps. Chromium leaves none. The pending frame runs late but keeps its original `ts`, so the delay sits in `run − ts`, which this rule never reads. code-reviewer's first probe showed it (1.2R scored 0/60 late, 1.5R 1/60). **Those two figures are unarchived:** they are not in `a616def`'s files, and they are kept only as the history of why the probe was run. The #11 recordings confirm it: **0% late** on negative, 0% on `render2`, 2.1% on paint and 0–0.5% on graded. Judging the frame's `run` time against `D` instead does see input-handler blocking (negative 100%), but it still scores `render2` 0% and paint 9.3%. Work queued into the next `rAF` runs after that frame's callback starts, so a rule built from `ts` and `run` alone cannot see the place where CodeMirror's cost sits.
- **A post-paint mark `q_k` against `D`.** `q_k` is a `MessageChannel` message posted inside frame `k`'s `rAF` callback. This was the previous text of this subsection. It does see input-handler blocking (negative 100% late) and `rAF`-phase work (`render2` 100%). **It fails the positive arm by itself: 97.3% on time strict and 95.6% jittered, against a ≥ 99% bar.** It marks the end of a main-thread task rather than presentation, so its timing noise lands on a trivial editor. It also catches only 63.9% of the paint arm, because raster and compositing happen after the mark. Only a mark taken at presentation sees input work, `rAF`-phase work and paint cost together, and Event Timing is that mark.

**The measurement settled it: raw recordings, scored offline by every candidate rule.** The control arms did not. They are what any future definition must pass on the same kind of recording. Every arm runs in the same harness, at the same cadence, with the same scenarios. Each arm's measured E0 score and its role:

| Arm | What it is | E0, measured | Role |
|---|---|---|---|
| Positive | bare `contenteditable` | 100.0% on time, n = 297, strict and jittered. Keys with no entry: 190 strict, 185 jittered. Worst-case absent margin: 0.80 ms strict, 0.70 ms jittered | **Gate on the run: ≥ 99% on time over at least 300 scored keys, strict AND phase-swept**, or the run is rejected |
| Negative | 2.2R busy-block in the `input` handler | 100% late, strict and jittered, n = 97. Keys with no entry: 0 | **Gate on the run: ≥ 95% late**, or the run is rejected |
| `render2` | 2.2R busy-block in an `rAF` callback queued by the `input` handler (where CM6 does its measure and DOM update) | 100% late, n = 97. Keys with no entry: 0 | **Gate on the run, required: ≥ 95% late.** It proves the rule sees `rAF`-phase work, which is where CodeMirror's cost actually sits |
| Paint | blur/drop-shadow repaint on every key | 100% late, n = 97. Keys with no entry: 0 | Reported. It shows the rule sees raster cost |
| Graded | 1.5R busy-block in the `input` handler | 86.3–93.9% late over 3 runs, 89.3% jittered, n = 197 each. Keys with no entry: 0 in every run | **Reported, not gated. Expected band 85–95% late** |

- **Graded is hypersensitive by construction, which is why it is not gated.** Presentation is quantised to vsync. A 1.5R block that starts anywhere in frame `j` always misses frame `j+1`, so it presents about one frame later than a positive key, close to `D`. Each key's verdict is then decided by the compositor's offset and the 8 ms rounding. The earlier draft expected about 50% late because it reasoned in continuous time, and that was wrong. A result outside the 85–95% band is investigated, not failed.
- **Scored keys, and the warm-up.** The positive arm scores at least 300 keys, and the negative and `render2` arms at least 100 each. All are counted after a **declared warm-up**: the first 3 keys of each run go to focus and are excluded (`analyze.mjs`'s `.slice(3)`). That warm-up is why the recordings scored 297 and 97. No keys were dropped. The warm-up length is recorded on the run line. **Any other key that goes unscored is recorded with its reason.**
- **Mutation is required, and it is the reason a negative control exists.** Forcing every verdict to on time (`frames_to_paint = 1`) takes the negative arm from 100% late to 0% late, so the run goes red. The positive arm stays at 100%. A positive arm alone therefore cannot tell a working rule from a constant. The harness's test suite must carry that mutant, and both the negative and `render2` arms must turn it red. Without it, this gate would be one more guard that cannot fail.
- **No compositor margin.** E0 already ends at the browser's presentation time, so the margin the previous draft deferred is not needed in Chromium.

**Caveats that travel with every figure.**

- **Headless Chromium presents through a software compositor**, so "presentation" here is a proxy. **NFR-PRF-02 is not signed off until the same rule, with the same three gated arms, has passed on the WebView2 reference machine.** That run is listed in §Open design questions.
- **Event Timing exists only in Chromium, so the gate is Chromium/WebView2-only.** WKWebView (macOS) has no Event Timing, so E0 cannot be computed there, and **macOS is explicitly not gated by NFR-PRF-02.** Instead it gets a figure from a different mark: the post-paint `MessageChannel` rule (`q_k > D`), labelled as a main-thread proxy, with the same control arms run and reported beside it. That rule's faults are recorded above: about 3–4% false-late on a trivial editor, and blind to raster cost. The figure is a trend line and is never a pass. WebKitGTK also lacks Event Timing and gets the same treatment.

**Diagnostic (b), reported and not gated:** the editor's own work per keystroke, in milliseconds. It is the handler time (`p − processingStart`, where `p` is stamped at the end of the dispatch, after CodeMirror's synchronous view update) plus frame `k`'s rendering. Frame `k` is the first frame whose `rAF` callback runs after `p`, and its rendering runs from that callback to the post-paint `MessageChannel` mark `q_k`. The diagnostic excludes the vsync wait by construction, and it is the number to look at when the frame metric fails. Measured `k = j+1` for 86–100% of keys across the arms. That is why `k` locates work but never judges it.

PRD v1.6's acceptance wording (*painted in the first frame after the keystroke*) is unchanged, and so is NFR-PRF-02's statement. This revision changes nothing in the PRD. It only defines how a keystroke is counted, and that is architecture's to define.

**Acceptance wording offered to product-analyst (task #32):** *"Given a 5,000-line note in the editor, when each benchmark scenario is typed through the browser's input pipeline, then at least 95% of keystrokes are painted in the first display frame after the keystroke, in every scenario, and a bare-contenteditable control arm on the same run is at 99% or better; the editor's own per-keystroke work is reported beside it."* The requirement's statement would read *"A keystroke's change shall be painted in the first display frame after it (16 ms is one frame at 60 Hz) for at least 95% of keystrokes in a 5,000-line note."*

The harness runs Playwright/Chromium against the production vite build, with the IPC client stubbed. The keystroke path makes no IPC call. Asynchronous replies still land on frames, though: the debounced save, the batched link resolution and a switcher-mode completion. So the stub answers each with **latencies recorded from the real binary** (a table of per-command p50/p95 captured once per build), rather than instantly. A reply that lands mid-typing is then inside the measurement, as it would be for a user.

- **Note.** A generated 5,000-line note: paragraphs dense with wikilinks, 50 GFM tables, task lists, footnotes, fenced code, headings every ~40 lines, a CRLF variant and a BOM variant. It lives with the harness, because the benchmark vault's notes average about 2 KiB.
- **Scenarios**, each at least 500 keystrokes with the viewport at the cursor: typing at the start, the middle and the end; typing inside a table cell; typing in a link-dense paragraph; Enter mid-note; Backspace across a bold delimiter (reveal/hide); and continuous typing in split-preview mode, so that a preview render landing on a frame is inside the measurement.
- **Basis.** Headless Chromium on the harness machine. It is the same engine as WebView2, not the same process or compositor. WKWebView and WebKitGTK are not gated, because E0 needs Event Timing (see the caveats above and F-96's basis clause). Every figure carries that basis, with the Chromium version and the measured `R`.

## Cross-cutting concerns (packaging, security, verification)

Three areas that carry Must-priority requirements and no interesting mechanism, which is exactly why they are easy to leave undesigned until they become a crisis. This section exists because a coverage check against the requirements baseline found them missing.

### 10.1 Distribution

Tauri's bundler produces the three platform artefacts from one workspace. macOS builds are signed with a Developer ID and notarised in CI, so a first launch shows no Gatekeeper warning; Windows builds are signed with an Authenticode certificate. Linux ships an AppImage and a .deb. Updates use signed manifests: the updater verifies a detached signature against a public key compiled into the binary, so a compromised update host cannot ship a payload.

Crash recovery is a journal, not a heuristic. Unsaved editor buffers are written to .serat/recovery/ on a two-second debounce, keyed by path and base hash; on startup any journal entry whose target file still matches its base hash is offered for recovery, and any whose target has changed underneath is offered as a diff instead. The journal is cleared on clean shutdown, so its presence at startup is itself the signal that the last session ended badly.

| Requirement | Design                                                                                                             |
|-------------|--------------------------------------------------------------------------------------------------------------------|
| FR-PLT-01   | One workspace, three bundler targets, one CI matrix.                                                               |
| FR-PLT-02   | Developer ID signing and notarisation on macOS; Authenticode on Windows. Both in CI, never on a developer machine. |
| FR-PLT-03   | Signed update manifests verified against a compiled-in public key.                                                 |
| FR-PLT-04   | Debounced buffer journal in .serat/recovery/ keyed by path and base hash.                                          |
| FR-PLT-05   | Settings as a readable TOML file in the platform config directory, version-controllable.                           |

### 10.2 Security posture

The security requirements are mostly negative — statements about what must not happen — and a negative is only credible if something enforces it. Each therefore has a mechanism rather than an intention.

| Requirement                          | Enforced by                                                                                                                                                                          |
|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| NFR-SEC-01 · no telemetry            | There is no analytics dependency in the tree, and CI fails on a deny-list of known telemetry crates. A network capture over a full session is part of the release checklist.         |
| NFR-SEC-02 · no unconfigured network | All outbound calls go through one client in serat-ai. With no provider configured it is never constructed, and a test asserts the process opens no socket during a scripted session. |
| NFR-SEC-03 · sandboxed extraction    | Child process with time and memory caps; the worker binary links no HTTP client at all, so a network call is a link error rather than a policy violation.                            |
| NFR-SEC-04 · credentials             | OS keychain via the keyring crate. A filesystem scan after configuring a key is part of the release checklist and must find no key material.                                         |

| FR-BIN-19 · binaries never rewritten | No write path accepts a non-Markdown target. Verified by comparing content hashes of every asset before and after a scripted session.                                                |

### 10.3 The verification harness

Every performance requirement in the baseline is measured against one artefact: a generated benchmark vault. It is deterministic from a fixed seed, lives in the repository, and is built by one command, because a benchmark nobody can reproduce is a number nobody can argue with.

- Shape: 20,000 notes by default and 50,000 for the scale run, with a realistic long-tailed link distribution rather than a uniform one — a uniform graph makes rollups and backlinks look far cheaper than they are.
- Content: a mix of typed and untyped notes, frontmatter and inline fields, tasks with due dates and estimates, and roughly 200 assets across PDF, DOCX, XLSX and image formats.
- Determinism: one seed produces byte-identical output, so a regression is attributable to a code change rather than to a different vault.
- CI: one job per budget in NFR-PRF. A pull request that breaches one fails, which is what NFR-PRF-08 means in practice. The generator itself lives in the repository and runs from one documented command, which is NFR-MNT-02.
- Property tests: the write-back patcher runs against a corpus of real notes, asserting that no byte outside the target field's range changes — NFR-MNT-03, and the single most important test in the suite.

**One thing is true of every P0 performance number and is worth saying once here rather than in each report.** Both figures the spike still argues about reduce to the same sentence: **the code is fine and the measurement environment is not the one the charter judges.** NFR-PRF-01's binding Serat term clears its budget while the platform term it excludes cannot be measured stably at all (F-407); NFR-PRF-03 sits at 4.306 ms against 50 with 11.6x of headroom. Both carry `gate_eligible: false` because the reference machine runs with real-time scanning off (RISK-012), and NFR-PRF-04's own drift is 35% session-to-session on unchanged code (F-327). **So the open question on both is the environment, not the design** — and the honest consequence is that a budget whose measurement noise or exemption exceeds its own margin is not yet a gate, whatever the number says. That is one statement about three requirements, and it is here so it stops being re-derived in each of them.
