# SIGBUS fix check: serat-app fixtures on tmpfs (task #124)

Serves NFR-REL-01 · NFR-PRF-08 · NFR-MNT-01. Owner: test-engineer. Follows `docs/05-testing/sigbus-105.md` (task #105b), which holds the diagnosis.


## Fix check

Change (test code only, `crates/serat-app/src/lib.rs::test_temp_dir`): every `std::env::temp_dir()` in the serat-app test modules (15 sites in `state.rs`, `index.rs`, `consumer.rs`, `vault.rs`, `settings.rs`, `lib.rs`, `asset/tests.rs`) now goes through a `#[cfg(test)]` helper that uses `/dev/shm` (tmpfs) when it exists and a probe file can be written there, otherwise the ordinary temp dir. The `-shm` mappings of the fixtures' `index.db` are then memory-backed. The shipped app is untouched and keeps WAL on the user's disk (ADR-0015). `crates/serat-app/tests/acl_behaviour.rs` (one `temp_dir()` use) is an integration test that opens no index and was left alone.

Repeat of the relink experiment, same method as experiment 2 (same loop, `--test-threads=1`, relink of the same path under the running binary, 10 rounds, fresh target dir with `CARGO_PROFILE_DEV_DEBUG=0`): **0 SIGBUS in 10 rounds** (all binary runs exit 0, 353 passed; all builds exit 0; in the three rounds sampled (1, 5, 10) the binary was still running and finished 9 to 11 s after the build log; no core). Baseline before the fix: 1 SIGBUS in 5. Ten clean rounds is not proof (at a 20% baseline the chance of ten clean rounds with no fix is 0.8^10, about 11%), so treat it as supporting evidence and keep the process rule from the previous section.

### Same hazard elsewhere (not changed here; named for owners)
- `crates/serat-index` tests (`src/*.rs` and `tests/*.rs`, about 100 `temp_dir()` uses): same hazard, they open a WAL index on `/tmp`.
- `crates/serat-vault` tests (`src/*.rs`, about 45 uses): same hazard only where a test opens an index; the vault crate itself holds no SQLite, so its fixtures map nothing.
- `bench/budget` (`lib.rs`, `subject.rs`, `tests/vault_gate.rs`, `tests/frontmatter_lists.rs`) and the 20k vault under `bench/vaults`: the vault is generated into the repo, and the budget jobs index it with a real WAL `index.db` on the checkout's disk. That is the hazard, and unavoidable by design for the budget jobs: they must measure the real disk, so they must not run concurrently with another cargo (process rule) and cannot move to tmpfs without changing what they measure.
- Fixture cleanup (S1 of the #124 review): fixtures did not delete their directories. 4,892 leftover `/tmp/serat-app-state-*` directories existed at the start of #124, and before cleanup each full serat-app run left about 5.5 MB in `/dev/shm` (60 MB after 11 runs; 22 entries per run; `refused-cap` alone about 4.2 MB, 1,005 one-byte files of 4 KB each). That is RAM. The `state.rs` and `settings.rs` fixtures, and `settings_state`, now return `crate::TestDir`, a guard that removes the directory in `Drop` (so a panicking test cleans up too, and a directory a test replaced with a file is removed as a file). Measured on one full `serat_app` lib run: **0 directories and 0 KB left in `/dev/shm`** (it was about 5.5 MB), with 353 passed and 6 ignored. The 226 leftover `serat-app-*` and `serat-settings-*` directories from the #105b and #124 experiments (60 MB) were removed afterwards, and only those whose pid was no longer alive.
