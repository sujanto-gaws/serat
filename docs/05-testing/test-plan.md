# Test Plan

**Owner:** test-engineer · **Status:** P0, live · **Upstream:** `docs/02-requirements/prd.md`, `docs/03-design/architecture.md` §10.3

Design goal 3 is "correctness is provable, not argued". This plan is how that is discharged: what is tested, by what kind of test, and which requirement each test answers to.

## Identifier scheme for tests

Tests are identified `TC-nnn`. **Not `T-nn`** — CLAUDE.md reserves `T-nn` for threats in the threat model, and a test plan that quietly squats on the threat namespace makes every cross-reference ambiguous. Like every other ID in this project, a `TC` number is permanent and is never reused once dropped.

Every test cites the FR-/NFR-/US- it verifies. A test that verifies nothing on the list is either testing an accident of the implementation or has found a missing requirement; both are worth saying out loud rather than leaving in the suite.

## Strategy

Six kinds of test, chosen because six different kinds of thing can be wrong.

| Kind | What it answers | Where it lives | Runs |
|---|---|---|---|
| **Unit** | Does this function do what its name says? | `#[cfg(test)]` in the owning crate | Every `cargo test` |
| **Integration** | Do two crates agree at their boundary? | `crates/<crate>/tests/` | Every `cargo test` |
| **Property** | Is this invariant true for *every* input, not the three I thought of? | `crates/<crate>/tests/` | Every `cargo test` |
| **Benchmark** | Is it fast enough, on a named machine, against a named vault? | `bench/` | CI budget jobs, per PR |
| **Conformance** | Does the query language mean what the grammar says? | `grammar/conformance.md` + a runner | P2 onward |
| **Hostile** | Does it survive the world being unfriendly — concurrent edit, undo/redo, crash mid-write? | `crates/<crate>/tests/` | Every `cargo test` |

Five rules that follow from the constraints rather than from taste:

1. **Every budget has exactly one asserting job** (NFR-PRF-08, C-06). A budget with no job is not a budget, it is an aspiration. A job that measures something other than what the requirement says is worse than none, because it produces a number people trust.
2. **A measurement names the interval it times.** Every budget carries the interval as data, printed and recorded, and a test fails a budget that leaves it blank. P0 finding F-03 — that NFR-PRF-03's 50 ms and §3.1's 150 ms coalescing window cannot both be about the same interval — is what happens when nobody writes it down. Where a requirement is genuinely ambiguous, the harness measures both readings and says which one it asserted.
3. **The gate number is measured in the environment a user has.** Filesystem-bound budgets are measured on the reference machine both with the on-access virus scanner enabled and disabled, and the *enabled* figure is what the gate is judged on. The harness detects the scanner state and marks a disabled run as not gate eligible, so a best case cannot be filed as a verdict. See `reference-machine.md`.
4. **A threshold is never weakened to make a build pass.** If a budget is genuinely wrong, it is re-baselined by product-analyst in the PRD with the measurement attached (task Q1), and the change is visible in the requirements history. Editing a number in a CI file is not that.
5. **The write-back patcher is property-tested against a corpus of real notes** (NFR-MNT-03) — that no byte outside the target field's range changes. Architecture §10.3 calls it "the single most important test in the suite" and P2 does not close without it.

## The verification artefact

One benchmark vault, generated by one command, deterministic from one seed. Documented in **`benchmark-vault.md`**; the machine every budget is measured on is **`reference-machine.md`**; the jobs that assert the budgets against it are **`budget-harness.md`**. Nothing in this plan measures performance against anything else.

## Entry / exit criteria

**Entry to a test gate:** the artefacts under test exist at their stated paths, `cargo test --workspace` and `cargo clippy --workspace --all-targets -- -D warnings` are clean, and the benchmark vault has been regenerated at the current `VAULT_FORMAT_VERSION`.

**Exit from a phase gate:** every requirement in the phase's scope has at least one passing test citing it; every budget in scope has a passing job; the measured numbers are recorded in `reports/` with the machine, the vault digest and the generator format version attached; and any failure is either fixed or carried as a named task owned by the crate that owns the defect.

**A failure becomes a task**, assigned to the owning dev, with the reproduction steps and the exact command. It is not a comment in a report.

**A measurement states the conditions it could not control, not only the ones it did.** No cold-start figure taken on the reference machine is a cold-*vault* figure: every iteration reads a page-cached vault, and dropping the Windows page cache needs privileges the measuring account does not have. Measuring against freshly generated vaults instead gave +42.9 ms against a null control of +15.9 ms with the same binary on both arms, so most of it was the harness measuring itself. That bound goes in the gate report beside `gate_eligible: false`, because a reader who takes a warm-vault number for a cold-vault one has been misled by omission rather than by error.

**A guard is only real at the level it runs, and only real if something has watched it fail.** Reading a test does not tell you whether it can fail — the assertion looks right either way. `bench/budget` is therefore swept by mutation before a gate number is taken: change one thing, run the suite, record whether anything went red. The first round of 16, whose tests I had written deliberately, caught 16; the second round of 10, aimed at code I had *not* written a test for, had **5 survivors**. Four of the five were the same shape — the guard was tested and its caller was not — and three could only be closed by testing at the level the guard actually runs, which is why `bench/budget/tests/vault_gate.rs` generates a real vault and tampers with one byte of it. The sweep is a technique, not a fixture: a mutation harness that runs in CI becomes a thing to satisfy rather than a thing to learn from, and the record of what it found belongs in the gate report.

**A test asserts what the mechanism actually does, including its limits.** Architect measured that truncating the index — by 0.1%, by half, to 5%, to 100 bytes — makes every statement fail immediately, `PRAGMA user_version` included, because SQLite compares the header page count against the file size. That is exactly NFR-REL-02's acceptance criterion, so TC-025 truncates and expects detection at open. But overwriting 4 KB mid-file passes the whole open check, passes `count(*)` over notes and blocks, and passes a full-text match; only `quick_check` catches it. So TC-060 asserts the *honest* property — that when a query touches the damaged page, `SQLITE_CORRUPT` routes to the same rebuild rather than to an error dialog — rather than claiming an open check catches arbitrary corruption. A test that asserted the stronger thing would pass today and mislead whoever read it.

Four things in `ci.yml` are deliberate:

**The suite runs from outside the repository root, twice.** Once from a `git worktree`, which is the layout `coding-standards.md` mandates for every teammate, and once from a plain copy in a temporary directory, which catches anything that needs the repository root to be an ancestor at all. This job exists because a real defect shipped that way: the dependency-rule check matched the substring `.worktrees` anywhere in an absolute path, so it passed at the repository root and failed one directory over — green for the lead, red for everyone working where they were told to. A suite whose result depends on which directory it ran in is a measurement that reports success because of *where* it was taken rather than *what* it measured, which is the class of defect this entire harness exists to prevent. CI is where "it passes on my machine" is supposed to die.

**The tests run twice more, per crate as well as per workspace.** The workspace run is the gate the definition of done names. The per-crate matrix exists because a workspace-wide gate couples every teammate's completion to every other teammate's crate compiling at that instant — P0 finding F-07 records that the real cost of this project so far has been coordination rather than Rust, and this is one of the places that cost lands. When the workspace job is red, the matrix says whose crate it is without anyone reading a log.

**The crate matrix is derived from `cargo metadata`, not typed out.** A hand-written member list drifts silently the first time somebody adds a crate, and a matrix that has quietly stopped covering a crate is worse than no matrix.

**Every Linux job that compiles the workspace installs Tauri's apt dependencies first.** `serat-app` (task S1) did not exist when this workflow was written, and Tauri v2 needs `libwebkit2gtk-4.1-dev` and friends to link on Linux — a gap `dev-setup.md` still has for a local Linux checkout. Found while rebasing this branch onto the main `serat-app` landed on, and fixed here rather than left for the first Linux CI run to surface as an unhelpful linker error nobody had a step to fix.

One job, `definition of done`, is green only when every leg is, so a branch protection rule has a single thing to point at.

## Reports

One report per gate, in `reports/`, from `reports/TEMPLATE-test-report.md`. Every report records the reference machine, the benchmark vault's `tree_digest_sha256`, the generator's `VAULT_FORMAT_VERSION`, the measurement environment (real-time scanner state and power plan), and the raw numbers — not just the pass/fail. P0 numbers replace the blueprint targets before P1 starts (charter §Milestones, working agreement 6), so they are reported to product-analyst and architect explicitly rather than left in a file for someone to find.
