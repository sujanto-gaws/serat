| F-03 | **RESOLVED — there was never a conflict; the design document was missing a paragraph.** F-03 conflated two paths into the index. A save made *in Serat* goes write → parse pool → writer with **no watcher and no debounce**, and that is NFR-PRF-03's 50 ms. An *external* change goes through the 150 ms coalescing window and is FR-VLT-04, whose own acceptance criterion is 500 ms — it allows 500 precisely because it has a debounce to absorb. The two requirements never conflicted. What makes this a discovery rather than a rationalisation: **§3.2 already requires the save path.** Echo suppression *drops* the watcher event for Serat's own write, so an index fed only by the watcher would never index a note saved in Serat at all — the mechanism that exists to prevent duplicated work would prevent all of it. For product-analyst at Q1 this is a wording clarification naming the path and the interval, not a re-baseline of the number. The lead's earlier framing — "unsatisfiable as written" — was right about the watcher path and wrong to imply the requirement was unmeetable. | rust-core-dev found it; architect ruled | Closed |
| F-04 | **`rebuild()` has no legal home under §2.1.** It walks, parses and writes, and no product crate may do two of those; the budget harness and T1 must both run without Tauri. | F-06 | **Backpressure was undefined and had to be decided in code.** Review verdict: the *policy* is defensible and needs no ADR to permit it; what an ADR should record is **which producer may be dropped**, not whether dropping is allowed. Blocking the producer instead blocks the watcher's coalescer, overflowing the OS event buffer — losing events with no record that anything was lost, the one failure C-02 cannot absorb. "Bounded" in §3.1 step 2 reads as a memory statement when it is a correctness one. | rust-core-dev, forced by I2 | Open — ADR-0011 candidate |
| F-07 | **A-06 / RISK-002: the Rust is not the risk.** serat-vault compiled first try, 35 of 40 tests passed on the first run, two clippy findings across two tasks, rusqlite bundled built SQLite unattended. | F-09 | **§1.2's three assumptions: P0 has produced evidence on none of them.** (a) *Write contention is the bottleneck* — not tested; first measurable in I4. | F-10 | **A single rebuild number cannot answer open design question 1.** The rebuild's cost splits four ways — walk, read+hash, parse, write — because the walk enumerates without hashing. Reported as one number, "the index writer dominates" and "reading 39.4 MiB off disk dominates" are indistinguishable, and they imply completely different fixes. B2 must report the four phases separately before it hardens; otherwise the P0 gate produces a number that passes or fails without saying what to change. | rust-core-dev, from I2's walk | **Implemented in B2** (`2186da0`). `prf04-full-rebuild` records walk / read+hash / parse / write beside the aggregate, in ms and as a share of wall clock, in both report and result JSON; the budget still asserts the total. | F-11 | **The drop-latch-rescan recovery path re-enters the loss, and it loses files permanently.** Queue capacity is 8,192; the P0 vault is 20,200 files; `walk()` returns sorted paths and the queue is FIFO, so every rescan pushes the same sequence and the same 8,192 paths win the slots. Running the documented contract exactly — full walk, push all, drain, check latch — **12,008 of 20,200 files had never once reached the consumer after five rescans.** A stable loop, not a slow one. It also means the *first* index of a 20k vault drops ~12k paths unless the consumer outpaces the walk, which a cold start cannot promise. Root cause: the bulk producer is routed through the bounded queue that drops. Fix: the walk hands `Vec<VaultEntry>` to the consumer directly, or `push` gets two modes so the walk blocks while the watcher drops — blocking the walk is safe because it is not the coalescer, so the OS-event-buffer argument does not apply to it. | code-reviewer, reproduced | Open — BLOCKING on I2 |
